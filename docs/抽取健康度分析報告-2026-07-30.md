## 0. 三句話結論

1. **兩個可選的模板都不對，而對的那個被鎖著。**
   `factory_report` 的機台填出率 **5.9%**、工單 **12.7%**；`general` 則完全放棄 L2。
   `service_order` 才符合實際業務物件，但它 `selectable: false`（§2）。
2. **只有 4.2% 的內容是「日報」。** 37% 是研發討論、20% 是「採購」、15% 是「維修」（§3）。
   —— 之前用產線報工模板抽不到東西，不是 AI 抽不好，是**客戶根本不在講那些**。
3. **⚠️ 連 L1 的分類本身都不合 —— 而這是 prompt 寫成那樣，不是 AI 分錯。**
   `procurement` 的定義裡明寫「零件詢價、報價」，所以客戶詢價落進去是照著做；
   而且沒有任何一類對應「業務／銷售」或「內部系統」，模型沒有別的地方可放（§4）。
   **好消息是這最便宜** —— `category` 是自由字串，改租戶 prompt 一行即可（§6.2）。

## 4. ⚠️ L1 的分類本身也不合

抽樣檢視後發現兩個分類是**大雜燴**，裡面裝著性質完全不同的事：

### 4.1 `maintenance` 裡有一半不是維修

| 實際標題 | 真正的性質 |
|---|---|
| A3唐修豪1升降機線路接觸不良查修完成 | ✅ 設備維修 |
| JS日峰品檢缺失修繕完畢 | ✅ 品檢修繕 |
| **鄭晴予 NAS／維修課系統存取問題** | ❌ **IT 權限** |
| **正航帳號權限未全開，需請郁嫺協助設定** | ❌ **IT 權限** |
| **郁芬桌機汰換／資料轉移安排** | ❌ **IT 資產** |
| **客訴：保固中車輛收費爭議** | ❌ **客訴** |
| **南部維修需旅玩家側門扶手治具** | ❌ **治具調度** |
| **2026-07-24 業務二部售服進度回報** | ❌ **售服工單**（客戶＋項目＋金額＋狀態）|

### 4.2 `procurement` 裡有一半是客戶詢價

> ⭐ **2026-07-30 補充 —— 這不是 AI 分類錯，是 prompt 就這樣寫的。**
> 租戶 prompt（`tenant-twh.ts`）裡 `procurement` 的定義是：
> 「**零件詢價、報價**、下單、交期、供應商、物料庫存」
> —— 「詢價、報價」是定義裡明寫的。客戶詢價落到這裡，是模型照著指示做。
> 而且**沒有任何一類對應「業務／銷售」**，它沒有別的地方可放。
> 同理 `maintenance` 的定義含「設備／工具異常」，IT 帳號問題就被掃進去了
> —— 因為也沒有「內部系統」這一類。


| 實際標題 | 真正的性質 |
|---|---|
| 請購單2026072202-FRP高頂安裝用工具簽核 | ✅ 請購 |
| A1庫存車8171點料 / B3白永恩點料 | ✅ 領料 |
| **雲林順益斗六廠詢價：得利卡側踏** | ❌ **業務詢價** |
| **彰化員榮醫院詢價：側踏** | ❌ **業務詢價** |
| **客戶詢價：旅行家/現代/得利卡福祉車報價** | ❌ **業務詢價** |
| **客戶來電購買輪椅安全固定帶5件組** | ❌ **業務接單** |
| **星統訂單修改 / 兩筆訂購單轉銷貨審核** | ❌ **訂單處理** |

> **為什麼這件事比模板更嚴重**：`category` 的填出率是 100%，看起來最健康 ——
> 但它把「IT 權限申請」歸成維修、「客戶詢價」歸成採購。
> **填得出來 ≠ 填得對。** 下游任何按分類做的統計（部門負載、問題類型分佈）都會失真，
> 而且**看不出來**（因為每一筆都有值）。

## 6. 建議

### 6.1 立刻可做（不需客戶確認）

| # | 建議 | 理由 |
|---|---|---|
| **A** | **把 `service_order` 開放 `selectable: true`，並切給台灣福祉** | §5 已提供 OQ-ESO-1 缺的欄位證據 · schema 與 prompt 都寫好了 |
| **B** | **不要停在 `general`** | 它讓 L2 完全停產 · 現在的設定是三個裡最沒有產出的 |
| **C** | 抽取健康度加一欄「**該模板下產出了幾筆 L2**」 | 目前只看欄位填出率 · `general` 的填出率是空的（沒有追蹤欄位），看起來「沒有警訊」，實際是沒在抽 |

### 6.2 分類問題 —— ⚠️ **本節於 2026-07-30 更正：它比我原本寫的便宜得多**

> **原本的寫法有誤。** 我把「拆分類」寫成需要權衡的 schema 決策，
> 實際上 `category` **早就從 enum 開放成自由字串**（WTB-M2），靠 `category_registry` 收斂 ——
> `CategoryEnum` 只是「建議清單」，prompt 提示模型優先歸入已知值。
>
> 所以**加分類 ＝ 改租戶 prompt 的六類定義，一行的事**：
> 沒有 migration、沒有 enum 變更、沒有 schema 變更。
> 新分類第一次被用到時會自動註冊進 `category_registry`（per-tenant · 目前 6 個都是 active）。

而且**租戶 prompt 本身就是為此設計的第三個槓桿** —— 我原本的報告只寫了「換模板」，
漏了「調租戶 prompt」。實際架構是兩層相加：

```
tenant.systemPrompt（每家自己的：分類定義／主檔／詞庫）
      ＋ TEMPLATE_REGISTRY[template].promptFragment（業種模板的 L2 規則）
```

（見 `classify.ts:65`）

#### 具體建議的 prompt 改法

關鍵的判別軸是**錢的方向**：採購是花錢（對供應商）、業務是收錢（對客戶）。
現在兩者被混在同一類裡，導致「這個月採購多少」與「這個月接了多少詢價」都算不出來。

| 現在 | 改成 |
|---|---|
| `procurement` 採購：**零件詢價、報價**、下單、交期、供應商、物料庫存 | `procurement` 採購：**對供應商的**詢價／報價／下單／交期、物料庫存 |
| （無） | **`sales` 業務**：**客戶端的**詢價／報價／接單／訂單修改／標案 ← 新增 |
| `maintenance` 維保異常：車輛售後報修、**設備／工具異常**、維修保養、備品更換 | `maintenance` 維保異常：車輛售後報修、**產線設備／工具**異常、維修保養、備品更換 |
| （無） | **`it_support` 內部系統與設備**：帳號權限（NAS／ERP）、電腦設備、系統操作問題 ← 新增 |

> ⚠️ **不要無限加分類。** 每多一類就多一個模型要判斷的邊界，也多一個統計維度。
> 上面兩個新類都有明確證據（客戶詢價 ≥4 筆、IT 支援 ≥4 筆）且**判別軸清楚**
> （對客戶 vs 對供應商；車輛設備 vs 辦公室系統）。判別軸模糊的就不要加。

> ⚠️ **歷史資料不會重算**（既有承諾）。所以改完之後前後期的分類統計語意不同，
> 報表上要標分類定義的變更時間點（同 FMEA E-1）。

### 6.3 不建議做的

| 不要做 | 為什麼 |
|---|---|
| 切回 `factory_report` 期待工時 | 機台 5.9% / 工單 12.7% / 工時 0% · 換回去只會拿到「有一列但每格都空」的日報 |
| 為了提高填出率而放寬抽取（讓 AI 猜機台編號） | 違反 R11（缺漏填 null、禁止臆測）· 填出率上升但資料是假的 |
| 在分類統計上做決策 | §4 · `category` 100% 填出但語意不準 · **先改 prompt 的分類定義**（§6.2 · 一行）再用它做管理判斷 |
