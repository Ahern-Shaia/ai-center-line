一 · 四條功能線

01

訂單

已定案🔧 底層已備 · pilot
LINE 群組 → 辨識文字與檔案 → 產出訂單 → 同步 ERP
  1. 機器人加入群組，客戶直接丟資料
    不限形式：對話文字、PDF、Word、Excel、照片截圖都收。只有這一條路，不另設人工輸入或系統端觸發的第二條路徑。
  2. 辨識並轉成結構化訂單
    抽出品號、品名、數量、單價、交期、客戶等欄位。
  3. 逐欄位判斷信心度把關點
    高於門檻自動帶入；低於門檻的單一欄位標記待確認，不整份退回。
  4. 確認後同步 ERP
    寫入訂單表單。
實作現況「對話分析 pilot」已可跑：LINE 匯出/上傳 → Claude 結構化抽取（zod schema）→ 產出記錄（tickets）→ 戰情室簽核 → Ragic 同步狀態欄位。**訂單專用**的欄位對應與寫入端待 ERP 表 fieldId（見文末阻擋項）。多模態（PDF/影像）辨識底層待接上（現以文字為主）。
02a

群組 → 工作日誌 → 任務

已定案✅ 大致上線
GROUP → DAILY LOG → TASK
  1. 被動收集群組訊息
    全程只收不回。記錄發言者、時間、內容、附件、來源群組，依綁定換算成員工身分。
    即時收集，不做分析
  2. 每日固定時間，逐群組產出工作日誌
    每個群組各自處理，不把多群組混在一起送進模型。
    每日排程（例如 20:00）· 批次，不逐則分析
  3. 萃取任務
    只挑有明確待辦性質的內容。輸出：事項、來源群組、來源訊息 ID、AI 建議負責人、優先度、分類。分類前先比對既有分類，語意相近就歸入。
  4. 任務同時走兩條路（互不阻擋）
    → 進負責人的日報草稿，不需等主管確認
    → 進待確認池等主管確認，確認後才寫入 ERP
    兩道關平行，日報不會因為主管沒空而延誤
  5. 主管於看板確認後寫入 ERP把關點
    確認事項是否成立、負責人是否正確，可改派。寫入異常通知單、QRQC 主表或專案表單。
實作現況群組訊息即收即存、批次分析、tickets 分類、戰情室任務看板（待簽核/逾時/已簽核）、單筆簽核、每日日誌檢視都已上線。寫入 ERP（Ragic）的欄位對應待 fieldId。
02b

私訊 → 個人日報 → 本人確認

已定案✅ 已上線（含 LIFF）
DIRECT MESSAGE ＋ TASK → DAILY REPORT → SELF CONFIRM → ERP
  1. 員工工作中隨手回報
    私訊說明「開始做什麼」與「這件事結束了」。不需格式、不需一次講完、不需要自己打時間。
    系統取訊息送出時間作為時間戳記
  2. 系統計算各事項時長
    以開始與結束兩筆相減得出時長。只有開始沒有結束時，當天最後一筆以下班時間收尾並標記為系統推定，不與實際回報混同。
    工時要兩個點才算得出來，引導語須設計成一頭一尾都回報
  3. 草擬日報：私訊回報 ＋ 群組任務 合併
    同一人在多個群組被指派的任務全部集中進來，並標示來源群組。
    每日排程（例如 17:30）
  4. 推送給員工本人確認把關點
    可增刪項目、修改時間、移除不是自己的任務。確認前不是正式紀錄。修改過的欄位標記為手動修正，保留系統原始值。
  5. 確認後寫入 ERP 日報表單
    日報屬語意整理，不設信心度分數，一律經本人確認。
實作現況已上線：私訊落庫、17:30 排程草擬、LIFF「我的日報」可增刪/編輯/存草稿/送出、送出後通知主管。本週剛完成 LIFF 收斂——LIFF 與網頁共用同一份 React 元件（單一實作、不再發散），時間欄位已加格式驗證。寫入 ERP 日報表單待 fieldId。
03

定位

新增📋 設計完成 · 待開發
圖文選單打卡 → LIFF ＋ GPS → 客戶選單 → 路徑里程 → 併入日報
  1. 出發與抵達各打卡一次（可多站）
    從圖文選單點進去，出發打一次，抵達下一站再打一次。一天多站逐段各記一趟。
  2. LIFF 開頁自動抓 GPS
    在 LINE 內開網頁，自動取得座標與精度值。不用 LINE 內建的位置訊息——它沒辦法同時挑客戶，圖釘還能用手拖。
  3. 客戶選單指定地點
    打第一個字即篩選客戶主檔，查無則手動輸入地址。
  4. 計算路徑里程（只記距離、不算費率）
    兩點間實際行駛距離，非直線距離（直線會低估兩三成）。費率/報銷金額不在本線，在 04 費用線核算。
  5. 併入當日移動紀錄，供 04 費用核算
具體情境
09:50　業務 B 在公司點圖文選單「出發」→ LIFF 自動抓到公司座標 → 選「A 客戶」→ 送出
10:35　抵達 A 客戶，點「抵達」→ GPS 座標與客戶主檔登記的座標相距 30 公尺，系統自動核對通過
13:00　點「出發」→ 選「B 客戶」
13:40　抵達 B 客戶，點「抵達」
結果：當日移動紀錄 — 公司→A 客戶 12.4 km、A 客戶→B 客戶 8.7 km，合計 21.1 km，自動併入當天日報的移動紀錄欄。
設計裁定（docs/modules/attendance-location-mileage.md） 取座標用 navigator.geolocation（LIFF 無 getLocation；含 iOS 16.4 定位 timeout 處理）；距離用雙 provider 可插拔（Google Routes ＋ OpenRouteService，管理員前端選用，aiproot 全域設定）；只記距離不算費率；上班打卡＋多次到點、逐段各記；打卡拍照建議智慧升級式（可疑才補拍＋開關）；前端座標零信任、後端速度/精度檢查。geofence（現場核對）與客戶座標核對需「客戶主檔含經緯度」——見文末阻擋項；MVP 可先不做 geofence。
需要一張客戶主檔：客戶名稱、地址、經緯度。存座標才能自動核對員工是否真的在客戶現場，以及計算兩點距離。
04

費用支出

新增📋 設計完成 · 待開發
私訊/LIFF 拍照 → 單據辨識 → 比對當月行程 → 核算 → 本人確認 → Ragic
  1. 上傳單據照片
    發票、收據、停車證明、計程車收據。走與日報回報同一個私訊/LIFF 管道，即收即存。
  2. 單據辨識（Claude 視覺）
    抽出金額、日期、品項、統編、發票號。每欄回信心度，缺漏填 null。
  3. 比對當月行程紀錄
    調出該月所有出發／抵達紀錄與里程（來自 03 定位線）。
  4. 依該公司設定的規則核算
    費率、計算方式、上限、單據要求，全部是每個客戶各自的設定值，不寫死在程式裡。里程 × 每公里費率的油資核算在此。
  5. 本人確認後回寫 Ragic「費用支出」表把關點
    客戶方自建 Ragic 費用支出表，透過 API 回寫，比照既有「訂單」確認流程（客戶語）。
具體情境
月底　業務 B 上傳 3 張照片：加油發票 1,200 元、停車費 60 元、計程車收據 350 元
系統　辨識金額與日期，三張信心度都在 0.95 以上，自動帶入
系統　調出當月行程：外出 21 天，總里程 486 km
系統　依該公司設定「每公里 5 元」核算差旅補助 2,430 元；停車與計程車依設定另計
系統　同時列出 2 天行程缺漏（有出發無抵達），該 2 天里程不予採計
結果：業務 B 看到核算明細與缺漏提示，補登其中一天後確認回寫 Ragic。
設計裁定（docs/modules/expense-receipt-ai.md）＋ 客戶語 Claude 視覺抽取（temp 0＋zod 鎖 schema＋影像 ≤1568px）；台灣特殊性＝民國日期正規化、二聯式/收據無統編＝不可扣抵；去重鍵＝發票號＋統編＋金額。客戶裁定：客戶方自建 Ragic「費用支出」表、透過 API 回寫、像訂單一樣讓他確認、不需戰情室檢視。待釐清：既有「訂單」確認流程長怎樣（要做「一模一樣」）＋ 費用支出表 fieldId。
這條線靠前兩條餵資料。單據月底才傳，行程資料整個月累積。油資按里程算，所以定位（03）沒做就沒有里程。辨識底層與 01 同一條管線，辨識對象換成單據而已，可沿用同一套辨識底層與信心度機制。

三 · 信心度是什麼

AI 辨識時除了讀出內容，也會給出「有多確定」的分數（0～1）。印刷工整分數高；模糊、手寫、被印章蓋住的分數低。

分數 ≥ 門檻自動寫入，不打擾使用者。九成清楚的資料直接過。
分數 < 門檻標記待人工確認，先呈現辨識結果供快速修正，確認後才寫入。

門檻的意義是分配人力。全部都要人確認，功能就沒價值；全部都不確認，遲早出事。

可以用信心度分數

OCR、表格辨識、影像辨識。這類模型的分數有實質統計意義，可直接當門檻依據。
用於 01 訂單、04 單據。

不能用模型自評分數

「這句算不算任務」「該歸哪一類」這種語意判斷。語言模型很擅長用很有把握的語氣講錯的事。
用於 02a 任務萃取與分類。

語意判斷改用結構性檢查，任一項不過就走人工確認：必填欄位有無抓到、金額與日期格式是否合法、客戶或料號能否在主檔對應到、小計與總計是否相符。

四 · 補登機制：五個情境　○ 規劃中

補登為什麼要嚴謹 客戶已確認日報的起訖時間與時長會作為出勤與工時依據。因此所有補登都必須留下軌跡：誰補的、什麼時候補的、原本是什麼、改成什麼。系統絕不可靜默補上任何時間。（現況：個人日報已有 aiItems/finalItems 雙軌與手動修正基礎；下列五情境的完整補登流程尚未實作。）

情境 1　忘記回報結束

員工 09:15 私訊「開始處理 A 客戶報價」，之後沒回報結束，直到 14:00 才傳「開始拜訪 B 客戶」。系統無法判斷報價做到幾點。
偵測
同一人有「開始」無對應「結束」，且已出現下一筆開始。
提醒
收到下一筆開始回報時即時反問「A 客戶報價是幾點結束的？」附快捷鈕（接續到剛才／自行輸入）。
補登
員工回覆，或在當日日報確認畫面補填。
未補登
該項時長顯示「未回報結束」，不自行推估。日報送出前必須選定一個時間。
標記
標示為手動補登，與即時回報區分。

情境 2　忘記打卡抵達

員工 10:00 從公司打卡出發前往 C 客戶，抵達後忘記打卡，直到 12:30 才在 D 客戶打卡。中間 C 客戶那段完全沒紀錄，里程算不出來。
偵測
兩次打卡間隔超過設定值（例如 90 分鐘），或有出發無抵達。
提醒
下次打卡時反問「10:00 出發後中間有去哪裡嗎？」提供客戶清單快速補選。
補登
補選地點與抵達／離開時間。查無客戶則手動輸入地址。
未補登
該段標記缺漏，里程不予採計，日報與費用單上顯示。
標記
補登的定位無 GPS 座標，標示為「事後補登、無定位驗證」。

情境 3　一整天完全沒回報

員工整天外出，忙到完全忘記回報，當天日報草稿是空白的。
偵測
草擬時點該員工當日零筆回報，且非請假或休假。
提醒
推送空白日報並提示補填，附上他當日在群組的發言時間點作為回憶線索（僅供參考，不自動轉成日報內容）。
期限
建議次一工作日內完成，逾期須主管核准並填寫理由。
標記
整份標示為事後補填。

情境 4　單據遺失

月底報帳時發現三週前的停車費收據弄丟，但定位紀錄顯示他當天確實去了客戶那裡並停留兩小時。
偵測
行程紀錄存在但無對應單據，且該類費用依該公司規則需附單據。
提醒
費用彙整時列為「缺單據」，不自動剔除也不自動通過。
補登
可提出無單據申請，填金額與說明，系統附上該日行程紀錄作為佐證。
核准
一律需主管核准，是否受理與上限依各公司設定。
標記
標示為無單據核銷，與有單據項目分開統計。

情境 5　月底才發現三週前有缺漏

月底核算時發現本月有四天行程不完整，最早一筆已是三週前，員工早想不起細節。
根源
缺漏偵測若只在月底跑，這種情況必然發生，而且必然補不回來。
正解
缺漏偵測必須每日執行，當天或次日就提醒，不要累積到月底。
期限
設補登截止日（例如次月 3 日前），逾期需主管核准。
月底
核算前先產出「本月缺漏清單」給員工與主管，處理完才進入請款。
標記
超過設定天數才補登的紀錄，標示補登延遲天數。

五 · 時間具出勤效力後的額外要求　🔧 部分

這一項改變了日報的性質 客戶已確認日報時間會作為出勤與工時依據。日報因此不再只是管理工具，而是具法定效力的出勤紀錄，適用勞動法規對出勤紀錄的保存、正確性與可查閱要求。以下設計請勿省略。
要求設計內容
🔧原始值不可覆蓋系統抓取的原始時間永久保留。員工修改時寫入一筆修正紀錄，不是覆蓋原值。日報顯示最終值，可展開看原始值。（現況：已有 aiItems 原始 vs finalItems 最終雙軌；完整逐欄修正軌跡待補。）
○完整修改軌跡記錄修改者、修改時間、修改前後值、修改原因（建議必填）。主管代改須另外標示。
🔧系統推定要標示非員工實際回報、由系統推估的時間（例如以下班時間收尾）必須明確標示，不得與實際回報混為一談。
○員工可查閱提供員工隨時查詢自己歷史出勤與工時紀錄的入口，並可申請匯出。
○保存年限出勤紀錄依法有保存年限要求，須確認客戶所在地規定並據以設定資料保存政策。
○告知義務員工須被明確告知「LINE 回報的時間將作為出勤依據」。這與先前 AI 加入群組的告知是兩件事，需另外完成並留存書面紀錄。
🔧異常不自動裁決缺漏、逾時補登、時間異常，系統只標示與提醒，不自動認定為遲到、早退或加班，一律由主管判斷。

六 · 費用規則為租戶參數　📋 設計
