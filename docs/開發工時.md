## 2. 方法與偏誤

### 2.1 怎麼算的

相鄰 commit 間隔**超過 90 分鐘**視為換一段工作；一段的工時＝該段第一筆到最後一筆的時距。
可跨午夜（本專案 41 段裡有 6 段跨），所以不按日曆天切。

`scripts/effort-report.py` 是唯一的計算來源，數字要重算就跑它，不要手改本文表格。

### 2.2 ⚠️ 為什麼不用「每日第一筆到最後一筆」

那個算法直覺上更合理（「那天投入在這個專案的時段長度」），但在**這份資料上會算出 244 小時**，
其中 **106.5 小時是日內空檔**：

| 日期 | 日內最大空檔 | 當日首末跨距 |
|---|---|---|
| 2026-07-21 | **15.5 h** | 22.3 h |
| 2026-07-05 | **10.9 h** | 20.2 h |
| 2026-07-03 | 9.9 h | 12.9 h |
| 2026-07-08 | 8.7 h | 17.7 h |
| 2026-07-28 | 6.7 h | 23.5 h |

15.5 小時的洞是睡覺，不是工作。**作息不規律又常跨午夜的專案，按日曆天切一定失真** ——
0.5 天的工作會被算成 23 小時。所以改切在真實的工作段。

### 2.3 這個數字**低估**了什麼

commit 時間看不到的工作，全部沒被算進去：

| 沒算到的 | 為什麼會漏 |
|---|---|
| 寫 design doc 的思考時間 | doc 寫完才 commit，一次 commit 前可能想了很久 |
| 查 prod 資料、排查 bug | 讀出來的結論進了 doc，過程沒有 commit |
| 等部署（Render 一次數分鐘～數小時）| 07-30 有一次等了 1 小時 40 分完全沒動 |
| 讀客戶 LINE 對話、對需求 | 完全不產生 commit |
| 與客戶／合夥人溝通 | 同上 |
| 段首之前的暖機 | 只有「＋20 分/段」這個粗估在補（＝13.7 h）|

### 2.4 這個數字**高估**了什麼

| 可能高估的 | 程度 |
|---|---|
| 段內的短暫中斷（回訊息、喝水） | 90 分鐘以下的空檔全數計入 |
| 一段裡穿插做別的事 | 無法從 git 分辨 |

**方向判斷**：低估的項目（design doc、查 prod、等部署）在本專案佔比很高
—— `docs/` 有 40+ 份 design doc、`scripts/prod-query.sh` 被大量使用。
所以 108.4 h 應視為**偏保守的下限**，實際投入更高。

**讀法與注意**：

- 每筆 commit 的成本＝與**前一筆**的間隔（段首記 0），所以加總剛好等於段內工時 94.7 h，
  不會因為換算方式多出或少掉時間。
- ⚠️ 但這個歸屬**系統性地把時間算給「後一件事」** —— 想了 40 分鐘才 commit 的那筆，
  40 分鐘會算在它頭上；反之收尾用的小 commit 會被低估。**scope 級的數字只能看趨勢，不能當結算依據。**
- scope 高度分散（100+ 個），因為 commit 訊息按功能命名而非按目錄。
  這對「哪個模組花最多時間」的分析不利，但對翻歷史很有用，不打算改。
