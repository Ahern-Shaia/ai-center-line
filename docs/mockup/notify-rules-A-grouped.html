1 「無限往下」先用分組解決，翻頁是後備 —— 依客戶分組並可收合，組頭直接寫「7 條 · 6 條啟用」。查證的五個產品裡，Grafana 就是用這招取代分頁；規則真的多到一頁放不下時，右上切「清單」檢視才出現分頁（見 B 方案）。
2 篩選：四個下拉，不做查詢語法 —— 搜尋框會搜進「規則名／表單路徑／群組名／通知欄位名」（抄 Make）。已套用的條件變成可單獨移除的標籤 —— 查證的五個產品沒有一個做這件事，卻是「為什麼只剩三筆」最常見的困惑來源。
3 不再擠壓：八欄砍成四欄 —— 來源路徑、觸發時機、欄位數全收進規則名下方的副標一行；啟用改成列內開關（不用跳頁）；操作只留「編輯 ＋ ⋯」。所有會過長的內容單行截斷並附滑過提示。

幾個刻意的決定（以及為什麼）

· 分組優先於分頁。查證的五個產品沒有一個做「每頁筆數」選擇器 —— 主流答案是用篩選和分組收斂。Grafana 的 Alert rules 就是用可收合的階層取代分頁。規則真的爆量時才切「清單」檢視吃分頁。
· 兩行式列（抄 Zapier）。來源路徑、觸發時機、欄位數都是「確認用」而非「掃視用」的資訊，收進副標就少三個欄位在搶寬度 —— 擠壓問題從根上消失，而不是靠調百分比。
· 啟用改列內開關。Zapier 的做法：0 次跳轉、0 次確認。原本「停用」是文字按鈕，跟「刪除」並排容易誤點。
· 「未登錄的群組」取代 33 碼原始 ID。ID 對人沒有意義，但「這條規則指到我們沒有紀錄的群」是要處理的狀態，用琥珀燈點＋組頭彙總標示，滑過看完整 ID。
· 欄位數可滑過看清單。「61 個欄位」現在只是個數字，看不出通知裡會出現什麼。
· 不做查詢語法。Datadog 與 Grafana 都要求學 `key:value` 或 Prometheus matcher —— 對業助這個 persona 是廢的。四個下拉 + 一個全文搜尋就夠。

§A5 對標與向上設計

· Grafana Alert rules — 對：用 folder→group→rule 可收合階層取代分頁，還能把篩選存成具名檢視。錯：label 篩選要用 Prometheus matcher（RE2、大小寫敏感），非工程背景直接卡死。
· Zapier Zaps — 對：列內 status toggle；app 用 icon 不用文字，省最多寬度。錯：搜尋只比對 Zap 名稱，找不到「用了哪張表」。
· Datadog Monitors — 對：facet 側欄與搜尋列雙向同步，新手用點的、老手用打的共用同一份狀態。錯：多選邏輯不一致（同 facet 內 OR、部分 tag 卻是 AND），UI 上看不出來。
· Make Scenarios — 對：搜尋會搜進流程內部（模組欄位值、URL）。錯：視覺化 Grid 規模一大就變麵條。
· GitHub Actions（反面）— 名稱固定欄寬硬截斷且無 tooltip，monorepo 使用者根本找不到 workflow。
我們的向上點：① 取 Grafana 的分組但拿掉查詢語法 ② 取 Make 的「搜到內部」（搜得到通知欄位名）③ 補上所有人都沒做的已套用條件標籤列 ④ 所有截斷一律配滑過提示（避開 GitHub 的坑）。
