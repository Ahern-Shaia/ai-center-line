B · 三個邊界狀態 實作不可省

功能好不好用取決於這三個，不是取決於 A 那張漂亮的清單。

B-1 · 這個群還沒有可選成員

最常見 —— 新拉進去的群

這個群目前還沒有可以 @ 的成員 系統只認得在群裡發過言的人。
請對方在群組裡發一則訊息，這裡就會出現。

不可以寫成「沒有成員」 —— 群裡明明有 20 個人。空的原因是我們只認得開過口的人， 文案要說出這件事，否則主管會以為系統壞了或那些人不在群裡。

B-2 · 已選的人可能已不在群

離職 / 退群後

王小明 （小星星） 已綁定
陳志豪 （豪） 可能已不在群
陳志豪 最後一次在這個群發言是 3 個月前，可能已經退群。 保留他不會讓通知失敗，但他不會收到 @ ——要不要移除由你決定。

措辭用「可能已不在群」：我們只知道他很久沒發言，不知道他退群了沒。 LINE 沒給我們查詢群成員名單的權限（需認證帳號），講死了就是在騙人。

B-3 · @ 不出來時，通知本身不受影響

通知紀錄頁 · 這是本模組唯一的 P0

時間規則結果 來源對象說明耗時

欄位＝既有六欄（時間 / 規則 / 結果 / 來源對象 / 說明 / 耗時，LogsTab.tsx）。 「結果」的狀態碼一個都不新增 —— @ 的成敗寫進「說明」欄， 展開列的「實際送出的訊息」本來就會原樣顯示第一行的 @。
理由：STATUS 那張表是「每種狀態要能直接讀成我現在該做什麼」的單一事實來源， 把「已送出但沒 @ 到」塞成新狀態碼，會讓「已送出」這件事有兩個代碼。

鐵則：@ 出任何問題都不得把通知本身弄丟。 第 2 列就是這個意思 —— @ 不到人只是少一個提醒，結果仍是已送出，差別只寫在說明欄。 為了 @ 不到人而整則送不出去，是把一個小遺憾換成一場事故；現在的通知是客戶每天在用的。

C · 群組裡實際看到的樣子

左為現況，右為 @ 之後。訊息主體、欄位、Ragic 連結都不變，只在最前面多一行指名。

業助群
鮮湧AI客服
【維修保養單｜已更新】 單號：TB-P71-0342 客戶：示範案場 B 狀態：待派工 預計到場：（未填） 檢視完整資料： https://ap5.ragic.com/aitode/service-tickets/10/342

現況：全群都看得到，但沒有人被指名 —— 於是每個人都覺得是別人的事。
此為 template.renderer.ts 的實際輸出格式： 【標題｜事件】 → 逐行 欄位：值 → 空行 →「檢視完整資料：」→ 原始網址。 缺值渲染成「（未填）」，沒有 emoji、沒有美化連結文字。

新版：被 @ 的兩人會收到個人推播，其餘成員看到的訊息完全一樣。 @ 獨立成第一行，長訊息捲動時第一眼就知道與自己有關。
實作上是在 renderTemplate() 的輸出前面接一行， 不動既有的渲染邏輯 —— 那支函式現在被所有規則共用。

不做 @全體（OQ-NGM-4 已裁定）：LINE 支援 mentionee.type = "all"，但一鍵吵全群、 發出去收不回來，與「LINE 群組一律不出聲」的克制取向衝突。真要吵全群，用戶自己在群裡打字更快。
@ 是每條規則各自的開關（OQ-NGM-5）：同一張單改三次就 @ 三次，兩天內對方就會把群組通知關掉 —— 那比不 @ 更糟。所以不做全域設定。
