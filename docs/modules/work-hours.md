# work-hours · 群組日誌的工時計算

> 📋 **M0 · 待裁定 OQ-WH-1..6**（2026-07-30）· 依 CLAUDE.md R6，資料模型與抽取 schema 變更需人裁定後實作。
>
> 觸發：用戶要求「在日誌計算完成的工時，計算任務的回報開始時間與回報完成時間」，
> 並指出不能只看 LINE 訊息的系統時間 —— 舉例：
> `09:59 早上6:30測試德本Chet功能有問題已發群給德本工程師` ／
> `10:00 德本回覆9:57已修正完成` → 正確工時是 **6:30–9:57**。
>
> 相關：[`task-completion-tracking.md`](task-completion-tracking.md)、
> [`personal-daily-report.md`](personal-daily-report.md)、
> backlog #39（抽取 schema 改成服務工單格式）

## 0. 一句話結論

**用戶的判斷完全正確 —— 系統時間會把 3 小時 27 分算成 1 分鐘。
但真正的障礙不是算法，是輸入裡沒有時間：118 則日誌型訊息只有 5 則（4.2%）提到時間。**

**而且「工時」與「處理時長」被混在一起了。** 我們有可靠的**終點**（他回報完成的那一刻），
但**完全沒有起點的訊號**。這兩者要分開，否則會做出一個看起來精確、實際上是錯的數字（§3）。

## 1. 現況查驗（2026-07-30 · prod 真實資料）

### 1.1 訊息裡幾乎沒有時間

| 指標 | 數字 |
|---|---|
| 群組文字訊息總數 | **652** |
| 含 `HH:MM` 形式的時間 | **19（2.9%）** |
| 含「X 點」 | 4 |
| 含時段詞（早上/下午/…） | 23 |
| **多行日誌型訊息（≥4 行）** | **118** |
| **其中含時間的** | **5（4.2%）** |

### 1.2 ⚠️ 那 19 則含時間的訊息，多數不是工時

逐則看過，只有 3–4 則是「工作起訖」，其餘是**完全不同性質**的時間：

| 實際訊息 | 是什麼 | 若當工時算的後果 |
|---|---|---|
| `預計7/28(二) 15:30~17:30請假` | 請假 | **把請假算成 2 小時工時** |
| `明天早上9:30去商協` | 未來行程 | 起點取到未來時間 |
| `開發組例行週會09:30` | 會議 | — |
| `7/23 15:35 彰化 員榮醫院 賴小姐…詢問側踏報價` | 客戶來電時間 | 誤當成開始工作 |
| `今日會加班，雲端人資當機，冠毅+韋志到20:00` | 加班預告 | — |
| `可慧寄信 預計5:10回` | 預計返回 | — |
| `大約15:00請來找我` | 約定時間 | — |
| `13:55 開始確認101～104工單的所有欄位` | ✅ 起 | 正確 |
| `14:07 檢查完畢，無缺漏欄位` | ✅ 訖 | 正確 |
| `7月24號早上9:20到9:30跟Patrick 討論客服機器人` | ✅ 同句起訖 | 正確 |

> **把請假算成工時**是最貴的那一種錯 —— 不是不準，是**方向錯**，
> 而且它會出現在主管看的日誌上。

### 1.3 ⭐ 真實日報長這樣（沒有時間）


**日期 ＋ 姓名 ＋ 一串活動條目。沒有時間、沒有時長、沒有機台、沒有工單。**
這就是為什麼現行 schema 抽不出東西。

### 1.4 現有的 `work_hours` 欄位填出率是 0%

`work_hours` 早就存在於抽取 schema（`src/schemas.ts:33`）。實際產出：

| 指標 | 30 天內 |
|---|---|
| 分析批次 | 51 |
| **抽出的日報筆數** | **9** |
| **其中 `work_hours` 有值** | **0** |

那 9 筆的 `machine_code` 全空、`work_order` 幾乎全空 ——

> 這正是 backlog **#39**。**工時要算，得先有一個載得住它的日報。**

### 1.5 ⚠️「報工生產」群根本不在報工

唯一按名字該有工時的群，8 天只有 **19 則訊息、0 則含時間**。
而內容是在**討論 Ragic 的 QRQC 表單設計**：

> `測試時，提出人反應問題後要存檔，沒辦法，因處理工時為必填，這個階段提出人並不會寫，所以需要調整`
> `好，我再把處理工時的必填拿掉`

**三件事因此成立：**

1. **客戶的 Ragic 裡已經有「處理工時」欄位**，而且有「處理的時間 / 結案時間」的概念。
2. 客戶**已經撞上同一個問題** —— 提出人在提出的那一刻不知道工時，所以他們把必填拿掉了。
3. 另外在技術工程群（07-28 18:39）：

   —— **另有一套「工時工序申請」流程存在**，工時不是只在 LINE 裡。

## 2. ⭐ 核心裁定：我們有終點，沒有起點

工時 ＝ 結束 − 開始。逐一檢查這兩端我們實際有什麼：

| | 有沒有可靠訊號 | 說明 |
|---|---|---|
| **結束** | ✅ **有** | 他回報完成的那一刻。今天（07-29）剛把私訊回報做完，`work_closed_at` 是確定的 |
| **開始** | ❌ **完全沒有** | 「開始做這件事」在系統裡不存在任何事件 |

「開始」的四個候選，逐一為什麼不行：

| 候選 | 問題 |
|---|---|
| 任務建立時間（materialize） | 那是**當天 18:00 批次**跑的時間，跟開始工作無關。會算出離譜的數字 |
| 來源訊息時間（有人在群裡提出） | 這是「**被交辦**的時間」，不是「開始做」的時間 —— 但它有另一種價值（§3.2）|
| 文字裡明講的時間 | **4.2% 覆蓋率**，且需先排除請假／會議／約定（§1.2）|
| 問他 | 多一次互動 · 而客戶已經證明「提出時不知道工時」（§1.5）|

## 3. ⭐⭐ 提案：把兩個不同的東西拆開

### 3.1 它們不是同一件事

| | 定義 | 能不能自動算 | 覆蓋率 |
|---|---|---|---|
| **處理時長**（cycle time） | 從被提出 → 到回報完成，經過多久 | ✅ **可以** | **100%**（兩端都有系統時間）|
| **投入工時**（effort） | 那個人實際花了幾小時在做 | ❌ **不行** | — |

**用戶的例子正好說明差別**：`6:30 發現問題 → 9:57 修正完成` ＝ **處理時長 3 小時 27 分**。
它**不代表**德本工程師投入了 3.5 小時 —— 他中間很可能在做別的事。

> ⚠️ **混在一起的代價**：日誌上出現「工時 3.5h」，主管拿它去算人力成本或考核，
> 而那個數字從來不是工時。**一個看起來精確的錯誤數字，比沒有數字貴。**

### 3.2 建議做「處理時長」，不要自動產「工時」

```
處理時長 = work_closed_at（回報完成） − 來源訊息的 sent_at（事情被提出）
```

兩端都是系統時間，**100% 算得出來、不需要抽取、不會誤判**。
而它回答的是主管真正會問的問題：**「這件事拖了多久？」**

用戶例子在這個定義下：`6:30 → 9:57` 若兩則訊息都能對到同一張任務，處理時長就是 3h27m ——
**跟用戶要的數字一樣**，但語意誠實。

### 3.3 「投入工時」怎麼辦

**不要猜，讓人給。** 而且要在他**知道答案的那一刻**問 —— 也就是**回報完成的時候**，
不是提出的時候（客戶已經證明提出時不知道，所以把必填拿掉了）。

今天剛上線的私訊回報流程正好是那個時刻：

```
他：好了
系統：✓ 已收到完成回報
      三號機軸承要換
      這件花了多久？ [ 半小時內 ] [ 1-2 小時 ] [ 半天 ] [ 稍後再填 ]
```

一個 tap、零個判斷，而且問在他記得的時候。**沒填就是沒有** —— 不要用處理時長去頂替。

### 3.4 文字裡明講的時間：只收「同句起訖」

`7月24號早上9:20到9:30跟Patrick討論` 這種**起訖在同一句**的，
不需要跨訊息配對、語意也最清楚，是唯一值得抽的形狀。

**明確不做**（§1.2 的證據）：
- 單一時間點（`明天9:30去商協`）→ 無法判斷是起還是訖，且多為未來行程
- 跨訊息配對（用戶的例子）→ 需要靠「德本」這種共同詞連結兩則訊息，
  而今天的完成訊號實測顯示跨訊息對應準確率不足

## 4. 前置條件：#39 沒做，這件事沒有載體

§1.4 的數字：30 天 51 個批次 → 9 筆日報 → 0 筆有工時。

**現行 schema 對不上業務型態**（生產線 vs 特種車輛改裝／長照）。
在它上面加時間欄位，等於在一個每月只產出 9 筆、關鍵欄位全空的管線上再加一個空欄位。

> **建議：#39 是本模組的 M1 前置。** 日報要先能抽出「這個人今天做了哪幾件事」
> （像 §1.3 那個樣本那樣的活動條目），才有東西可以掛時長。

## 5. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **W-1** | 抽取 | 把請假／會議／約定的時間當成工時起訖 | **請假變成 2 小時工時**，進到主管看的日誌 | **P0** | §3.4 只收同句起訖 · 抽到的時間必須先分類，分不出來就不算 |
| **W-2** | 語意 | 「處理時長」被當成「投入工時」用於成本或考核 | 一個看起來精確的錯誤數字 | **P0** | §3.1 兩個欄位分開命名、UI 上分開顯示 · 絕不把處理時長寫進 `work_hours` |
| **W-3** | 起點 | 用任務建立時間（18:00 批次）當開始 | 所有時長都錯，而且錯得看不出來（都是幾小時） | **P0** | 起點只能用來源訊息的 `sent_at` · 程式碼註解寫明不可用 `created_at` |
| **W-4** | 配對 | 跨訊息配對錯，把 A 的完成時間掛到 B 的任務 | 兩張任務的時長都錯 | P1 | 本輪不做跨訊息配對（§3.4）|
| **W-5** | 時區 | 文字裡的「6:30」沒有日期，跨日時算成負數或 +24h | 出現負時長或 27 小時 | P1 | 只在同一天的訊息內解讀 · 算出負值一律丟棄不顯示 |
| **W-6** | 隔夜 | 提出在昨天、回報在今天 → 處理時長含整個夜晚 | 「這件事花了 18 小時」技術上對、實務上誤導 | P1 | 顯示為「跨日 · 約 N 小時」而不是純數字 · 或只算工作時段（需 OQ-WH-5）|
| **W-7** | 空值 | 大多數任務沒有工時 → 欄位一片空白 | 看起來像功能壞了 | P2 | 空值顯示「—」並說明「工時由當事人回報時填寫」，不要顯示 0 |

## 6. 開放問題（OQ-WH-N）

| # | 問題 | 建議 |
|---|---|---|
| **OQ-WH-1** | 「處理時長」與「投入工時」要分成兩個欄位嗎？ | **要**（§3.1）· 合併是 W-2 那個 P0 的來源 |
| **OQ-WH-2** | 自動算的那個要叫什麼？ | 建議「**處理時長**」或「**經過時間**」· **不要叫工時** |
| **OQ-WH-3** | 投入工時用「回報完成時問一次」的方式收嗎？ | **建議是**（§3.3）· 問在他知道答案的時刻 · 選項式一個 tap |
| **OQ-WH-4** | 要不要抽「同句起訖」的時間？ | **要**，但列為 M3（覆蓋率低、價值有限，先做 100% 覆蓋的那個）|
| **OQ-WH-5** | 隔夜的處理時長要扣掉非工作時段嗎？ | **需要你的業務判斷** —— 扣的話要定義工作時段（含週末？加班？），不扣的話會出現「18 小時」 |
| **OQ-WH-6** | Ragic 那邊已有「處理工時」與「結案時間」（§1.5），要不要以它為主來源？ | **需要你的業務判斷** —— 若 QRQC 表單才是正式紀錄，那我們該做的是**把時長回寫進 Ragic**，而不是在日誌另算一份 |

> **OQ-WH-6 可能是最重要的一題。** 客戶已經有一套工時流程（Ragic QRQC ＋ 工時工序申請），
> 我們如果另建一份，會變成兩個數字互相矛盾。
