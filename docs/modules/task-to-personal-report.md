## 0. 觸發與現況查驗

用戶提出三條需求，2026-07-27 逐條對照程式碼查驗：

| # | 需求 | 現況 | 證據 |
|---|---|---|---|
| ① | 群組 → 工作日誌 → 任務 | ✅ **已實作** | `line_message` → group_batch → `analysis_result.records` → `TicketMaterializerService` → `tickets` |
| ② | 私訊 → 個人日報 → 本人確認 | ✅ **已實作** | 私訊（`chat_context='personal'`）→ 17:30 `pdr` 排程 → `personal_daily_report` → `POST /mine/save`（本人才能存） |
| ③ | 任務 → 個人日報（自動歸屬當責人並同步匯入） | ❌ **未實作** | 見下 |

### 0.1 ③ 為什麼算「未實作」

**「自動歸屬當責人」只做了一半**：`tickets.assignee_display_name` 有值，但它**只是 AI 從對話抽出的一段文字**。schema 註解自己寫得很清楚：

```sql
COMMENT ON COLUMN tickets.assignee_display_name IS
  '從對話抽的「派給誰」· 為顯示用文字 · 未來可 JOIN line_member.display_name 對到 user';
```

沒有 `assignee_user_id`。**系統知道對話裡出現了「阿明」，但不知道阿明是誰。**

**「同步匯入日報」完全沒有**：個人日報的資料來源只有一條，且只吃本人的私訊：

```sql
FROM line_message
WHERE sender_user_id = ${userId} AND chat_context = 'personal'
```

`personal-daily-report/` 全目錄 grep `ticket` → **0 筆**。兩個模組之間沒有任何連結。

## 1. 問題拆解 —— 這是三個獨立問題，難度差很多

| # | 問題 | 難度 | 風險 |
|---|---|---|---|
| **P1** | **身分解析**：人名文字 → `user_id` | **高** | **對錯人＝把 A 的工作寫進 B 的日報** |
| **P2** | 資料匯流：個人日報要吃第二種來源 | 中 | 覆蓋本人已編輯的內容 |
| **P3** | 時序：任務比日報晚出現 | 中 | 已確認的日報被偷改 |

**P1 是真正的難題**，P2/P3 是工程問題。把三者當成「接個線」會出事。

---

## 2. 核心原則：寧可不歸屬，不可歸錯人

把 A 的任務塞進 B 的日報，同時造成三件事：

1. **資料錯誤** —— B 的日報出現他沒做過的事
2. **隱私外洩** —— B 看到 A 的工作內容（客戶名、金額、異常）
3. **信任崩塌** —— 一旦發生一次，使用者會開始懷疑**所有**自動歸屬的內容

而「沒有自動歸屬」的代價只是：**維持現狀**，本人自己私訊回報。

**代價完全不對稱 → 判準是：不確定就不歸屬，並且要讓人看得到「有一筆待認領」。**

## 3. P1 · 身分解析

### 3.1 身分鏈是通的（已有基礎建設）

```
AI 抽出的 person 文字（「阿明」）
        ↓  ← 這一段是缺的
line_member.display_name   （該群成員的 LINE 顯示名）
        ↓  line_member.user_id (Uxxx)
user_line_binding.line_user_id  （status='active'）
        ↓
user_line_binding.user_id  →  users（系統帳號）
```

後三段都已存在（[`employee-line-binding`](employee-line-binding.md) 已 SHIPPED）。**只缺第一段。**

### 3.2 ⭐ 設計主張：在抽取階段 grounding，不要事後模糊比對

多數人的直覺是「先抽出人名，之後再做模糊比對」。**這是錯的方向**：

| 事後模糊比對 | 抽取階段 grounding |
|---|---|
| 候選集是「全公司的人」 | 候選集是**這個群當天有講話的成員**（通常 3–10 人） |
| 要處理「阿明／明哥／李明」的別名問題 | LLM 看得到實際名單，直接輸出名單中的值 |
| 比對邏輯自己寫，錯了難以調整 | 對不到就輸出 `null`，是模型能力範圍內的事 |
| 與 CLAUDE.md 既有做法不一致 | **與主檔 grounding（R11）一致** —— 本專案本來就這樣做 |

**做法**：分析該群當日對話時，把 `line_member` 的成員名單（限該群、限已綁定者）放進 prompt，要求 `person` 欄位**只能輸出名單中的顯示名，或 `null`**。

> 承 CLAUDE.md R11：「缺漏欄位填 null，禁止讓模型臆測」。人名尤其不可臆測。

### 3.3 歸屬信心度（三態，不是二元）

| 狀態 | 條件 | 行為 |
|---|---|---|
| **已歸屬** | person 精確命中名單中**唯一**成員，且該成員已綁定 | 寫入 `assignee_user_id`，可匯入其日報 |
| **待認領** | person 有值但對不到（未綁定／同名多人／不在名單） | **不歸屬**，任務看板顯「待認領」，可由主管指派或本人認領 |
| **無指派** | person 為 null | 維持現狀，不做任何事 |

**「待認領」是這個設計的關鍵**——沒有它，系統只能在「猜」和「丟掉」之間二選一，兩個都不對。

### 3.4 同名怎麼辦

同一群裡兩個「小明」→ **一律進「待認領」**，不用任何啟發式規則（誰講話多、誰先加入…）猜測。
猜對沒有獎勵，猜錯要付上面三種代價。

## 4. P2 · 匯流進個人日報

### 4.1 資料模型

個人日報的 item 目前是自由 jsonb（`ai_items` / `final_items`）。加一個來源標記即可，**不新增表**：

```jsonc
{ "title": "...", "detail": "...", "time": "...", "followup": "...",
  "source": "personal_dm" | "assigned_task",     // 新增
  "ticketId": "uuid"                             // 僅 assigned_task 有
}
```

### 4.2 三條紀律

1. **不覆蓋本人編輯過的內容**。`final_items` 一旦存在就是本人的版本，任務只能**追加**，不能改動既有項目。
2. **已確認（`status='confirmed'`）的日報不自動塞東西**。承 2026-07-27 裁定「AI 是輔助，不自動重跑」——新任務走 §5 的待整理區。
3. **來源要看得見**。匯入的項目在 UI 標「來自任務看板」並可點回原任務。使用者要能分辨「我自己講的」與「系統給我的」。

## 5. P3 · 時序

**問題**：日報 17:30 生成，群組分析 08:00 跑（或當日手動觸發），任務可能在日報之後才出現。

**建議**：沿用 2026-07-27 已上線的「**尚未整理進日報**」pattern —— 不重新生成、不偷改，而是在日報頁顯示：

```
有 2 項指派給你的任務尚未加入日報
  · 客戶 A 側踏改裝圖面待確認    [加入日報]
  · 3 號機軸承叫料              [加入日報]
```

**由本人決定要不要納入。** 這同時解掉「已確認日報被偷改」與「歸屬錯了本人可以不收」兩個問題——**本人是最後一道防線**。

## 6. 權限與隱私

| 誰 | 看得到什麼 |
|---|---|
| 本人 | 自己日報中的任務項目（含來源連結） |
| 主管 | **任務看板**上的任務（原本就看得到）；**看不到**別人的日報 |
| 未歸屬的任務 | 只在任務看板，不進任何人的日報 |

**不新增權限**：日報走本人 `user_id`，任務走既有 tickets RLS（部門範圍）。兩邊都已有正確的範圍控制。

> ⚠️ 一個必須擋的洩漏路徑：任務可能來自**本人不在的群組**。
>
> **v1（2026-07 上旬）**：日報一律只帶 `summary`、不帶原始對話（怕跨群洩漏）。
>
> **v2 修訂（2026-07-31 · 部門制 gate）**：改成「**任務屬本人部門才給原始對話**，跨部門仍擋」。
> 判準沿用系統既有的隱私邊界（tickets RLS 本來就按部門），而非另立一套。
> 落地：`GET /personal-daily-report/assigned-tasks/:ticketId/source`，app 層三道明驗
> （讀不到 ticket→404、assignee≠本人→403、ticket 部門≠本人部門→403），通過才回原文；
> 列表每筆帶 `canSeeSource`（部門相符）決定前端顯不顯示「對照原始訊息」。
> 未分配部門者一律不給（安全預設）。P0 測試：`test/personal-report-assigned-source.test.ts`。

## 8-bis. 落地實況（2026-07-27）

### ⭐ 用戶裁定改變了設計重心

> 「還在和廠商談合作、還沒正式導入。頂多就是變**待認領**，主管、總經理還能人工派發，
> 等員工 LINE 綁定了自然就會自動派發。**手動派發只是在 AI「可能」會認錯的情況下做的確認機制。**」

原本文件把「大量待認領」視為風險（FMEA F-10）。用戶指出這是**導入期的正常主流程**——
手動派發本來就是必要的確認機制，不是自動歸屬失敗時的退路。

**設計重心因此反轉：手動派發是主要介面，自動歸屬是之後長出來的加速器。**

### 一個比預期更好的事實

**手動派發今天就能用，不必等任何人綁定 LINE。**

「我的日報」是網頁、走 email 登入 —— 只要有系統帳號（台灣福祉已有 9 個）就看得到指派給他的任務。
**綁定只影響「AI 能不能自動對到人」，不影響「派了之後看不看得到」。**

1. **重跑不可蓋掉手動結果**：材料化 UPSERT 加 `CASE WHEN tickets.assigned_by IS NULL` —— 人的決定優先於 AI。沒有這條，主管派好的東西會被下次分析洗掉。

| ② | **綁定率 10%**（42 人出現在群裡，僅 4 人綁 LINE） | 導入進度 | 不是程式問題 |

沒有候選集，AI 抽出來的是自由文字：
「郁芬Sandra」「佳慧/小星星/威廉/三爪」「許佳惠/SHIN 新」——
這種字串連「對得上名單」的機會都被削掉了。

> ⚠️ **但要公平講**：即使 grounding 做到完美，能自動對上的上限也只有已綁定的那 4 個人。
> 這正是本文 §2 當初的判斷——**待認領是導入期的正常主流程，不是失敗**。
> 手動派發的路徑是通的，功能可用。

### 8.6 缺一個量測

現在**沒有任何地方看得到自動歸屬率**。
grounding 接上之後，我們不會知道有沒有變好。
→ 建議併入 `extraction-health` 那頁（同 tenant-prompt-decoupling OQ-TPD-8 的理由：
沒有量測就等於沒有 grounding）。
