# task-materialization-gate · 什麼才該變成任務

> 狀態：🚧 **M0 DRAFT v0.1**（2026-07-28）· 待用戶裁定 OQ-TMG-1..9
>
> 相關：[`warroom-task-board.md`](warroom-task-board.md)（任務看板本體）、[`ai-analysis-layering.md`](ai-analysis-layering.md)（L1 抽取欄位）、[`task-to-personal-report.md`](task-to-personal-report.md)（任務→當責人）
>
> ⚠️ **本文的兩個數字**：現在任務看板上 **15 張有 6 張（40%）不是待辦事項**；
> 而 AI 抽出來的 **58 筆中信心記錄，沒有任何人看過**。
> 這是同一個問題的兩面：**門檻只問「抽得準不準」，沒問「該不該追」。**

## 0. 觸發與現況查驗

用戶問：「目前信心值怎麼設定？如果介於多少信心值，有沒有必要設計成讓群組負責人或總經理可以被詢問，要不要將日誌中某事件變成任務？」

查 prod（台灣福祉，2026-07-22 ～ 07-27，6 天）後發現，這個直覺是對的，但**還有一個更該先修的問題**。

### 0.1 信心值是什麼

不是分數，是模型自評的三級。定義寫在 system prompt（`tenant-twh.ts`）：

> confidence：欄位完整明確 = high；有推斷成分 = medium；訊息模糊 = low

**沒有可調的數值門檻**，也沒有「幾分以上通過」的設定。

材料化的唯一條件是一行（`ticket-materializer.service.ts:88`）：

```ts
if (rec.confidence !== "high") { skipped++; continue; }
```

### 0.2 prod 實測

| 信心 | 筆數 | 目前下場 |
|---|---|---|
| high | 20 | 進任務看板 |
| **medium** | **58（64%）** | **只留日誌，沒有任何出口** |
| low | 13 | 只留日誌 |

**現有 15 張任務卡，按來源記錄的 status 拆開：**

| 來源狀態 | 張數 | 實際內容 |
|---|---|---|
| in_progress | 5 | 詢價、請購、技轉支援 ✅ 是待辦 |
| open | 4 | 領料需求、治具協調 ✅ 是待辦 |
| **info** | **4** | 「工作回覆規則」「開會通知」「提醒：採購須對…」❌ **是公告** |
| **resolved** | **2** | 「線路接觸不良查修**完**」「滅火器貼紙議題**結案**」❌ **已經做完了** |

**6 張（40%）不是待辦事項，卻掛在「待簽核」等主管處理。**

> ⚠️ 這 6 張**AI 沒有抽錯**。「開會通知」確實是開會通知，抽得很準，所以是 high。
> 問題出在我們拿「抽得準不準」當「該不該追」用——這是兩個問題。

**而 58 筆中信心裡，抽樣看到的是：**
客訴：保固中車輛收費爭議（處理中）／ JS日盛後保桿支架料件問題（處理中）／
台中標案交接與報價單作業（處理中）／ BOM 建置編碼不同的處理方式（處理中）

**這些是真的該追的事，現在沒有任何人會看到。**

### 0.3 一個已經存在但沒被用的欄位

`tickets.status` 欄位在 `0001_init.sql` 就有了，**materializer 從來沒寫過它**——
prod 15 張任務，`status` 有值的是 **0 張**。

記錄的 status（open / in_progress / resolved / info）在材料化那一步就被丟掉了。
這也是為什麼看板上分不出「待辦」跟「公告」。

## 1. 兩個獨立問題，不要混在一起做

| | 問題 | 症狀 | 難度 |
|---|---|---|---|
| **甲** | 門檻只看信心，不看是不是待辦 | 看板 40% 是公告與已完成的事 | **低** |
| **乙** | 中信心沒有出口 | 64% 的抽取成果沒人看得到 | 中 |

**建議先做甲。** 理由：
- 甲是**減法**，做完看板立刻乾淨一半，不新增任何使用者負擔
- 乙是**加法**，會把更多東西推到主管面前——在看板還有 40% 雜訊時做加法，等於把雜訊放大
- 甲做完才知道「乾淨的看板」長什麼樣，乙的量體才好評估

---

## 2. 甲 · 加一層「是不是待辦」的判斷

### 2.1 主張：不要「擋掉」，要「換一區放」

最直覺的做法是 `if (status === 'info') continue;`——**但這是錯的**。

如果 AI 把一件真的待辦標成 `info`，那件事會**無聲消失**，而且沒有人會發現。
本專案已經反覆吃過同一個虧：失敗跟成功長得一模一樣。

所以主張是：**所有高信心記錄都還是建卡，但分流到不同的區**。

| 來源 status | 進哪 | 要不要簽核 |
|---|---|---|
| `open` / `in_progress` | **待辦**（現在的看板） | 要 |
| `info` | **僅供參考** | 不要 |
| `resolved` | **已完成**（存查） | 不要 |

「僅供參考」與「已完成」預設收合，但**點得開、可以手動改成待辦**。
沒有東西消失，只是不再擠在待簽核佇列裡。

### 2.2 落地

1. materializer 補寫 `tickets.status`（欄位已存在，不用 migration）
2. 依 status 決定初始 `confirm_status`
3. 看板依 status 分區

---

## 3. 乙 · 中信心的出口

### 3.1 量體（決定它會不會變成負擔）

若只收「中信心 **且** 狀態是 open / in_progress」：

| 日期 | 要看幾筆 |
|---|---|
| 07-27 | 21 |
| 07-24 | 6 |
| 07-23 | 3 |
| 07-22 | 4 |
| 07-26 | 1 |

**平均 7 筆／天，尖峰 21 筆。** 分散到各部門後，主管掃得完。
（中信心 58 筆中，`info` 15、`resolved` 8，這 23 筆依 §2.1 同樣不進待確認。）

### 3.2 主張：做成看板上的一區，不要做成推播

**不要**用 LINE 推播問「這件要不要變任務？」——
一天 7 則、尖峰 21 則的打擾，兩天就會被關掉。

改成任務看板加一欄「**待確認**」，主管進去掃，每張兩個選擇：
**收為任務** / **不用追**。

### 3.3 決定必須記得住（否則重跑就前功盡棄）

群組會重新分析（手動重跑、排程補跑）。
如果「不用追」的東西下次分析又冒出來，主管第二次就不會再點了。

**建議做法：中信心也寫進 `tickets`，但 `confirm_status` 用新值 `待確認`。**

為什麼不開新表：materializer 現有的冪等鍵
`(source_upload_id, source_record_index)` 已經能唯一標定一筆記錄，
重跑走 `ON CONFLICT DO UPDATE`。沿用等於白拿冪等性，
另開一張表要把這套再寫一遍，而且兩邊會漂移。

「不用追」→ `confirm_status = '已忽略'`，重跑時比照 `assigned_by` 的做法**不覆寫人的決定**。

## 4. ⚠️ 會連帶打壞的東西（動手前必讀）

**中信心票一旦進 `tickets` 表，總覽儀表會立刻壞掉。**

`warroom.service.ts:60`：

```ts
const signed = dt.length > 0 && dt.every((t) => t.confirmStatus === "已簽核");
```

部門要「所有票都已簽核」才算簽核完成。中信心票是 `待確認`、永遠不會變 `已簽核`
→ **每個部門的 signed 永遠是 false → 簽核率直接掉到 0%**。

同一段還有：

```ts
const hasLow = dt.some((t) => t.confidence === "low" && t.confirmStatus === "待簽核");
const health = overdue || !active ? "red" : hasLow ? "yellow" : "green";
```

`hasLow` 目前是**死碼**（只有 high 會進來，low 永遠不存在）。
一旦放寬信心門檻，這行會突然活過來並開始把部門判成黃燈。

**所以這不是「加一個 status 就好」的改動。** 必須一併 sweep：

| 位置 | 要改什麼 |
|---|---|
| `warroom.service.ts` 簽核率 | 只算「待辦」類的票，`待確認`／`僅供參考`／`已完成` 不進分母 |
| `warroom.service.ts` 健康度 | 決定 `hasLow` 要復活還是刪掉 |
| `warroom-tasks.service.ts` 看板查詢 | 分區、預設只顯示待辦 |
| 個人日報 | 待確認的票**不可**匯入個人日報（還沒確認是不是任務） |
| 抽取健康度儀表 | 分母定義若含 tickets 需同步 |

> 這條就是 `rule_outer_shell_sweep` 的典型案例：改的是材料化那一行，
> 但受影響的是儀表、看板、日報三個外層。

## 5. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **F-1** | status 分流 | AI 把真待辦標成 `info` → 事情無聲消失 | **漏事** | **P0** | 不刪只分區（§2.1）· 「僅供參考」點得開、可手動改回待辦 |
| **F-2** | 儀表 | 中信心票進表 → 簽核率永遠 0%、健康度全紅 | **主指標失真** | **P0** | §4 sweep · 指標只算待辦類 · 上線前用 prod 快照對算 |
| **F-3** | 忽略決定 | 重跑後「不用追」的又冒出來 | 主管失去信任、不再使用 | **P1** | 決定寫 `tickets` 並在 UPSERT 保護（比照 `assigned_by`）|
| **F-4** | 負擔 | 待確認每天累積無人清 → 變成第二個沒人看的清單 | 功能空轉 | **P1** | 顯示積壓筆數 · 超過 N 天未處理提示 · 先觀察一週再決定要不要提醒 |
| **F-5** | 誤用 | 主管把待確認當待辦，一次全收 | 任務品質下降到跟沒門檻一樣 | **P1** | **不做「全部收為任務」按鈕**（多一個批次鈕就等於預設全收） |
| **F-6** | 日報 | 待確認的票被算進當責人日報 | 同仁看到還沒確認的事 | **P1** | 日報只吃待辦類（§4） |
| **F-7** | 期待 | 客戶問「那則怎麼從看板不見了」 | 誤以為資料掉了 | P2 | 分區可展開 · 今日日誌仍完整保留 |
| **F-8** | 既有資料 | 現有 15 張票沒有 status，改版後全部落到未知分類 | 看板暫時錯亂 | P2 | 回填 SQL：依 source record 補寫 status（**由人執行 · R10**）|

## 6. 開放問題（OQ-TMG-N）

| # | 問題 | 建議 |
|---|---|---|
| **OQ-TMG-1** | 先做甲（門檻）還是乙（待確認）？ | **先甲** · 減法先做，否則等於放大雜訊（§1） |
| **OQ-TMG-2** | `info` / `resolved` 要不要建卡？ | **要建，但分區** · 不刪不擋（§2.1 · F-1） |
| **OQ-TMG-3** | `resolved` 要不要簽核？ | **不用** · 事情做完了，簽核沒有意義；放「已完成」存查 |
| **OQ-TMG-4** | 中信心的決定存哪？ | **存 `tickets`，`confirm_status='待確認'`** · 沿用現成冪等鍵（§3.3） |
| **OQ-TMG-5** | 待確認放哪個畫面？ | **任務看板加一欄** · 主管動線已經在那 |
| **OQ-TMG-6** | 要不要推播提醒？ | **不要** · 一天 7 則、尖峰 21 則會被關掉（§3.2） |
| **OQ-TMG-7** | 誰能確認？ | 與簽核同權（群組負責人＋總經理室） · 待裁定 |
| **OQ-TMG-8** | 低信心要不要也給出口？ | **不要** · 13 筆／6 天，訊息本身就模糊，成本高於價值 |
| **OQ-TMG-9** | 簽核率分母怎麼改？ | 只算待辦類 · **但這會讓歷史數字不可比**，需決定要不要標記改版日 |

## 7. 里程碑

| 里程碑 | 內容 |
|---|---|
| **M0** | 本文件 + OQ 裁定 ← 目前在這 |
| **M1** | 甲 · materializer 補寫 `tickets.status` + 依 status 分流 + 看板分區 |
| **M2** | 甲 · 回填 SQL（現有 15 張補 status）+ 儀表 sweep（§4）+ 用 prod 快照對算指標 |
| **M3** | 乙 · `confirm_status` 加 `待確認`／`已忽略`（migration）+ 中信心材料化 + UPSERT 保護 |
| **M4** | 乙 · 看板「待確認」欄 + 收為任務／不用追 |
| **M5** | FMEA 覆核（2 個 P0）+ 觀察一週積壓量 + docs 收尾 |

> **M2 是 gate**：儀表指標沒有對算過就不要進 M3。
> 簽核率是給總經理看的主指標，掉到 0% 會比看板有雜訊嚴重得多。
