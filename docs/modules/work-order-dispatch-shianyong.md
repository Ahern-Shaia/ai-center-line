## 3. 今天就能交的（M0.5 · 零程式）

明天驗收只需要「按鈕會開出一張報工單」，這**不需要寫任何程式**：

2. 選 6 區塊版型，框好六格
3. **第 4 格**動作選「連結」，貼一張真實報工單的網址：

4. 第 1–3 格貼既有 LIFF 網址（格式見 [`../sop/richmenu-attendance-setup.md`](../sop/richmenu-attendance-setup.md) B3，`botId` 用鮮湧那支）

### ⚠️ 驗收前一定要做的一件事

**用驗收者本人的手機點一次，不要用自己已登入的手機測。**
Ragic 連結在 LINE 內建瀏覽器開啟時，若沒有登入 session，出現的是 **Ragic 登入頁**而不是報工單。
你的手機已登入所以會正常，客戶的不會 —— 這是明天最可能當場翻車的點。

## 4. 兩條路線

差別只在「**那份『我的待辦清單』由誰生**」。

| | **A · 我方做 LIFF 清單頁** | **B · 直接用 Ragic 的個人視圖** |
|---|---|---|
| 按鈕指到 | 我方 LIFF（新增 `?page=work`）| Ragic 的一個篩選視圖網址 |
| 清單怎麼來 | 我方後端打 Ragic API `where=員工,eq,X` ＋ 狀態=未完成 | Ragic 依登入者自己篩 |
| 身分怎麼解 | LINE userId → `user_line_binding` → 我方 `users` → **Ragic 的員工值**（三段都要對得上）| 不用解，Ragic 認得登入的人 |
| 前置條件 | 員工全部綁定 LINE | 員工有 Ragic 帳號 |
| 我方工時 | 高 | 幾乎零 |
| 主要風險 | 對不到人 → **空白清單，而且長得跟「你今天沒被派工」一模一樣** | 受制於 Ragic 篩選能力（見下）|

### 4.1 建議：先做 B，A 當第二階段

理由不是 B 比較優雅，是 **A 的前提現在不成立**：鮮湧的 LINE 綁定數大概是 0（§2），
第一天打開會是所有人都看到空清單。而空清單與「今天沒被派工」**在畫面上無法區分** ——
這是 [[pitfall_green_because_empty]] 的同一個形狀，也是本模組最糟的失效（§10 F-1）。

而且步驟 f 已經要求員工登入 Ragic 了。既然如此，**先讓 Ragic 做它本來就會做的事**，
等綁定率起來、或客戶明確要更好的 UI，再用 A 取代。

### 4.2 B 的未查證點（不可跳過）

**Ragic 的固定篩選能不能用「目前登入者」當條件**（寫得出「負責人 = 我」這種動態條件嗎）
—— **我沒有查證，不憑印象寫**。若不行，B 就退化成「每個員工各自一個篩選網址」，
那會變成要維護 N 條網址、而且圖文選單是**全租戶共用一張**、貼不了個人化網址 → B 直接不成立，只能走 A。

> **這是 B 成立與否的單一判準，M1 第一件事就是驗它。**（OQ-WOD-2）

### 4.3 第三個選項：不做清單，改成派工當下推播

主管在 Ragic 派工 → 我方發 LINE **私訊**給該員工，一單一則、帶 Ragic 連結。

- 符合既有界線：「**有人對他做了決定**」可以主動推（[`task-assign-notify.md`](task-assign-notify.md)）
- 零件全都在：notification-hub 的 `line_user` 管道 + Ragic webhook 早就在跑
- 但**一樣要解身分**（要知道推給誰），所以它不是 A 的替代，是 A 的**前半段**
- 缺點：一天多單會洗版；沒有「還剩幾張」的總覽（步驟 c 要的正是總覽）

**不與 A/B 互斥**，建議當作 v2 的加值，不進 v1。

## 5. 若走 A · 技術設計（暫記 · 等 Q1 答案才展開）

### 5.1 身分鏈

```
LINE userId ──(user_line_binding)──> 我方 users ──(???)──> Ragic 派工單的「員工」欄位值
                     ↑ 已有                        ↑ 這一段不存在
```

第三段是新問題：Ragic 那格填的是**人名字串、員工編號、還是 Ragic 帳號**？
- 若是**員工編號**：`users` 加一欄 `external_employee_id`（中性欄名，見 AGENTS.md 通訊通道中立）→ 可靠
- 若是**人名字串**：⚠️ **不做模糊比對**（[[project_onboarding_requires_line_binding]] A-2 P0：指派給錯的人）
  → 要嘛請客戶把那格改成選單，要嘛在我方維護一張對照表，由人確認

### 5.2 查詢

```
GET /{apname}/{path}/{sheetIndex}?api&naming=EID
    &where=<員工欄位>,<op>,<值>
    &where=<狀態欄位>,eq,<未完成>
```

⚠️ **`naming=EID` 不可省** —— 不加的話 key 會是「欄位名稱」而不是 ID，取值全空且不報錯
（[[pitfall_ragic_api_naming_eid]]）。

⚠️ **「一張派工單多位員工」會決定 `where` 寫不寫得出來**：
若「員工」是**多選欄位**，`eq` 是比不到的（值是多個），要用 `like`／`contains` 之類的運算子；
若是**子表格**，主表的 `where` 可能根本篩不到子表欄位 → 得改成撈回來自己過濾（效能與正確性都變差）。
**這是 Q2 要問的原因。**

### 5.3 UI

沿用既有 LIFF 版式（`web/src/liff/`），新增 `?page=work`：
一行一張單（單號／案場／派工日／狀態），點一下開 Ragic。
**空清單必須分兩種文案**：「今天沒有派給你的單」vs「**認不出你是誰**（尚未綁定）」——
這兩句話對應完全不同的行動，混在一起就是 F-1。

## 6. 企業級 cross-cutting

### 6.1 安全模型
- **看到別人的派工單＝資料外洩**，且員工之間會立刻發現。查詢一律以「已驗證的身分」為條件，
  不接受前端傳來的員工代號（同 [[pitfall_permission_code_is_not_tenant_boundary]]：不要用 client 傳的值當範圍）
- Ragic 金鑰是**我方持有的高權限憑證**，經我方後端代打，不外流給前端
- 走 B 時我方完全不碰資料（優點），但也**看不到任何使用狀況**（見 6.3）

### 6.2 容量與成本
每人每天按幾次、每次一個 Ragic 查詢，量級是每天數十次 —— 可忽略。
真正的成本在 **Ragic 帳號授權費**（若走 B、每個員工都要帳號），那是客戶的成本，要先講清楚。

### 6.3 觀測
⚠️ 走 B 的話**我方沒有任何埋點** —— 不知道有沒有人在用、也不知道有沒有人卡在登入頁。
若採 B，至少要約定一個回頭量測的方式（例如兩週後請客戶看 Ragic 的資料筆數），
否則「上線了但沒人用」我們不會知道（同 [`task-assign-notify.md`](task-assign-notify.md) §8 的量測點主張）。

### 6.4 向後兼容
新增 `?page=work` 對既有 LIFF 三頁零影響（`main.tsx` 是白名單分派，不在名單內走原本的 binding 流程）。
⚠️ 但要注意：**不在白名單的 page 目前會掉進「綁定/設密碼」分支**，
所以在後端支援之前就把按鈕指過去，員工會看到莫名其妙的綁定畫面 → 部署順序：後端 → 前端 → 改圖文選單網址。

## 10. 失效場景反思（FMEA · R17 · M0 版）

| 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|
| 清單 | 認不出這個 LINE 是誰 → 空清單 | **員工以為今天沒單，整天不做事** | **P0** | ⚠️ OQ-4 兩種文案分開 · 這是本模組最糟的失效 |
| 清單 | 多選欄位 `where` 篩不到 → **漏單** | 員工少做一張且**沒有人會發現** | **P0** | ⚠️ 卡 Q2 · 篩不到就別用 `where`，撈回來自己過濾 |
| 清單 | 對到**錯的**員工 | 看到別人的派工單＝資料外洩，員工之間馬上發現 | **P0** | ⚠️ 禁模糊比對 · 只用可靠鍵（員工編號／Ragic 帳號）|
| 開啟 | LINE 內建瀏覽器沒有 Ragic session → 登入頁 | 員工卡住、放棄 | **P1** | ⚠️ **明天驗收就會遇到**（§3）· 長期要看 Ragic 的 session 在 webview 撐多久 |
| 資料 | 鮮湧金鑰仍是 106（讀不到資料）| 走 A 時查詢一律回空 → 退化成 F-1 | **P1** | 🔒 外部 gate · 客戶換金鑰（backlog 用戶側待辦第 5 項）|
| 部署 | 按鈕先指到 `?page=work`、後端還沒支援 | 員工看到莫名其妙的**綁定畫面**（白名單外會掉進 binding 分支）| P1 | ✅ 部署順序：後端 → 前端 → 改選單網址（§6.4）|
| 期望 | 驗收看到固定連結 → 以為功能已完成 | 後續被當成「已經好了」而不再排期 | P1 | ⚠️ §8 已寫明 · 對客戶說明時要講「這是示意」|
| 觀測 | 走 B 時我方零埋點 | 上線但沒人用，我們不會知道 | P2 | ⚠️ OQ-7 約定回頭量測 |

**M0 結論：三個 P0 全部指向同一件事 —— 清單「錯了」或「空了」的時候，畫面看起來都很正常。**
這個模組的驗收重點不在正常路徑，在這三種失敗長什麼樣子。
