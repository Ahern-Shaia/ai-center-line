# four-features-reflection · 四項功能的向上設計

> 狀態：🚧 **M0 DRAFT v0.1**（2026-07-28）· 待用戶裁定 OQ-4FR-1..10
>
> 相關：[`tenant-prompt-decoupling.md`](tenant-prompt-decoupling.md)（同一個病的一個切面）、[`task-to-personal-report.md`](task-to-personal-report.md)、[`attendance-location-mileage.md`](attendance-location-mileage.md)、[`notify-selfserve-platform.md`](notify-selfserve-platform.md)
>
> ⚠️ **這份文件的結論一句話**：四項功能裡**唯一穩定運作的那項，是唯一不需要系統「認得東西」的那項**。
> 其餘三項不是做得不好，是**共同缺了一層主檔**——所以每一處都退化成自由文字，而自由文字之間永遠對不起來。

---

## 0. 方法

不憑感覺反思。以下每個判斷都對照 prod 實資料（台灣福祉，2026-07-22 ～ 07-28）。

---

## 1. 四項的實際狀態

| | 做什麼 | prod 實績 | 需不需要系統「認得東西」 |
|---|---|---|---|
| **一、訂單** | Ragic 訂單作業表變更 → LINE 群組通知 | **48 則送出、0 失敗**、3 條規則啟用 | ❌ **不需要** |
| **二、日誌** | 群組對話 → AI 整理 → 任務看板 | 39 群日、91 筆記錄、15 張任務 | ✅ 需要（人／機台／工單） |
| **三、日報** | 私訊＋任務 → 彙整 → 本人確認 | 16 份、**僅 3 份送出（19%）** | ✅ 需要（人） |
| **四、打卡** | 外勤定位＋里程 | 45 次、**僅 4 人用過**、31 趟 | ✅ 需要（人／客戶） |

---

## 2. ⭐ 核心診斷

**唯一跑得順的是唯一不需要認人的。**

訂單通知：Ragic 那邊有真實主檔（客戶編號、客戶全稱、業務人員、聯絡人、地址），
系統只要把欄位搬過來推到群組，不需要判斷「這是誰、這是哪個客戶」。
所以它 48 則零失敗。

另外三項全部要求系統「認得東西」，而系統認不得——於是全部打折。

> 這不是巧合，是**結構**。

---

## 3. ⭐⭐ 更深一層：不是綁定率問題，是沒有共用主檔

很容易把問題歸給「員工還沒綁 LINE」（4/42）。但綁定率只是**一個特例**。
真正的問題是：**系統沒有共用主檔，所以每個功能各自用自由文字。**

### 3.1 三處證據，同一個病

| 功能 | 應該對到的東西 | prod 實際填進去的 |
|---|---|---|
| **AI 抽取 · 當責人** | 公司同仁 | 「郁芬Sandra」「**佳慧/小星星/威廉/三爪**」「許佳惠/SHIN 新」 |
| **AI 抽取 · 機台／工單** | 工位代碼／工單號 | 命中率 **7% / 8%**（主檔是假的，靶子不存在） |
| **打卡 · 客戶／地點** | 客戶 | 「台北福特」「**午餐**」「**小卷米粉**」「加碼」「回廠」「測試」 |

打卡那一欄特別能說明問題：**它是自由輸入框**，所以同仁填的是「今天在幹嘛」，
不是「我在哪個客戶」。這不是同仁的錯——**沒有選單，就只能打字**。

### 3.2 於是四項功能之間永遠 join 不起來

任務裡的客戶是「雲林順益斗六廠」「彰化員榮醫院」（AI 從對話抽的），
打卡裡的客戶是「小卷米粉」「午餐」（同仁手打的），
訂單通知裡的客戶是 Ragic 的客戶編號（真的主檔）。

**三種寫法，零交集。** 所以：
- 打卡到某客戶 → 日報不會自動知道「今天去了雲林順益」
- 任務提到某客戶 → 看不出這個客戶今天有沒有人去
- 訂單成立 → 對不到後續的討論與出勤

### 3.3 而主檔其實就在旁邊

`data-sync-layer` 早就建好 `customer` / `contact` / `order` 三個 model 與資料表。

**prod 是 0 筆 —— 從來沒同步過。**

Ragic 那邊有：客戶編號、客戶全稱、聯絡人、聯絡電話、地址、業務人員、所屬部門⋯
（從 TB-P01 分析表的欄位清單就看得到，我們每天都在讀它來發通知）。

> **我們每天從 Ragic 讀客戶資料發通知，卻沒有把那份資料留下來當主檔。**

## 4. 向上設計 A ⭐ 補上主檔層（最高價值，其餘三項是它的下游）

```
現在                          應該
訂單 ──→ Ragic（有主檔）✅          ┌─ 共用主檔 ─┐
日誌 ──→ 自由文字 ❌          Ragic ─┤ 人/客戶/車輛 ├─→ 訂單/日誌/日報/打卡
日報 ──→ 自由文字 ❌         LINE ──┤   /工單     │   都從這裡取候選集
打卡 ──→ 自由文字 ❌                └────────────┘   輸出代碼而非字串
```

**立即可得的效果**（不需要員工改變任何行為）：

| 功能 | 改變 |
|---|---|
| **打卡** | 客戶欄從自由輸入 → **下拉選單**（近期去過的排前面）· 「小卷米粉」不會再出現 |
| **日誌** | AI 抽取有候選集 → 輸出對得上的人名與客戶（解 `tenant-prompt-decoupling` M1b） |
| **日報** | 能自動帶入「今天去了雲林順益（來自打卡）」 |
| **訂單** | 不變（它本來就有） |

> ⚠️ **這一項與 `tenant-prompt-decoupling` 是同一件事的兩半**。
> 那份 doc 講「prompt 裡的主檔是假的」，這份講「主檔根本沒同步進來」。
> **應該一起做**，否則會做兩次。

## 5. 向上設計 B · 以「一件事」為主體，而不是以「一個功能」為主體

真實世界裡這是**一條線**：

```
訂單成立 → 群組討論 → 出門看客戶 → 晚上回報
 (訂單)     (日誌)      (打卡)       (日報)
```

現在是**四條平行管線，各留一份，互不相識**。

有了主檔（§4）之後才 join 得起來，所以這是 A 的下游，不能先做。

**做到之後長什麼樣**：
- 客戶頁：這個客戶的訂單／討論／誰去過／幾次
- 日報：自動帶出「今天去了 A、B 兩家；A 那件事有一張任務在你身上」
- 任務卡：「這個客戶上週有人去過」

> 這是「戰情室」真正該長的樣子——現在的戰情室只看得到日誌那一條線。

## 6. 向上設計 C · 把散在四處的「人工確認」收斂

四項功能各自長出一個「人要確認」的環節：

| 功能 | 要誰確認 | 在哪 |
|---|---|---|
| 日誌 | 主管簽核 | 總覽儀表 |
| 任務 | 主管收為任務／不用追 | 任務看板 |
| 日報 | 本人送出 | 我的日報 |
| 打卡 | 里程申訴（M3 未做） | — |

**主管每天要進三個地方**，才知道今天要處理什麼。

建議收斂成一個「**今天要你確認的事**」入口，四種來源匯進同一個佇列。
不改各功能的邏輯，只改入口。

> ⚠️ 但**不要為了收斂而收斂**：四種確認的語意不同（簽核＝AI 抽對了嗎、
> 收為任務＝這件事要追嗎、送出日報＝我認可這份彙整）。
> 合併成一個佇列可以，但**不能合併成一顆按鈕**。

## 7. 向上設計 D · 價值對等（這是產品原則，不是技術）

看一下四項對員工的成本／收益：

| 功能 | 員工要做什麼 | 員工得到什麼 |
|---|---|---|
| **訂單通知** | **什麼都不用做** | 群組直接看到訂單狀態 |
| 日誌 | 什麼都不用做（被動採集） | 沒有 |
| 日報 | 綁定 + 每天確認送出 | 沒有（是主管要的） |
| 打卡 | 綁定 + 每次外出操作 | 沒有（是主管要的） |

**唯一零成本的那項，是唯一跑得順的。** 這不是巧合。

後三項要員工付出，回報卻都給了主管——所以 4/42 綁定、19% 送出率。

**原則：向員工要的每一個動作，都要有給員工的回報。**

可以立刻做的小事（不需大改）：
- 打卡 → 讓同仁自己看得到「本月跑了幾趟、多少公里」（里程已經在算了，只是沒給他看）
- 日報 → 送出後給一句回饋，而不是石沉大海
- 綁定 → 綁完立刻能查自己的東西（現在綁完沒有任何立即好處）

## 8. 明確**不**做的

| 不做 | 為什麼 |
|---|---|
| 四項合併成一個大模組 | 它們的節奏、使用者、失效模式都不同。合併只會讓一個壞掉時全部壞掉 |
| 為了 join 而強制員工填代碼 | 那是把成本再推給員工（違反 §7）。要用選單降低成本，不是加規則 |
| 打卡改成自動定位追蹤 | 隱私紅線。現在的「本人主動打卡」是對的 |
| 現在就做客戶 360 頁 | 沒有主檔之前那頁會是空的（同素材看板的教訓：先有資料再有畫面） |

## 9. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **F-1** | 主檔同步 | Ragic 客戶主檔同步進來含個資（電話／地址），進了 prompt 送給模型 | **個資外流** | **P0** | 只送名稱給 AI 當候選集，聯絡方式不進 prompt |
| **F-2** | 主檔同步 | 客戶主檔跨租戶混入（同 `tenant-twh` 的老問題） | 跨租戶外洩 | **P0** | 主檔查詢一律帶 tenant_id · 沿用既有 RLS |
| **F-3** | 打卡改選單 | 客戶不在主檔裡（新客戶、私人行程）→ 同仁選不到就不打卡 | 功能倒退 | **P1** | **必須保留自由輸入**作為 fallback，選單是加速不是限制 |
| **F-4** | 歷史資料 | 既有 45 筆打卡的「小卷米粉」對不到主檔 | 歷史無法 join | P2 | 不回頭清洗 · 從新資料開始 |
| **F-5** | 確認收斂 | 四種確認合成一顆按鈕 → 主管一鍵全過 | 把關失效 | **P1** | 可合佇列不可合按鈕（§6） |
| **F-6** | 價值對等 | 給員工看里程／日報回饋反而引發爭議（「你怎麼知道我去哪」） | 抗拒 | **P1** | 只給本人看自己的 · 不做同儕排名 |
| **F-7** | 範圍 | 這份反思被當成「四項都要重做」 | 停下正在跑的功能 | **P1** | §8 劃界 · 四項現在都能用，是**加地基**不是重蓋 |

## 10. 開放問題（OQ-4FR-N）

| # | 問題 | 建議 |
|---|---|---|
| **OQ-4FR-1** | 先做哪一項向上設計？ | **A 主檔層** · B/C 都是它的下游，D 是可並行的小事 |
| **OQ-4FR-2** | 主檔從 Ragic 同步還是自建？ | **同步** · Ragic 已是客戶的真實來源，自建會變成兩份互相打架 |
| **OQ-4FR-3** | A 要不要跟 tenant-prompt-decoupling 合併？ | **要** · 同一件事的兩半（§4），分開做會改兩次 prompt |
| **OQ-4FR-4** | 打卡客戶欄改選單，保不保留自由輸入？ | **保留**（F-3）· 選單是加速不是限制 |
| **OQ-4FR-5** | 確認收斂做不做？ | 可延後 · 等中信心「請您確認」跑一週看積壓量再說 |
| **OQ-4FR-6** | §7 那三件小事要不要現在做？ | **要** · 成本低、直接對著 4/42 與 19% 這兩個數字 |
| **OQ-4FR-7** | 客戶 360 頁？ | **不要現在做**（§8）· 沒主檔就是空頁 |
| **OQ-4FR-8** | 主檔同步頻率？ | ❓ 每日一次應該夠 · 但新客戶當天要用得到，需評估 |
| **OQ-4FR-9** | 要不要把「主檔命中率」做成常設指標？ | **要** · 同 OQ-TPD-8：沒有量測就等於沒有主檔 |
| **OQ-4FR-10** | 這份反思要不要拆成獨立模組 doc？ | A 拆出去跟 tenant-prompt-decoupling 合併；B/C/D 留在本文追蹤 |

## 11. 建議順序

| 期 | 做什麼 | 為什麼這個順序 |
|---|---|---|
| **P1** | §7 三件小事（讓員工看到自己的里程／日報回饋／綁定即時好處） | 成本最低、直接對著 4/42 與 19% |
| **P2** | **主檔層**：Ragic 客戶／聯絡人同步落地（`data_sync_customer` 現在 0 筆） | 其餘一切的地基 |
| **P3** | 打卡客戶欄改選單（保留自由輸入） | 主檔的第一個受益者，立刻可驗證 |
| **P4** | AI 抽取接主檔候選集（＝ tenant-prompt-decoupling M1b/M2） | 解機台 7%／工單 8%／人名對不上 |
| **P5** | 以「一件事」串四項（§5） | 主檔穩定後才有意義 |
| **P6** | 確認佇列收斂（§6） | 最不急 |

> **P2 是 gate**：主檔沒進來之前，P3–P5 全都做不了。
> 而 P1 不依賴任何東西，可以現在就做。
