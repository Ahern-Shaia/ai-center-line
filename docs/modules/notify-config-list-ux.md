## 1. 目標與範圍

### 1.1 目標
讓通知設定的兩個頁籤在規則與紀錄成長時仍然可用：找得到、看得懂、不被截斷成無意義。

### 1.2 為什麼現在做
- 規則從 5 條長到 **10 條**（2026-08-12 一天內新增 5 條），還會繼續加
- 通知紀錄 prod 現有 **70 筆**（2026-07-07 起、五週），依現行速度**約兩週後突破 100 筆**
  —— 而 `LogsTab` 寫死 `limit: 100`，超過的部分**不是難找，是查不到**

### 1.3 不做的事（B 方案的界線）
- 不做依客戶分組的可收合階層（A 方案的核心，已被否決）
- 不做可點的摘要條、不做「已套用條件」標籤列
- 不做兩行式列、不做列內啟用開關
- 不做查詢語法（`key:value`）—— 這條 A/B 都不做，見 §4.3

## 4. 技術設計

### 4.1 分頁做在哪一層 —— 兩頁不同

| 頁面 | 做法 | 理由 |
|---|---|---|
| **規則清單** | **client-side** | 10 條規則、可預見的規模是數十到數百。一次撈完再前端切頁，搜尋與篩選也在前端做 —— **零後端改動**，且篩選是即時的（無 round-trip）|
| **通知紀錄** | **server-side** | 筆數只會單調成長且無上限；不可能一次撈完 |

> 這是刻意的不對稱。統一做成 server-side 會讓規則清單多兩個端點卻沒有收益；
> 統一做成 client-side 則會在紀錄破萬筆時炸掉。

### 4.2 API 變動（只有紀錄頁）

```
GET /notify-config/logs
  ?status=&ruleId=            （既有）
  &from=YYYY-MM-DD            （新）· 省略＝不限
  &page=1&pageSize=25         （新）· 取代 limit
→ { rows: [...], total: number, statusCounts: { sent: 231, line_failed: 6, ... } }
```

- 回傳形狀由**陣列**改成**物件** —— 這是破壞性變更（R1），但這支端點只有 `LogsTab` 一個消費者
- `total` 與 `statusCounts` 各需一次 aggregate；`statusCounts` **不受 status 篩選影響**（否則點了「推送失敗」其他數字會全變 0）
- 排序索引已存在；`from` 過濾走同一支 `received_at DESC` 索引

### 4.3 為什麼不做查詢語法
Datadog 要學 `key:value`、Grafana 的 label 篩選要寫 Prometheus matcher（RE2、fully anchored、大小寫敏感）。
這頁的使用者是**業助與 aiproot 內部維運**，不是 SRE。四個下拉 ＋ 一個全文搜尋即可。

## 5. §A5 對標與向上設計（R16）

查證日期 2026-08-12，均為現行版本：

| 產品 | 做對的 | 最弱的 |
|---|---|---|
| **Datadog Monitors** | facet 側欄與搜尋列**雙向同步**（新手用點的、老手用打的共用同一份狀態）| 多選邏輯不一致（同 facet 內 OR、部分 tag 卻是 AND），UI 上看不出來 |
| **Grafana Alert rules** | folder→group→rule 可收合階層取代分頁；篩選可存成具名檢視並設為預設 | label 篩選要 Prometheus matcher，非工程背景直接卡死 |
| **Zapier Zaps** | 列內 status toggle（0 跳轉 0 確認）；app 用 icon 不用文字，省最多寬度 | 搜尋只比對 Zap 名稱，找不到「用了哪張表」|
| **Make Scenarios** | 搜尋會**搜進流程內部**（模組欄位值、URL、註解）| 視覺化 Grid 規模一大就變麵條 |
| **GitHub Actions**（反例）| —— | 名稱固定欄寬硬截斷且**無 tooltip**，monorepo 使用者找不到 workflow |

**共同弱點**：五個產品**沒有一個**提供「已套用條件可單獨移除的標籤列」。

**我們的向上點（B 方案能拿到的部分）**：
1. 取 Make 的「搜到內部」——搜得到**通知欄位名**（R1）
2. 避開 GitHub 的坑 —— **所有截斷一律配滑過提示**（R3 / L5）
3. 狀態篩選帶筆數（L3）—— Datadog / Grafana / Zapier 的狀態篩選都不顯示各狀態有幾筆

> ⚠️ **B 放棄的向上點**：可點摘要條、已套用標籤列、失敗原因整行寬。
> 這幾條在 A 方案裡；選 B 等於接受「出事時要多花幾秒才讀得懂」。

## 7. 測試策略

| 層 | 測什麼 |
|---|---|
| 後端單元 | `page=2` 真的跳過前 25 筆；`from` 邊界（當天 00:00 含入）；`statusCounts` **不受 status 篩選影響**；`pageSize` 上限鉗制（避免 `pageSize=99999` 當成 DoS）|
| 後端單元 | `total` 與實際列數一致（分頁最常見的 off-by-one）|
| 前端 | 手動：1000px 視窗下兩頁皆無折行；篩選後分頁重置回第 1 頁 |

> ⚠️ **「篩選後分頁不重置」是分頁最典型的 bug**：停在第 3 頁時改篩選 → 結果只剩 1 頁 → 畫面空白，看起來像沒資料。

## 9. 失效場景反思（FMEA · R17）

| 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|
| 紀錄頁載入 | 回傳形狀由陣列改成物件，前端沒同步 | 整頁白畫面 | **P0** | ✅ 只有一個消費者；M1/M2 必須同一次部署上線，或後端先相容兩種形狀 |
| 分頁 | 篩選改變後分頁沒重置 | 停在第 3 頁 → 空白畫面 → 看起來像沒資料 | P1 | ✅ 列入 §7 測試；篩選變動一律 `setPage(1)` |
| 分頁 | `pageSize` 未鉗制被塞大數 | 一次撈全表 | P1 | ✅ OQ-9 上限 100，後端鉗制（不信前端）|
| 時間範圍 | 預設近 7 天，使用者找的是三週前那筆 | 以為紀錄不見了 | P1 | ✅ OQ-3：空結果時明確提示「這個範圍內沒有紀錄，試試更長的範圍」，而非只寫「沒有資料」 |
| 截斷 | 截斷但沒有滑過提示 | 資訊等於消失（GitHub 反例）| P1 | ✅ R3/L5 明列；所有 `.clip` 必帶 `title` |
| 隔離 | 日後把這兩頁開放給租戶端 | `notification_log` 無 RLS → **跨租戶紀錄全可見** | **P0** | ⚠️ 本次不開放；開放前必須先補 tenant 過濾或加 RLS（見 §2.3、[[pitfall_analysis_tables_no_rls]]）|
| 效能 | `total` 每次都 `count(*)` 全表 | 紀錄破十萬筆後變慢 | P2 | ⚠️ 目前 70 筆，遠未到；破萬再考慮估算或 cursor 分頁 |
