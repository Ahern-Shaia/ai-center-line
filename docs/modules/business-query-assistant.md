## 0. 觸發

用戶提出 9 個真實使用情境（2026-07-27），並附台灣福祉現行的內部回報日報照片。

### 0.1 日報照片解讀（比 9 個情境更早該處理的訊號）

照片是一份**陌生開發拜訪紀錄**，每筆結構高度一致：

| 欄位 | 例 |
|---|---|
| 機構名稱 | 頤園護理之家 |
| 地址 | 台北市士林區福順里重慶北路四段 138 號 |
| 電話 | 0228119666 |
| 聯絡人 | 李先生 |
| 現況／洽談內容 | 「目前和車行配合接送，另外談和醫院有合作內容」 |
| 後續動作 | 「加 Line 保持聯絡」「留 DM」「待內部討論決議後評估」 |
| 商機訊號 | 「之後規劃會有福祉車的需求」「剛購入 Luxgen 斜坡板福祉車兩年」 |

**三個推論**：

1. **他們要的其實是 CRM，不是日報。** 這些欄位就是潛在客戶主檔——機構、地址、電話、聯絡人、階段、下一步。現在它們被寫成一段純文字，寫完就沉沒；下次誰去拜訪、上次談到哪、什麼時候該回訪，全靠人腦記。
2. **這是情境 1（業績圖表）的源頭。** 沒有把拜訪沉澱成結構化的客戶／商機，就沒有漏斗、沒有轉換率，「業績圖表」只能畫已成交訂單，看不到過程。
3. **這是情境 8（對話 → 行事曆）的真實素材。**「待內部討論決議」「兩年」「之後規劃」都是後續追蹤時點，但**沒有一個是明確日期**——這直接決定了情境 8 的設計（見 §5.3）。

> ⚠️ 我方現行 `personal-daily-report` 的抽取 schema 是 `title / detail / time / followup`，**接不住這個格式**（沒有機構／地址／電話／聯絡人／階段）。這是一個獨立的既有缺口，見 OQ-BQA-13。

## 1. 需求分類 —— 這不是一個功能，是三條技術路徑

把 9 個情境當成「加一個 AI 問答」會出災難。它們的資料來源與正確性要求完全不同：

| # | 需求 | 類別 | 答案來自 | 錯了會怎樣 |
|---|---|---|---|---|
| 1 | 個人／部門業績圖表 | **B · 指標聚合** | ERP 訂單 | 數字錯 → 決策錯、考績爭議 |
| 2 | 庫存車數量／價位／年份 | **A · 結構化查詢** | ERP 庫存主檔 | 報錯價 → 對客戶失信 |
| 3 | 料號（成品／原料）價格 | **A** | ERP 品號主檔 | 同上 |
| 4 | 客戶應收帳款 | **A**（財務敏感） | ERP AR | 洩漏 or 錯報 → 合規問題 |
| 5 | 兩個月內有給佣金的訂單 | **A**（多條件） | ERP 訂單 + 佣金 | 佣金算錯 → 薪酬糾紛 |
| 6 | 預計訂單何時交車 | **A**（可能需推算） | ERP 訂單 + 交期 | 承諾錯交期 → 客訴 |
| 7 | 本週可交貨訂單 → 排業務行事曆 | **A + D · 主動推送** | ERP | 漏排 → 漏交車 |
| 8 | 對話出現日期 → 自動同步行事曆 | **C · 對話抽取** | LINE 對話 | 誤排 → 行事曆變垃圾場 |
| 9 | 某專案研發進度 | **A 或 C**（看資料在哪，見 §2） | ? | — |

### 1.1 核心設計主張：數字一律由資料庫算，LLM 只負責翻譯問題

**2–7、9 的答案是錢和交期。** 這類問題**不能**用 RAG（把資料塞進 prompt 讓模型讀出答案）：

| RAG 做數字查詢的問題 | 後果 |
|---|---|
| LLM 會算錯、會編造沒看到的欄位 | 直接違反 **CLAUDE.md R11**（禁止臆測數字、缺漏填 null） |
| 資料量一大塞不進 context | 「這兩個月的訂單」可能上千筆，塞不下就變抽樣，答案默默失真 |
| 無法稽核 | 客戶問「這數字哪來的」，答不出來 |

**正解是 text-to-query**：

```
使用者問句
   ↓  LLM 只做這一步：把人話對應到「哪個指標 / 哪張表 / 哪些條件」
受控查詢（不是自由 SQL · 見 §4.2）
   ↓  數字由 Postgres 算
結果 + 「這個數字怎麼來的」說明 + 原始資料連結
```

LLM **不接觸數字的計算**，只做語意對應。算錯的可能性從「模型幻覺」降到「查詢寫錯」——後者可測試、可稽核、可回歸。

> 這與 [`rag-conversations.md`](rag-conversations.md) 是**互補不是重疊**：RAG 回答「誰在群組裡說過什麼」，本模組回答「數字是多少」。兩者共用問答入口，但走完全不同的後端。

## 3. 分層架構

```
┌──────────────────────────────────────────────────────────┐
│  入口（三個，共用同一套後端）                              │
│  · 戰情室問答框   · LINE 私訊 bot   · 主動推播（情境 7）   │
└───────────────────────────┬──────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────┐
│  意圖路由 —— 這題該走哪條路？                              │
│  指標型(1) / 查詢型(2-7,9) / 對話型(RAG) / 不會答          │
└───────┬───────────────┬───────────────┬──────────────────┘
        ↓               ↓               ↓
   ┌─────────┐    ┌───────────┐   ┌──────────┐
   │ 指標層  │    │ 語意查詢層 │   │ RAG      │
   │ (§4.1)  │    │  (§4.2)   │   │（既有）   │
   └────┬────┘    └─────┬─────┘   └──────────┘
        └───────┬───────┘
                ↓
      ┌────────────────────┐
      │ 權限過濾（§6）      │ ← 同一問句 · 不同角色不同答案
      └─────────┬──────────┘
                ↓
      ┌────────────────────┐
      │ 中介資料層（既有）   │ ← ERP-agnostic
      └────────────────────┘
```

**關鍵：權限過濾在查詢層，不在 prompt。** 用 prompt 說「你不可以告訴業務別人的業績」是可以被繞過的（prompt injection）；正確做法是查詢本身就帶 scope 條件，資料庫層根本查不出來。

## 4. 兩個核心元件

### 4.1 指標層（Metric Layer）· 對應情境 1

**問題**：「業績」是什麼？簽約日還是交車日認列？含稅還是未稅？退訂算不算？主管的業績含不含下屬？

這些**沒有標準答案，只有公司的答案**。所以指標必須**先定義、存起來、被所有入口共用**——不能每次讓 LLM 自由發揮，否則同一個問題今天和明天的答案會不一樣。

```
metric_definition
  metric_key      業績金額 / 訂單數 / 平均客單價 / 毛利
  display_name    中文名（使用者看的）
  aggregation     sum | count | avg
  source_entity   order
  value_field     哪個欄位
  date_field      認列時點依哪個日期（簽約 / 交車 / 收款）
  filters         排除退訂 / 只算已成交…
  scope_field     業務歸屬欄位（算誰的業績）
```

**指標定義一律前端可設**（承 2026-07-24 用戶鐵則「如果有配置設定的話，一律前端操作」）。

圖表型別（線／長條／圓餅）由「維度 × 時間」自動決定，不讓使用者選——時間序列給線圖、分類比較給長條、佔比給圓餅。

### 4.2 語意查詢層 · 對應情境 2–7、9

**不做自由 text-to-SQL。** 讓 LLM 直接產 SQL 打正式庫是三重風險：注入、洩漏、拖垮 DB。

改用**受控查詢範本**：

```
query_template
  template_key    inventory_search / price_lookup / ar_by_customer / orders_by_period …
  display_name    中文說明（也是給 LLM 的選擇依據）
  entity          查哪個 entity
  allowed_filters 允許哪些條件（欄位 + 運算子白名單）
  allowed_sorts   允許怎麼排
  default_limit   預設筆數上限
  required_perm   要什麼權限才能用
```

LLM 的工作只有兩件：**選一個 template** + **填參數**（走 structured output + zod 驗證）。填出白名單以外的欄位 → 驗證直接擋下。

**答不出來要明說。** 找不到對應 template（例如問「毛利率趨勢」但沒定義）→ 回「這個問題目前查不到，需要先設定對應的查詢」，**絕不讓 LLM 硬掰**。

### 4.3 每個答案都要附「怎麼來的」

承 [`attendance-mileage-transparency`](attendance-mileage-transparency.md) 的教訓——**數字沒有依據就會被質疑，然後整個系統失去信任**。

每個回答固定附：

```
本月業績 NT$ 2,340,000（12 筆訂單）

依據：訂單表 · 認列時點＝交車日 · 已排除退訂 2 筆
期間：2026-07-01 ~ 2026-07-27
範圍：你自己的訂單
[查看這 12 筆明細]
```

## 5. 情境 7 / 8 · 行事曆

### 5.1 情境 7（本週可交貨 → 排行事曆）＝ 查詢 + 推送

這題其實是「排程查詢 + 主動通知」，**不需要行事曆整合就能解 8 成**：每週一早上把本週可交貨訂單推到業務的 LINE 私訊。走既有 [`notification-hub`](notification-hub.md) 的 `schedule` 來源即可，工程量小、沒有外部依賴。

### 5.2 情境 8（工作日誌出現日期 → 同步行事曆）· ⚠️ 最該謹慎的一題

> **資料來源已由客戶指明：「從工作日誌裡面」＝ 我方 `personal-daily-report`（我的日報）。**
> PDR 抽取 schema 已有 `followup` 欄位（自由文字，例「明日 09:00 跟人資申請 2 名」），**這就是現成的原料**——不必另建抽取管線，但要把自由文字再解析成明確日期。

「自動」兩個字是陷阱。看日報照片的實際用語：

> 「**之後**規劃會有福祉車的需求」「待內部討論決議後評估」「剛購入⋯**兩年**」

**沒有一個是可直接排程的日期。** 而真正出現日期的對話，也未必是承諾（「上週三我去過了」是過去式、「下週三再說」是推託）。

若做成「看到日期就寫入行事曆」，兩週內行事曆就會變成垃圾場，然後使用者關掉功能——這是**比沒做更糟**的結果。

**建議設計**：AI 只做「**建議**」，不直接寫入。

```
LINE 私訊 bot：
  偵測到你和「頤園護理之家」的對話提到後續追蹤，
  要幫你排提醒嗎？
  ┌──────────────┬──────────────┬──────────┐
  │ 排 8/15 回訪  │  改時間       │  不用     │
  └──────────────┴──────────────┴──────────┘
```

按了才寫。**沒有「按了才寫」這一步，這個功能會自己殺死自己。**

#### 5.2.1 三個階段（第一階段完全不碰外部整合）

| 階段 | 內容 | 外部依賴 | 這一階段真正的目的 |
|---|---|---|---|
| **① 系統內待辦 + LINE 到期提醒** | 日報 `followup` → 解析成有日期的待辦 → 到期前 LINE 私訊 | **無** | **驗證抽得準不準**——十筆有六筆是垃圾的話，後面兩階段不用做 |
| **② 問過才寫** | LINE 私訊確認後才建立行程 | 無 | 把誤排成本降到 0 |
| **③ 對外行事曆** | .ics 訂閱（→ 必要時才 OAuth） | Google | 讓使用者在原本就在看的地方看到 |

**①「驗證抽得準不準」是整條路的閘門**，不是暖身。三種典型誤判要在這階段量化：

| 誤判 | 例 |
|---|---|
| 過去式當成未來 | 「上週三我去過了」 |
| 推託當成承諾 | 「下週再說」 |
| 相對時間基準錯 | 「下週三」是相對訊息當下，還是相對日報日期？ |

誤排的代價**不對稱**：行事曆是每天都會看的東西，塞進三筆垃圾就會被關掉，而且會連帶不信任整個系統。**這比不做更糟。**

### 5.3 行事曆落在哪

> **2026-07-27 客戶原話**：「請問我們從工作日誌裡面，有跟客戶約時間日期或有相關會議可以同時同步到行事曆嗎？LINE 或 Gmail」
>
> 需求由客戶主動提出＝**需求是真的**，不是我方臆測。但客戶指定的兩個目標，一個不存在、一個有前提。

#### 5.3.1 ⚠️ LINE 沒有可寫入的行事曆

消費者版 LINE **沒有行事曆功能，也沒有對應 API**。Messaging API 能做的只有「到時間私訊提醒」——那是**通知，不是行事曆**。

- 若客戶想的是「LINE 會提醒我」→ 我方**現有的 notification-hub 就能做**，不需要任何新整合。
- 若客戶用的是 **LINE WORKS**（企業版、另外訂閱），那才有行事曆與 API。**需確認他們有沒有用**（見 OQ-BQA-16）。

**溝通時要先把這件事講清楚**，否則會答應一個做不到的東西。

#### 5.3.2 Gmail ＝ Google Calendar · 授權成本取決於一件事

| 客戶用的是 | 授權方式 | 成本 |
|---|---|---|
| **Google Workspace**（公司網域） | 管理員一次 domain-wide 授權 | 低 · 員工無感 |
| **個人 Gmail** | **每人各自跑一次 OAuth** | 高 · 還要處理 token 過期、離職回收 |

→ **這是動工前必問的前提**（OQ-BQA-16）。

#### 5.3.3 三個落點選項

| 選項 | 成本 | 優點 | 缺點 |
|---|---|---|---|
| **A · 系統內建行程**（我方 DB + 頁面 + LINE 提醒）| 小 | 無外部依賴、可帶客戶／訂單關聯、**可驗證抽取準不準** | 使用者要多看一個地方 |
| **B · .ics 訂閱連結** ⭐ | **小** | **零 OAuth、零 token 管理**、離職撤銷網址即可、Google／Apple／Outlook 通吃 | 唯讀、更新有數小時延遲（依對方抓取頻率） |
| C · Google Calendar OAuth 雙向 | 大 | 即時、可雙向 | 每人授權、token 續期、離職回收、API 配額 |

**建議 A → B → C，且 C 不預先承諾。**

**B（.ics 訂閱）是被低估的解**：給每位員工一個私密網址，他自己在 Google Calendar 選「從網址加入日曆」即可，之後自動更新。把「Google 整合」的成本從「一人一次 OAuth ＋ token 生命週期管理」降到「產一個 URL」。**只有在實測後確認延遲不可接受，才值得升級到 C。**

## 6. 權限模型 · 同一問句、不同答案

| 角色 | 業績（1） | 庫存／料號（2,3） | 應收帳款（4） | 佣金（5） | 交期（6,7） |
|---|---|---|---|---|---|
| 業務個人 | 只有自己 | ✅ | ❌ | 只有自己的 | 只有自己的單 |
| 業務主管 | 自己 + 部門 | ✅ | ⚠️ 依裁定 | 部門 | 部門 |
| 財務 | ❌ 或唯讀 | ✅ | ✅ 全部 | ✅ 全部 | ✅ |
| 總經理 | 全公司 | ✅ | ✅ | ✅ | ✅ |

實作方式：
- **每個 query_template 綁 `required_perm`**（沿用既有 permission-engine）
- **scope 條件由後端依 JWT 注入**，不接受前端或 LLM 指定「查誰的」
- 越權的問句回「你沒有權限查看這項資料」，**不是回空結果**——回空會讓人以為沒資料，反而製造誤解

> 承 `rule_outer_shell_sweep`：這是 cross-cutting concern，permission 要一路 sweep 到問答入口、推播、匯出，不只 endpoint。

| **P0** | §2 資料盤點 | — | 決定後面全部做不做得成 |
| **P1** | 拜訪紀錄結構化（日報 → 潛在客戶主檔） | 無 | **不依賴 ERP**、立刻可做、是情境 1 的源頭 |
| **P2** | 指標層 + 業績圖表（情境 1） | 訂單有業務歸屬 | 主管最有感 |
| **P2.5** | **行事曆階段①**：日報 followup → 系統內待辦 + LINE 到期提醒（§5.2.1） | P1 · **不需 ERP、不需外部授權** | **客戶 2026-07-27 主動要求** · 也是抽取準確度的閘門 |
| **P3** | 語意查詢層 + 3 個 template（情境 2/3/6） | 對應 ERP 表已同步 | 「問一句就有答案」的體感 |
| **P4** | 財務類 template（情境 4/5）+ 權限 | 財務資料已同步 | 敏感度高、最後做 |
| **P5** | 排程推播（情境 7）+ 行事曆階段② 問過才寫 | P2.5 | 主動化 |
| **P6** | 行事曆階段③ .ics 訂閱（必要時才 OAuth） | P5 + ① 準確度過關 | 讓使用者在原本的地方看到 |

**P1 先做的理由**：它是唯一**不依賴 ERP 有資料**的一項，而且直接對應照片裡他們每天在做的事。P0 盤點若發現 ERP 是空的，P1 仍然能交付價值。

**行事曆從 P6 提前到 P2.5 的理由**（2026-07-27 修訂）：客戶主動開口＝需求已驗證，且**階段①不需要 ERP 資料、不需要外部授權**，與 P0 盤點結果無關。但只提前階段①——對外整合（③）維持在最後，且不預先承諾。

## 8. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| F-1 | 語意查詢 | LLM 選錯 template，答非所問但看起來合理 | **決策依錯數字** | **P0** | 回答固定附「依據」（§4.3）；低信心時要求使用者確認 template 而非直接答 |
| F-2 | 語意查詢 | 參數填出白名單外欄位 | 洩漏 / 錯誤 | **P0** | zod 白名單驗證，擋下即回「查不到」 |
| F-3 | 權限 | scope 由 LLM 決定 → 業務查到別人業績 | **資料外洩** | **P0** | scope 一律後端依 JWT 注入，LLM 無法指定 |
| F-4 | 指標 | 指標定義沒共識（認列時點不同）→ 各部門數字對不起來 | 內部爭議 | **P0** | 指標定義前端可設 + 顯示定義；上線前與客戶對帳 |
| F-5 | 資料 | ERP 沒資料就上線 | 使用者問三次都查不到 → 永久放棄 | **P0** | §2 gate，沒資料的項目不進 M1 |
| F-6 | 同步延遲 | 中介層資料落後 ERP | 報舊數字 | P1 | 回答附「資料截至 HH:MM」；財務類要求即時查或明示延遲 |
| F-7 | 行事曆 | 自動寫入誤排 | 行事曆變垃圾場 → 關掉功能 | **P0** | §5.2 只建議不自動寫 |
| F-7b | 行事曆 | 對客戶承諾「同步到 LINE 行事曆」，但該功能不存在 | **交付不出來、信任受損** | **P0** | §5.3.1 · 對外溝通前先確認 LINE WORKS 有無（OQ-BQA-16）|
| F-7c | 行事曆 | 個人 Gmail 逐人 OAuth · token 過期或離職未回收 | 同步靜默停止 / 前員工仍收得到公司行程 | P1 | 優先走 .ics 訂閱（可撤銷 URL）· 走 OAuth 才需 token 生命週期管理 |
| F-8 | 成本 | 每個問句都打 LLM | token 成本失控 | P1 | 常見問句快取；意圖路由先用規則命中再退 LLM |
| F-9 | 效能 | 大範圍聚合拖垮 DB | 全系統慢 | P1 | template 帶 default_limit + timeout；重指標預先物化 |
| F-10 | 信任 | 答錯一次 | 使用者不再相信任何答案 | **P0** | 寧可答「查不到」也不硬掰（§4.2） |

**P0 共 7 條** —— 這個模組的風險密度明顯高於前面幾個模組，因為它直接產出「被拿去做決策的數字」。
