## 0. 觸發 · 資料自己劃出了那條線

平台是多租戶，但每家客戶的business性質不同。抽取要做到什麼程度的共用、什麼程度的客製？

2026-07-27 查台灣福祉正式環境 6 天真實資料（60 筆結構化紀錄），**填充率把答案講得很清楚**：

| 欄位 | 填充率 | 判讀 |
|---|---|---|
| `status` 狀態 | **100%** | 跨業種通用 |
| `person` 對口 | **72%** | 跨業種通用 |
| `title` / `detail` | ~100% | 跨業種通用 |
| `machine_code` 機台 | **7%** | 業種特定（工廠） |
| `work_order` 工單 | **8%** | 業種特定（工廠） |

**關鍵洞察：不是所有東西都一樣「因客戶而異」。**

「誰要做什麼、狀態如何」在任何行業都成立；「機台／工單」只在產線成立。
**這條線不是我們畫的，是資料量出來的**——所以它可信。

## 1. 三個直覺解法，以及它們為什麼不行

| 解法 | 問題 | 實證 |
|---|---|---|
| **A · 每家客製一套 schema** | 10 家＝10 套 prompt／schema／回歸樣本。共通 bug 要改 10 次。維護成本線性成長 | 這是接案模式。競品業務王走這條路，靠的是一支團隊；我方 solo，會被拖死（見 [`../market/競品分析-業務王Salesking.md`](../market/競品分析-業務王Salesking.md)） |
| **B · 做一個超級通用 schema（欄位聯集）** | 欄位爆炸、大部分 null、LLM 面對太多欄位會亂填 | 現行 `daily_reports` 才 11 個欄位，機台／工單就已經是 7%／8% |
| **C · 完全自由抽取（不定 schema）** | 每次結果形狀不同 → 無法聚合、無法做看板、無法回歸測試 | 違反 R11（結構化契約）與 R12（回歸驗證） |

**正解不是三選一，是分層。**

## 2. 三層模型

```
┌─────────────────────────────────────────────────────────┐
│ L1 · 通用核心   所有租戶共用 · 不可改 · 不可關            │
│    誰說的 / 什麼事(title,detail) / 當責人(person)        │
│    狀態(status) / 信心度 / source_ids 可溯源              │
│    ← 台灣福祉實測 72–100% 填充                            │
├─────────────────────────────────────────────────────────┤
│ L2 · 業種模板   我方維護的有限選項 · 開通時選一個          │
│    · 服務工單型（客戶/車輛/施作項目/金額）                 │
│    · 產線報工型（機台/工單/產出/不良/工時）                │
│    · 專案型（專案/里程碑/交付物）                          │
│    · 通路巡店型（門市/陳列/競品）                          │
├─────────────────────────────────────────────────────────┤
│ L3 · 租戶詞彙   是「資料」不是「程式」· 客戶自己維護        │
│    客戶名單 / 車型 / 站點 / 人員 / 產品                    │
│    ← 從 ERP 或中介資料層來（data-sync-layer）             │
└─────────────────────────────────────────────────────────┘
```

### 2.1 判準：什麼該進哪一層

**問一句就分得出來：**

| 差異是什麼 | 進哪層 |
|---|---|
| **欄位結構不同**（工廠有機台、服務業有客戶車輛） | **L2 模板** |
| **同欄位、不同值**（都有「客戶」，但客戶名單不同） | **L3 詞彙** |
| **任何行業都需要**（誰、什麼事、狀態、可溯源） | **L1 核心** |

範例：「客戶名稱」這個**欄位**所有服務型客戶都有（L2）；但客戶**名單**每家不同（L3）。

### 2.2 L1 不可關

L1 是安全網（見 §4）。任何租戶、任何模板、模板選錯的時候，L1 都照常運作。

## 3. 商業紀律：模板必須刻意稀少

**接新客戶時只問一句：他能不能套現有模板？**

| 答案 | 做法 |
|---|---|
| **能** | 開通即用，邊際成本趨近零 |
| **不能** | 要嘛投資做第 N+1 個模板（一次投入、之後所有同業複用），**要嘛不接** |

> **如果每家都要一個新模板，那不是 SaaS，是接案公司。**

這條紀律的成本是**要有能力拒絕不合的客戶**；不守的代價是產品線被客製拖垮。

**判斷是否值得做新模板**：這個模板能不能開一個**垂直市場**（不只服務一家）？
- 「服務工單型」→ 可服務福祉車、設備維修、水電工程、長照派工 ✅ 值得
- 「某客戶特有的三個欄位」→ ❌ 那是 L3 或不做

## 4. 過渡期的安全網：L1 永遠先運作

模板還沒有、或選錯的時候，**不會開天窗**——L1 的通用抽取照樣產出。

**實證**：台灣福祉現在 `daily_report` 是 **0 筆**（schema 不合），但 L1 的 `records` 抽了 **60 筆**且品質良好（採購詢價、維修協調、技轉支援都抽得準）。客戶當下仍有價值可用。

這讓「先接客戶、再補模板」變成可行路徑，而不是賭注。

---

## 5. 可觀測性：填充率要當常設指標

**今天的問題是：模板不合，是我手動連 prod DB 撈出來才發現的。**

這不該靠人臨時查。**模板選錯的訊號很明確：某幾個欄位長期接近 0%。**

**建議**：aiproot 後台加「抽取健康度」——每租戶、每欄位的填充率與信心度分佈。

| 訊號 | 判讀 |
|---|---|
| 某欄位填充率 < 10% 且持續一週 | 模板可能不合，或該欄位對此租戶無意義 |
| high 信心佔比過低 | 抽取品質問題，或對話本身太零碎 |
| 整體產出量低但訊息量高 | 群組性質不適合分析（閒聊為主）|

**價值**：開通新客戶跑一週就知道模板套對沒有，不用等客戶抱怨「怎麼都抽不到東西」。

> 這也回答了「怎麼證明系統有在work」——用同一組指標對客戶說明（今天的客戶文件就是這樣寫的）。

## 6. 對三個待裁定事項的影響

**先定本文，再定它們**，否則會做出三套不一致的做法：

| 待裁定事項 | 本文的裁決 |
|---|---|
| [`extraction-schema-service-order`](extraction-schema-service-order.md) | 它就是 **L2 的第一個模板**。原本 OQ-ESO-2「並存 vs 取代」在分層框架下自動有答案：**並存**，因為 L2 本來就是多選一 |
| [`business-query-assistant`](business-query-assistant.md) | 指標定義同樣分層：**L1 通用指標**（筆數、完成率）所有租戶共用；**L2 業種指標**（產能利用率 vs 服務單均價）依模板；**L3 是資料**（客戶名單） |
| [`task-to-personal-report`](task-to-personal-report.md) | 人名對應屬 **L3**（每租戶的成員名單），但「有當責人」這個欄位屬 **L1** —— 所以身分解析要用 L3 的名單去 grounding L1 的欄位 |

## 7. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| F-1 | 商業紀律 | 為了成交而承諾客製模板 | **產品線退化成接案**，維護成本線性成長 | **P0** | §3 明文紀律：模板要能開垂直市場才做；不合就不接 |
| F-2 | 模板選錯 | 開通時選錯，客戶用了三個月才發現抽不到東西 | 信任損失、可能流失 | **P0** | §5 填充率常設指標；開通後一週回檢 |
| F-3 | L1/L2 界線模糊 | 業種欄位偷偷混進 L1 | L1 開始膨脹，退化成解法 B（欄位聯集） | **P1** | §2.1 判準；L1 變更需明確理由與跨租戶驗證 |
| F-4 | L2 爆炸 | 模板越開越多，變相客製 | 同 F-1 | P1 | 模板數量設上限（建議 ≤5），新增需裁定 |
| F-5 | L3 缺資料 | 租戶沒有主檔 → grounding 失效 | 抽取品質下降 | P1 | L1 不依賴 L3 仍可運作（§4）；L3 只提升精度不決定可用性 |
| F-6 | prompt 膨脹 | 多模板並存導致 prompt 變長、成本上升 | token 成本 | P2 | per-tenant 只啟用選定模板；system prompt 走 caching |
| F-7 | 回歸 | 新增 L2 模板讓既有模板抽取品質下降 | 既有客戶退化 | **P0** | R12：新舊樣本都要過；`samples/` 每個模板一組基準 |

**P0 共 3 條**：兩條關於「別退化成接案」，一條關於「別讓新客戶拖累舊客戶」。

### 刻意的預設值（compat）

`tenants.extraction_template` **default = `factory_report` ＝現行行為**。跑完 0030 不會有任何租戶的抽取行為改變；要切 `general` 由人在後台操作。

### R12 回歸的處理方式（與慣例不同，說明理由）

CLAUDE.md R12 要求改 schema/prompt 後重跑 `samples/`。**這次沒有跑，改用單元測試**，理由：

- `npm run analyze` 跑的是 **CLI prototype（`src/`）**，本次改的是 **server pipeline**（兩份各自獨立 copy）。跑 CLI 會「通過」但完全沒驗到這次的改動——**那是假的綠燈**。
- 真正的風險是兩件事，且都能靜態驗證：① 拆 prompt 時漏掉規則 ② `general` 模板叫模型產出 schema 裡沒有的欄位。
- 已加 `server/test/conversation-analysis.templates.test.ts`（9 tests）覆蓋：L1 各模板皆可解析、factory_report 形狀與改版前一致、prompt 拆分後指示不漏、base prompt 不得殘留 L2 指示、模板上限 5 個、default 必須等於現行行為。**永久防線，不花 API 費用。**

> ⚠️ **已知技術債**：`src/`（CLI）與 `server/src/conversation-analysis/pipeline/`（prod）是兩份 copy，本次只改後者，兩邊已進一步分歧。收斂成 shared package 另議。

### 實測（本機 · migration 0030 已跑）

造 20 筆記錄（person 15、machine_code 1、work_order 0）驗證聚合與警示：

```
aiproot [產線報工型]  訊息=60 L1=20 L2=0
  L1 當責人  75%  L1 狀態 100%  L1 機台 5%  L1 工單 0%
  ⚠ machine_code、work_order 幾乎抽不到（<10%）· 模板可能不合
  ⚠ 套用的業種模板完全沒有產出 · 該客戶的回報格式可能對不上
```

**成功重現台灣福祉的樣態**（§0 基準：對口 72% / 機台 7% / 工單 8%）——這正是儀表要抓的訊號。
