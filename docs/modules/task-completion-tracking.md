## 0. 觸發

用戶提的流程：

```
任務追蹤(AI分析、人工指派) → 個人日報(每日更新) → 未完成 → 每天追蹤
                                              → 完成   → 任務結束
```

這正是目前明確缺的一塊——`回覆總經理_群組分析能做什麼_業務用.md` §C 就寫著
「不要說可以自動催辦／自動判斷有沒有做完，**目前沒有，它只記錄，不追蹤完成度**」。

## 1. 現況查驗

### 1.1 tickets 已經有三個狀態維度，擁有者各不相同

| 欄位 | 誰決定 | 回答什麼 | 值 |
|---|---|---|---|
| `status` | **AI** | 對話裡這件事到哪了 | open / in_progress / resolved / info |
| `confirm_status` | **主管** | 簽核佇列位置 | 待簽核 / 已簽核 / 逾時警示 / 待確認 / 已忽略 / 存查 |
| `assign_status` | AI ＋主管 | 歸屬 | none / unclaimed / assigned |

要加的「完成度」是**第四個維度，擁有者是當責人本人**。

### 1.2 ⚠️「已簽核」不是「已完成」——這個混淆要先擋掉

看板第三欄叫「已簽核」，很容易被讀成「這件事做完了」。
實際上它的意思是「**主管確認 AI 抽對了**」（`signoff.service.ts`：待簽核 → 已簽核）。

一張任務可以「已簽核」但工作根本還沒開始。
→ 完成度必須是**另一個欄位**，而且 UI 上要能一眼分辨這兩件事（§5 F-6）。

### 1.3 ⚠️ 不可複用 `tickets.status`

`status` 已經有 `resolved`。但——

> **AI 從對話讀到「修好了」≠ 本人回報完成。** 前者是推論，後者是承諾。

共用同一欄會有兩種壞事：
- materializer 重跑時 `status = EXCLUDED.status`，**把人回報的完成洗掉**
  （跟 `assigned_by` 保護是同一個坑）
- 或反過來：人標了完成，下次分析 AI 又把它改回 in_progress

→ **必須新增獨立欄位。**

### 1.3b ⭐ 「當成一條生命週期」的後果已經寫在程式碼裡了

`personal-daily-report.controller.ts`：

```sql
WHERE assignee_user_id = ${user.user_id}::uuid
  AND confirm_status IN ('待簽核', '逾時警示')
```

**主管一簽核，任務就從當責人的清單消失。**
但簽核＝「AI 抽對了」，不是「工作做完了」——
負責的人在「這被確認是一件真任務」的那一刻失去了它。

這正是把四條軸當成一條串接的結果：
把簽核當成流程的下一步，於是簽完就從當責人手上拿走。

**四條軸的擁有者不同**：

| 軸 | 擁有者 | 生命週期 |
|---|---|---|
| 抽取狀態 `status` | AI | open → in_progress → resolved／info |
| 簽核 `confirm_status` | 主管 | 待確認 → 待簽核 → 已簽核（或 存查／已忽略）|
| 歸屬 `assign_status` | AI＋主管 | none → unclaimed → assigned |
| **工作 `work_status`（本案要加）** | **本人** | **open → done／dropped** |

真正像「生命週期」的只有第四條 —— 前三條描述的是
「這張卡片被系統與管理者怎麼處理」，不是「這件事做到哪」。

把它們**當成一條鏈來存**會錯在：
- 一件事可以**還沒簽核就先做完**（同仁本來就在做，主管兩天後才簽）
- 也可以**簽核了永遠沒人做**（prod 現在就有 7 張躺了 4–5 天）
- 簽核的人與做事的人**不是同一個人**，串接等於規定「主管沒簽你不准做完」

→ M2 的範圍因此擴大：**任務要留在當責人手上直到他標完成，而不是直到主管簽核**（§7 M2）。

#### ⚠️ 但「不能串接」這個說法太絕對 —— 競品研究打臉了它

本文 v0.2 原本寫「四條軸只能並行，**不能串接**」。這是錯的，反例很硬：

**Jira Service Management 的簽核就是串在工作流裡的** —— approval step 綁在某個 status 上，
approve／decline 是兩個 transition，簽核前任何人都不能轉場。ServiceNow 也一樣。
兩者都是成熟、廣用、運作良好的產品。

但拆開看：**ServiceNow 把簽核放在獨立的 `sysapproval_approver` 表**，
一筆變更可掛多筆各有自己 state 的簽核 —— **前台那條鏈是投影，不是真相**。

> **修正後的結論：儲存分軸，呈現可以合成一條。**
> 分開存（不同 owner、不同 audit、不同指標），UI 可以投影成單一動線給現場主管看。
> 原本的表述把「儲存」和「呈現」混在一起講了。

**還有一筆漏算的帳**：四軸全正交 ＝ 3×3×3×3 ＝ **81 種組合，大多數無意義**。
Jira 的解法是加**跨軸約束**（resolution 不得出現在非 Done 狀態）。

→ 需要補的是一份**非法組合清單** ＋ 一個推導出**單一對外顯示狀態**的函數（§4.3），
而不是把四個下拉並排丟給現場主管看。

（理論依據：Harel statechart 的 orthogonal region —— N 個面向各 M 個狀態，
攤平成單一 FSM 要 M^N 個狀態，用平行 region 則是線性成長。詳見競品研究 §4.7）

### 1.4 任務↔日報的連結目前「有資料、無模型」

`PersonalDailyReportItem` 的型別只有 `{ time, title, detail, followup }`——**沒有 `ticketId`**。

而「加入日報」時前端有塞 `ticketId` / `source`，`saveFinal` 是
`JSON.stringify(finalItems)` 直接進 jsonb、**沒有 schema 驗證**，所以資料存得下來。

→ 要做追蹤就得把它正式化（否則沒辦法從日報回推是哪張任務）。

### 1.5 `due_at` 全是 null，所以現在做不了逾期

抽取 schema 根本沒有時間欄位（`calendar-sync.md` 卡住的同一件事）。
→ v1 用「開了幾天」代替，不做逾期（OQ-TCT-7）。

## 2. ⭐ 核心主張：預設繼續，只有完成需要動作

用戶的流程寫「未完成 → 每天追蹤」。若照字面做成「每天要人更新狀態」，
以 prod 現況（指派 0 次、簽核 0 次）判斷，**那個動作不會發生**。

所以把流程反過來設計：

```
指派 → 自動進入「進行中」 → 不做任何事就一直是進行中（成本 0）
                          → 做完那天點一下「完成」（一次點擊）
```

**未完成不需要任何人做任何事。** 系統自己知道哪些還開著、開了幾天。
同仁只在真的做完時付出一次點擊。

> 這是 `four-features-reflection` §7 的直接應用：
> 向同仁要的每一個動作都要有回報，而**能不要的動作就不要要**。

### 2.1 ⭐ 但只給一顆「完成」鍵還是會沒人按 —— 要有低承諾的中間動作

競品**外勤筋斗雲**把外勤人員的動作拆成兩顆按鈕：

| 按鈕 | 效果 |
|---|---|
| **回報** | 更新進度，**留在「進行中」** |
| **結案** | 才轉「已完成」 |

這正面解掉 F-1 背後的真正機制：

> **員工不敢按完成，所以乾脆什麼都不動。**

「做完了嗎」是一個**帶承諾**的問題 —— 按下去等於背書。
只給一顆完成鍵，不確定的人的最佳策略就是不碰它。
給一個低承諾的動作，狀態才會被維護。

**對我們尤其重要**：AI 從對話抽出來的任務**本來就常是半成品**，
強迫二選一（做完／沒做完）本身就不合理。

→ 修正 §2 的流程：

```
指派 → 進行中 → 什麼都不做：一直是進行中（成本 0）
              → 有進展：點「回報進度」+ 一句話（留在進行中，低承諾）
              → 做完了：點「完成」（一次點擊，有承諾）
```

「回報」同時給我們一個**免費的訊號**：有人在跟這件事，
只是還沒好 —— 這正是 §5 F-7「久懸」要分辨的東西。

## 3. ⭐ 日報與任務要分開，不要每天複製

若未完成任務每天塞進日報項目，一件做兩週的事會出現在 **14 份日報**裡，
把「今天真正做了什麼」埋掉。

| | 是什麼 | 性質 |
|---|---|---|
| **個人日報** | 今天做了什麼 | 一次性、當天有效 |
| **我的任務** | 這些事現在到哪 | 持續狀態、跨日 |

→ 日報頁**上方**顯示「你手上的任務（N 件進行中）」，
**不自動寫進日報內容**。完成時可以選擇「順便寫進今天的日報」，但那是選項不是預設。

## 4. 資料模型

### 4.1 ⭐ 「結束了沒」與「為什麼結束」要拆兩欄（Jira resolution 模型）

v0.2 原本設計 `work_status IN ('open','done','dropped')`。**這是錯的** ——
把「結束了沒」跟「為什麼結束」壓在同一欄，以後每多一種結束理由就要多一個狀態。

Jira 官方對 resolution 的說法正是這件事：
「指定議題被關閉的原因，**免除為了說明關閉原因而開多個狀態的需要**」。
不分開的後果社群叫 **resolution chaos** —— Done／Resolved／Fixed／Won't Fix 全變成狀態。

```sql
ALTER TABLE tickets
  -- 軸本身：只回答「結束了沒」
  ADD COLUMN work_status text NOT NULL DEFAULT 'open'
    CHECK (work_status IN ('open', 'closed')),

  -- 結束原因：open 時必須為 null，closed 時必須有值（§4.2 約束）
  ADD COLUMN work_outcome text
    CHECK (work_outcome IN ('完成', '不用做了', '轉他人', '做不到')),

  -- ⚠️ 誰標的 ≠ 當責人是誰。代標是必然不是例外（F-5 / C-5）
  ADD COLUMN work_closed_by uuid REFERENCES users(user_id) ON DELETE SET NULL,
  ADD COLUMN work_closed_at timestamptz,
  ADD COLUMN work_note text,                     -- 結束時的一句話（選填）

  -- 最後一次「回報進度」（§2.1）· 有值代表有人在跟，只是還沒好
  ADD COLUMN work_last_report_at timestamptz,
  ADD COLUMN work_last_report_note text;
```

⚠️ **照 Atlassian 的警告：禁止建立語意為「未完成」的 outcome 值。**
Jira 有人建了叫 `Unresolved` 的 resolution，結果那些票全被系統當成已解決。
「還沒結束」要用 `work_status='open'` 表示，**不是**一個叫「未完成」的 outcome。

**`完成` 與 `不用做了` 都讓任務結束，但完成率的分母必須排除後者**（Linear 的做法）——
否則「取消一堆」會被算成「做完一堆」。

### 4.2 跨軸約束（避免 81 種組合裡的無意義狀態）

```sql
-- 結束了就必須說為什麼；沒結束就不能有結束原因
ALTER TABLE tickets ADD CONSTRAINT work_outcome_matches_status CHECK (
  (work_status = 'open'   AND work_outcome IS NULL AND work_closed_at IS NULL) OR
  (work_status = 'closed' AND work_outcome IS NOT NULL AND work_closed_at IS NOT NULL)
);
```

這是 Jira「resolution 不得出現在非 Done 狀態」的同一招。
**沒有這條約束，第一個忘記寫 outcome 的路徑就會製造出永遠算不出來的票。**

其餘跨軸規則（不寫成 DB 約束，因為合法但需要在 UI 講清楚）：

| 組合 | 合法？ | UI 要怎麼講 |
|---|---|---|
| `status=resolved` ＋ `work_status=open` | ✅ 常見 | 「**AI 判讀為已完成，當責人尚未確認**」（ITIL 的 resolved vs closed）|
| `confirm_status=待簽核` ＋ `work_status=closed` | ✅ 合法 | 同仁本來就在做、主管還沒簽。**不可阻擋** |
| `assign_status=unclaimed` ＋ `work_status=closed` | ⚠️ 可疑 | 沒人認領卻有人結案 → 記錄 `work_closed_by`，不擋 |

### 4.3 ⭐ 對外只顯示一個狀態（投影函數）

四個下拉並排丟給現場主管 = 沒人看得懂。**存四軸，但算出一個字給人看**：

```ts
// 單一事實來源。看板、日報、LINE 卡片都吃這一個函數，不各自 if-else。
export function displayState(t: Ticket): string {
  if (t.work_status === "closed")
    return t.work_outcome === "完成" ? "已完成" : `已結束（${t.work_outcome}）`;
  if (t.confirm_status === "待確認")            return "待確認是不是任務";
  if (t.assign_status !== "assigned")           return "待指派";
  if (t.status === "resolved")                  return "AI 判讀已完成 · 待當責人確認";
  if (t.work_last_report_at)                    return "進行中（有回報）";
  return "進行中";
}
```

> 這就是 §1.3b 講的「**儲存分軸、呈現合成一條**」。
> ServiceNow 前台那條鏈也是投影 —— 底下是獨立的簽核表。

### 4.4 其他

- **`work_status` 與 `status` 是兩件事**：前者是人回報的，後者是 AI 讀到的（§1.3）
- materializer 重跑時 **所有 `work_*` 欄位一律不覆寫**（比照 `assigned_by`）

日報 item 型別補上連結：

```ts
export interface PersonalDailyReportItem {
  time?: string; title: string; detail?: string; followup?: string;
  ticketId?: string;                       // 來自哪張任務（原本只存在 jsonb 裡，沒有型別）
  source?: "attendance" | "assigned_task" | "ai" | "manual";
}
```

## 5. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **F-1** | 採用 | 沒有人按「完成」→ 全部任務永遠開著，「進行中」變成一個只會長大的清單 | **功能空轉** | **P0** | §2 預設繼續、完成才需動作 · 上線後量測「完成率」，低於門檻就回頭改設計而不是催人 |
| **F-2** | 覆寫 | 重跑分析把人回報的完成狀態洗掉 | **人的回報被 AI 蓋掉** | **P0** | `work_status` 不在 UPSERT 的更新清單裡 · 加測試斷言 |
| **F-3** | 語意混淆 | 使用者把「已簽核」當成「已完成」 | 以為做完了其實沒有 | **P1** | 兩者在 UI 上分開呈現、用詞不重疊（簽核／完成）· §1.2 |
| **F-3b** | 串接 | 把四條軸串成一條狀態機（待簽核→已簽核→完成） | **簽核後任務從當責人手上消失**（現況即如此） | **P1** | 四條軸並行不串接（§1.3b）· M2 改掉那句查詢 |
| **F-4** | 誤標 | 標錯完成後無法還原 | 事情被遺漏 | **P1** | 完成可還原（改回進行中）· 記錄誰標的、何時標的 |
| **F-5** | 代標 | 主管代標完成，但當事人其實沒做 | 資料失真、KPI 被灌水 | **P1** | **代標是必然不是例外**（Jira 的 Only-Assignee 是 opt-in、Asana 根本沒這權限）· 允許但**記錄 `work_closed_by`**，且 `work_closed_by ≠ assignee` 時 UI 明示「由 ○○ 代為結案」· 抄釘釘：代結在當責人清單裡是**獨立狀態**（「被創建人結束」）**不是同一個 ✅**，這是日後「你說我沒做」爭議時唯一的證據 |
| **F-6** | 噪音 | 未完成任務每天塞進日報 → 日報被舊事淹沒 | 日報失去「今天」的意義 | **P1** | §3 分開呈現 · 不自動寫入 |
| **F-7** | 久懸 | 任務開了 60 天沒人動，也沒人發現 | 靜默遺漏 | **P1** | 「開了幾天」在卡片上顯示 · 主管端可依天數排序 · **但不做自動催辦通知**（OQ-TCT-8） |
| **F-8** | AI 自動完成 | AI 從對話讀到「好了」就自動標完成 | **系統說做完了但其實沒有** | **P0** | **不做**（OQ-TCT-3）· AI 至多提示「這件事看起來完成了？」由人確認 |
| **F-9** | 隱私 | 主管看得到別部門同仁的任務進度 | 越權 | **P1** | 沿用既有部門 RLS，不另開查詢路徑 |
| **F-10** | 統計 | 「完成率」被當成績效指標 | 同仁亂點完成 | P2 | 這是管理決定不是技術 · 但**不主動做排行榜**（同 §7 F-6 的理由） |
| **F-11** | 完成 gate | 為了憑證而強制「沒拍照／沒填表就不能結案」 | **關不掉的任務**（技術依賴一失敗任務就永遠開著）· 直接放大 F-1 | **P1** | **v1 不加任何硬性 gate**（C-6）· 競品實證：業務王「畫面一直轉圈圈」、筋斗雲 FAQ 兩題都在處理「開了權限還是無法上傳照片」 |
| **F-12** | 曝光 | LINE 端的任務確認／認領提示**全群可見** | 等於 **AI 在群裡公開點名誰該做事** · 這是導入被推翻的典型死法 | **P1** | 抄釘釘智慧待辦的可見性規則（C-7）：只推給**發話者＋被指認的當責人**；`@所有人` 的訊息不出任務提示；給**個人層級**關閉開關（不是管理員層級）|

## 8. 這個功能會不會被用：先看這三個數字

上線前就該知道自己在賭什麼。目前 prod：

| 指標 | 現況 | 為什麼相關 |
|---|---|---|
| 任務被指派 | **0 次** | 沒有指派就沒有人「手上有任務」 |
| 簽核動作 | **0 次** | 主管還沒開始進任務看板 |
| 日報送出率 | **19%**（16 份僅 3 份） | 完成按鈕預計放在日報頁 |
| LINE 綁定 | **4/42** | 沒綁定就沒有「本人」可以標完成 |

**四個數字都指向同一件事：客戶還沒真的開始用。**

→ 這個功能做出來大概率一開始也是 0。**那不代表設計錯，但代表不該為它加更多東西**
（催辦、統計、排行榜都先不要）。先做最小的一顆按鈕，看有沒有人點。
