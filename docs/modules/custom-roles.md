## 0. 三句話結論

1. **可以做，而且比 v0.2 預估的便宜一個數量級** —— 因為「範圍」與「能力」兩條軸

## 2. `role` 現在同時扛兩件事

### 2.1 兩條軸被壓在同一個欄位裡

| 軸 | 決定什麼 | 現在靠什麼實現 |
|---|---|---|
| **範圍（scope）** | 這個人**看得到哪些資料列** | **RLS 裡的角色字串比對**（`app.actor_role`）|
| **能力（capability）** | 這個人**能做哪些動作** | 權限碼 · **已有 102 個端點在用** |

能力那一軸其實**已經現代化了**（102 個端點吃權限碼，只剩 16 個用 `@Roles`）。
問題全部集中在範圍那一軸。

### 2.2 直接放寬四層會造成越權（P0）

`tickets` 的 RLS policy（prod 現況）：

```sql
tenant_id = current_tenant
AND ( current_setting('app.actor_role') IS DISTINCT FROM 'group_owner'
      OR department_id = current_setting('app.current_department')::uuid )
```

**部門隔離只對字面字串 `'group_owner'` 生效。** 而 `app.actor_role` 是把 JWT 的
`user.role` 原封不動塞進去的（`tenant.interceptor.ts:18` → `db/client.ts:41`）。

所以若現在就讓自訂角色可指派：建一個「助理」只勾 2 個權限（**看起來非常受限**）→
指派給某人 → 他的 `app.actor_role = 'assistant'` **不等於 `'group_owner'`** →
RLS 讓他看見**全租戶所有部門的任務**。

> 這條 policy 是「**列舉誰要被限制**」的寫法。每多一個角色，
> 它就自動落在「不被限制」那一側 —— **預設開放，不是預設關閉。**

### 2.3 ⭐⭐ 這個寫法現在就已經在漏（與自訂角色無關）

同一條 policy 代表 **`employee` 現在就看得到全租戶的任務** —— prod 有 **8 個** 這種帳號。
目前擋住他們的只有 API 層的權限碼（`employee` 只有 2 個權限），**RLS 這一層是敞開的**。

**這是既有缺口，不是新功能帶來的。** 它是本份 doc 唯一該立刻處理的東西（§5）。

## 3. ⭐ 巨人的肩膀：v0.1 的提案是錯的

v0.1 提議在 `roles` 表加一欄 `data_scope`（`platform` / `tenant` / `department`）。
查了 Kubernetes RBAC 之後確認 **那是一個已知的錯誤形狀**。

### 3.1 Kubernetes：scope 在「綁定」上，不在「角色」上

K8s 的 `Role` / `ClusterRole` **只宣告「對什麼資源做什麼動作」，完全不宣告作用範圍**。
範圍由 `RoleBinding` 決定 —— 同一份 `secret-reader` ClusterRole，
綁到哪個 namespace 就只在那裡生效，角色定義一個字都不用改。

**它避開的正是 v0.1 會踩的三個坑：**

| 坑 | v0.1 的後果 |
|---|---|
| 角色要在 N 個範圍用就得複製 N 份 | 「部門主管」用在 12 個部門 → 12 份角色定義，改權限要改 12 次，必然 drift |
| 同一人無法在不同範圍有不同角色 | 「在 D2 是主管、在 D5 是員工」表達不了（`users.role` 單欄也表達不了）|
| 角色定義與組織結構耦合 | 部門改組要改角色表 |

### 3.2 K8s 的另外兩條可直接搬

- **純加法，沒有 deny 規則。** 官方理由（sig-auth maintainer 在 issue #85963）：
  deny 讓 API 無法安全演進 —— 「`*` 減去某物」預設你已知道 `*` 包含什麼，
  但未來新增的資源可能和被排除的一樣強大，於是每次升級都要稽核所有新資源 × 所有 deny 規則。
  **換來**：判定可交換、無優先序衝突、找到任一條 allow 即可短路。
- **防提權在「寫入時」擋，比對請求者當下的有效權限。**
  建/改 Role 時你必須已擁有該 Role 內含的**所有**權限（否則需 `escalate` verb）；
  建/改 Binding 時你必須已擁有即將授出的所有權限（否則需 `bind` verb）。

### 3.3 修正後的形狀（**若將來要做**）

```sql
roles(role_id, tenant_id NULL, role_key, role_name, is_system)   -- 只宣告「能做什麼」
role_permissions(role_id, permission_id)
user_role_assignment(user_id, role_id, scope_type, scope_id)     -- 宣告「在哪裡」
```

平台管理員 ＝ `(admin, platform, NULL)`；租戶管理員 ＝ `(admin, tenant, X)` ——
**同一個 role**，差別只在 assignment。自訂角色天然就有資料範圍了，
**因為範圍根本不是它的屬性。**

RLS 對應改成：session variable 不再放角色字串，改放
`app.scope_level` ＋ `app.allowed_dept_ids`（該 user 本次 request 所有 assignment 的聯集）。
**RLS 比對 ID 集合，從此新增角色不動 policy。**

> ⚠️ **`scope_type` / `scope_id` 絕不可由 client 傳入**，必須 server 端從 JWT 推導。
> 否則就是 memory `pitfall_permission_code_is_not_tenant_boundary` 那個坑的原形重演。

## 4. ⭐ 建議：這個功能現在不要做（**v0.2 的裁定 · 已於 v0.3 解凍**）

### 4.1 一線產品的實際做法

| 產品 | 自訂角色 |
|---|---|
| **Linear** | **至今沒有**（只有 5 個固定角色）|
| **Notion** | **沒有**（Enterprise 只多群組層的資源授權，不是角色）|
| **Figma** | **沒有** |
| **Vercel** | **沒有真正的自訂角色**（Enterprise 只給 extended permissions ＋ 專案層指派）|
| **Slack** | Enterprise Grid 才有 · 公司成立 **8 年後**（2021）· 蓋成獨立 Go 服務 ＋ gRPC ＋ 相容雙寫 |
| **GitHub** | repo 層 2021、**組織層 2023 才 GA** · 限 Enterprise Cloud · 上限 20 個 |
| **GitLab** | 自訂管理員角色 **2025-08 才 GA** |

**一線產品是「固定角色撐 8～10 年」，自訂角色是 Enterprise 檔次的變現功能，
不是產品早期的基礎建設。**

它們在沒有自訂角色時怎麼滿足「我要一個只能做 X 的人」？
**加「範圍」維度，而不是讓客戶自組權限包** —— Guest 角色、資源層分享、per-project 權限。

### 4.2 動手判準（滿足任一才做）

| # | 判準 | 我們現況 |
|---|---|---|
| 1 | ≥3 家租戶提出**互不相同**的角色切法（一家 ＝ 加內建角色就好）| ❌ 1 家 |
| 2 | 出現在**採購／資安稽核清單**（SOC 2、ISO 27001、招標規格）| ❌ 無 |
| 3 | 內建角色數量**超過 8** 或出現「XX 部門專用」這種租戶特化角色 | ❌ 5 個 |
| 4 | 客戶因為角色問題**擋住付款或續約** | ❌ 無 |

**命中 0 / 4。** 客戶總共 19 個帳號。

> **2026-08-21 重測（v0.3）**：判準 #1 命中**第 1 家**（用戶轉述客戶需求），
> #2 #3 #4 仍為否（內建角色仍是 **6 個**）。**嚴格說 1/4 還沒達標。**
>
> 之所以仍決定解凍，是因為 §6 發現**實作成本比 v0.2 預估低一個數量級**
> —— 當初「不做」的理由是「代價高 × 需求不明」，現在代價那一半塌了，
> 只剩需求不明。所以 **OQ-CR-7（客戶到底要哪個角色）變成唯一的 gate**（§10 M0.5）。

### 4.3 為什麼「先做起來放著」在這裡特別貴

§2.2 已經證明：這個功能的每一個 P0 都出自「開放任意建角色」這個前提。
不開，那四個 P0 就不存在。而現在做的話，我們是**在猜**客戶想要的切法 ——
等第 3 家客戶提出需求時，才會知道真正的形狀，那時再做反而更準。

## 5. ⭐ 現在該做的三件事（v0.2 提案 · **三件都已完成**，見 §6.1）

### 5.1 安全修正（**與自訂角色無關，建議立刻做**）

把 `tickets` 的 RLS 從「列舉誰要被限制」改成**正向、fail-closed**：

```sql
-- 現在（預設開放）
AND (current_setting('app.actor_role', true) IS DISTINCT FROM 'group_owner'
     OR department_id = ...)

-- 改成（有設部門就限縮 · 預設關閉）
AND (nullif(current_setting('app.current_department', true), '') IS NULL
     OR department_id = nullif(current_setting('app.current_department', true), '')::uuid)
```

`app.current_department` **本來就已經在設了**（`db/client.ts:42`），這不是新機制。

**prod 驗算（改完誰會變）：**

| 角色 | 帳號數 | 有掛部門 | 改後 |
|---|---|---|---|
| `tenant_admin` | 7 | **0** | 不變（看全租戶）|
| `aiproot_admin` | 1 | **0** | 不變 |
| `group_owner` | 3 | **3** | 不變（只看自己部門）|
| `employee` | 8 | 3 | **3 個從「看全租戶」收斂成「只看自己部門」** ＝ 修正 |

> ⚠️ 另外 5 個沒掛部門的 `employee` 仍看得到全租戶 —— 見 OQ-CR-3。

### 5.2 「助理」升格為第 6 個內建角色

客戶要的是**一個具體角色**，不是一個角色工廠。把 `assistant` 轉成
`is_system = true`、沿用它現有那 2 個權限碼，加進 `users_role_check`、DTO enum 與前端下拉。

**一個 migration ＋ enum 加值 ＋ 下拉多一項**，客戶需求 100% 滿足，**不引入任何 P0**。
這正是 Linear / Figma 的做法。客戶建的東西**變成真的能用**，而不是被刪掉。

### 5.3 把「新增角色」入口收起來

`RolesManagement` 的「＋ 新增自訂角色」目前讓人完成一個到不了任何地方的動作。
改成 aiproot-only ＋ 註明「新增角色請聯繫 AIPROOT」，
**保留「調整既有角色的權限碼」** —— 那部分是可用的，也是最常見的真實需求。

| §5.3 新增角色入口收成 aiproot-only | ✅ **已上線** | 租戶端只有「請聯繫 AIPROOT」提示（`styles.css:2343`）|

⚠️ **§2.2 那個 P0 已經不存在了。** 現在的 policy 是：

```sql
tenant_id = current_tenant
AND (current_department IS NULL OR department_id = current_department)
```

不再比對角色字串。**但判斷點只是搬到了 TypeScript**：

```ts
// tenant.interceptor.ts
const DEPT_SCOPED_ROLES = new Set(["group_owner", "employee"]);
```

自訂角色不在這個集合裡 → `current_department = null` → 看得到全租戶的任務。
**同一個「列舉誰要被限制」的形狀，換了個檔案。** 這是 v0.3 要處理的真正缺口。

### 6.2 38 條 RLS policy 的形狀普查

| 形狀 | 條數 | 自訂角色落在哪一側 |
|---|---:|---|
| A · 平台逃生門（`app_is_platform_ops()`）| 6 | ✅ 不匹配 → 擋住 |
| C · 平台逃生門（字串白名單 `IN (aiproot_admin, consultant, system)`）| 29 | ✅ 不匹配 → 擋住 |
| D · 用 `current_department` 變數（新形狀）| 1 | ⚠️ 沒帶部門 → **看全租戶** |
| E · 純租戶隔離 | 2 | ✅ 擋住跨租戶 |
| **B · 列舉誰被限制（v0.2 的 P0 形狀）** | **0** | — |

**B ＝ 0 是本次最重要的發現。** v0.2 說「每多一個角色就自動落在不被限制那側」——
那條敘述今天已經不成立。

⭐ **所以自訂角色今天的實際風險輪廓是：**

| | 結果 |
|---|---|
| 跨租戶 | ✅ **擋得住** —— `tenant_id` 那層在 35 條裡都是無條件的 |
| 平台資源（通知規則、Ragic 金鑰）| ✅ **擋得住** —— 白名單不含自訂角色 |
| 個人日報 | ✅ 只看得到自己（`personal_daily_report_scope` 有正向 scoping）|
| **租戶內的任務／訊息／成員／素材** | ❌ **全部看得到** |

不是跨租戶外洩，是**租戶內沒有部門收斂**。嚴重度比 v0.2 描述的低，但仍是真問題 ——
一個叫「品保組長」的角色，客戶會預期他只看品保部。

### 6.3 ⭐⭐ 兩條軸其實已經分開了（v0.2 沒發現）

§2.1 說「範圍與能力被壓在同一個欄位」。**今天不是這樣了。** 權限解析的實際 SQL：

```sql
-- permission.service.ts:36
LEFT JOIN role_permissions rp ON rp.role_id = COALESCE(
  u.role_id,                                                    -- ← 先看外鍵
  (SELECT r.role_id FROM roles r WHERE r.role_key = u.role AND r.is_system)
)
```

| 欄位 | 決定什麼 | 誰在用 |
|---|---|---|
| `users.role`（text · CHECK 鎖 6 值）| **資料範圍** → `app.actor_role` | 35 條 RLS policy |
| `users.role_id`（uuid · FK）| **能做什麼** → 權限碼 | 127 個 `@RequirePermission` 端點 |

這是 `0067`（租戶自管權限）的 fork-on-edit 機制順帶造成的結果 ——
分岔時只改 `role_id`、`role` 原封不動。**沒有人是為了自訂角色設計它的，但它剛好就是對的形狀。**

### 6.4 「建角色」不是缺口，「指派」才是

`createRole` **後端早就存在**（`permission.controller.ts:49`，`@RequirePermission("roles:manage")`，aiproot-only），
而且建得出帶 `tenant_id` 的租戶角色。權限管理頁也已經寫著「請聯繫 AIPROOT 並說明這個角色要做哪些事」。

缺的是三件：

1. **指派不了** —— `assignableRolesFor` 硬編內建角色清單；`users.role_id` 沒有任何 UI 寫得到
2. **範圍講不清** —— 建出來的角色沒有宣告它該看全租戶還是單一部門
3. **沒有防提權** —— 誰都能把自己沒有的權限放進新角色（K8s 的 `escalate` 那條紀律，§3.2）

## 7. ⭐ v0.3 設計

### 7.1 三個方案

| | 方案 A · 基準角色 | 方案 B · `roles.scope_level` | 方案 C · 完整 assignment（§3.3）|
|---|---|---|---|
| 形狀 | 自訂角色只給能力；範圍沿用 `users.role` 的 6 個基準值之一 | 角色自己宣告 `tenant` / `department` | `user_role_assignment(user_id, role_id, scope_type, scope_id)` |
| 要改 RLS | **0 條** | 0 條 | **35 條** |
| 要改 `users_role_check` | **不用** | 不用 | 不用（改走 assignment）|
| 一人在不同部門有不同角色 | ❌ | ❌ | ✅ |
| 新增角色要不要動 policy | 不用 | 不用 | 不用 |
| 估計工作量 | **小**（M1–M3）| 小＋ | **大**（跨 35 條 policy 的資料存取模型變更）|

### 7.2 ⭐ 建議：方案 A

**自訂角色 ＝ 一組權限碼 ＋ 一個「資料範圍基準」。**

```
建立角色「品保組長」
  ├─ 能做什麼：勾權限碼（沿用 0067 已經在用的那份目錄）
  └─ 看得到什麼：選一個基準 →  ○ 只看自己部門（同「部門主管」）
                              ○ 看全公司（同「總經理室」）
```

落地成資料就是：

```sql
users.role     = 'group_owner'      -- 基準：決定 RLS 範圍（35 條 policy 照舊）
users.role_id  = <品保組長的 role_id> -- 能力：決定 127 個端點放不放行
```

**為什麼這是對的形狀而不是偷懶**：§3.1 批評 v0.1 的 `data_scope`，理由是
「角色要在 N 個範圍用就得複製 N 份」。方案 A **沒有這個問題** ——
它放在角色上的是**範圍層級**（部門／全租戶），不是**範圍實例**（哪一個部門）。
哪一個部門仍然來自 `users.department_id`。K8s 的三個坑，方案 A 避開兩個，
第三個（一人多範圍）留給方案 C，等真的有人要求再說（OQ-CR-9）。

**為什麼不直接做 C**：C 要改 35 條 policy 的比對方式，那是**資料存取模型的置換**，
不是加功能。在只有 1 家客戶提出需求時做那個，是 §4.3 警告過的「在猜切法」的加強版。
而方案 A 若將來要升級到 C，`roles` / `role_permissions` 兩張表完全不用動 ——
**A 是 C 的真子集，不是死路。**

### 7.3 防提權（K8s §3.2 那條，必做）

寫入時比對請求者當下的有效權限：

```
建立／修改角色時，permissionIds ⊆ 請求者自己的有效權限集合
指派角色給人時，  該角色的權限   ⊆ 請求者自己的有效權限集合
```

沒有這條，`tenant_admin` 可以建一個含 `tenants:onboard` 的角色再指派給自己 ＝ 自我提權。
**這條在 server 端做，不是前端隱藏**（前端只送得出看得到的，但會改請求的人不受限）。

同時：可選的權限目錄沿用 `0067` 的 `TENANT_VISIBLE_SCOPES`（只有 `tenant` / `department` 級），
**platform 級 34 項不回傳**（不是灰掉，是不回傳）—— 這條 v0.2 已經驗證過，直接沿用。

### 7.4 基準角色的可選範圍

租戶建角色時，「資料範圍基準」**不可以選 `tenant_admin` 以上**：

| 基準 | 租戶可選 | 理由 |
|---|:--:|---|
| `employee` | ✅ | 只看自己 |
| `group_owner` | ✅ | 只看自己部門 |
| `tenant_admin` | ⚠️ 見 OQ-CR-10 | 看全租戶 —— 給不給是業務決定 |
| `assistant` | ❌ | 平台角色 · 白名單含它 → 跨租戶讀通知規則與 Ragic 金鑰（2026-08-21 實證）|
| `consultant` / `aiproot_admin` | ❌ | 平台角色 |

⚠️ **`assistant` 絕對不可以當基準** —— 這是今天才確認的：`app_is_platform_ops()`
是純角色白名單、無租戶條件，而 `assistant` 在裡面。
細節見 memory `pitfall_platform_role_in_tenant_list`。

## 8. 失效場景反思（FMEA · R17）

### 8.1 v0.3（方案 A）的失效場景

逐路徑走：建角色 → 指派 → 登入 → 讀資料 → 改角色 → 刪角色。

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **V-1** | 建角色 | 建立者把自己沒有的權限放進去 → 指派給自己 ＝ 自我提權 | 租戶取得平台級能力 | **P0** | ✅ `assertWithinCallerPermissions` 於建立與指派兩處各擋一次 · 測試已用**破壞法實測**（拿掉守衛會轉紅）|
| **V-2** | 建角色 | 基準選了 `assistant` | **跨租戶**讀所有通知規則與 Ragic API 金鑰 | **P0** | ✅ service 白名單 ＋ **DB CHECK 兩層**（`0070`）· 已實測 `UPDATE ... baseline_role='assistant'` 被 constraint 拒絕 |
| **V-3** | 建角色 | `tenant_id` 沒帶 → 角色變成全平台可見 | 別家租戶看得到／用得到這個角色 | **P0** | ✅ `tenantOf(user)` 一律取自 JWT · 別家角色回 `role_not_found`（不洩漏存在與否）· 有測試 |
| **V-4** | 指派 | 只寫了 `role_id` 沒設 `role` 基準 | `app.actor_role` 是舊值 → 範圍不對（可能過寬）| **P0** | ✅ 兩欄同一句 UPDATE · 測試斷言兩欄一致 · **反方向**（換回內建角色要先清 `role_id`）在前端處理 |
| **V-5** | 指派 | 寫了 `role` 沒寫 `role_id` | 權限退回基準角色的 → 少權限、畫面全白 | P1 | 同上 · 這個方向是 fail-closed，比 V-4 安全 |
| **V-6** | 登入 | 權限有 5 分鐘 in-memory 快取 | 改完角色的人在 5 分鐘內行為不變，客戶以為沒生效 | P2 | ✅ 建立／改權限／指派／刪除四處都呼叫 `invalidateAll()` · ⚠️ **殘留**：UI 還沒提示「重新登入後生效」|
| **V-7** | 讀資料 | 基準 `group_owner` 但那個人沒有 `department_id` | `current_department = null` → **看全租戶**（不是看不到，是看太多）| **P0** | ✅ 指派時擋下並要求先指派部門 · 測試同時斷言「擋下來不可留下任何寫入」· 已用**破壞法實測** |
| **V-8** | 刪角色 | 刪了還有人在用的角色 | 那些人 `role_id` 變懸空 → 落回基準角色 | P1 | ✅ 後端擋 ＋ 前端確認框顯示「還有 N 位成員在使用」|
| **V-9** | 相容 | 既有 12 個帳號的 `role_id` 是 NULL | 走 `COALESCE` fallback 到內建角色 ＝ 行為不變 | — | ✅ 已是現況 · 空窗期安全（同 `0068` 的 DEFAULT 紀律）|
| **V-10** | 觀測 | 建／改／指派自訂角色沒進 `audit_log` | 事後查不出誰給了誰什麼權限 | P1 | ⚠️ **殘留** · `TenantTxInterceptor` 會記下 method+url+actor（涵蓋「誰在什麼時候呼叫了哪支」），但**不含 body**，所以查不到「給了哪些權限」· 治本＝寫結構化 audit 事件 |

> **V-1 / V-2 / V-3 / V-4 / V-7 未緩解不得上 prod**（R17）——
> **✅ 五個 P0 全部已緩解且有測試**，其中 V-1 與 V-7 另用破壞法實測過
> （把守衛拿掉，對應測試確實轉紅），不是「綠燈因為什麼都沒跑到」。
>
> ⚠️ **已知殘留兩項（皆 P1/P2，可忍）**：
> · **V-10 稽核不含 body** —— 查得到「誰呼叫了建立角色」但查不到「給了哪些權限」。
>   治本方向：寫結構化 audit 事件而不是只靠 interceptor 的 method+url。
> · **V-6 沒有「重新登入後生效」的提示** —— 權限有 5 分鐘快取，改完可能看起來沒動靜。
