> **一句話**：客戶要「任務先給部門主管、需要才給總經理」——
> 查下來**前半完全沒有**（主管在任務出現時收不到任何通知），

| 事件 | 現在通知誰 |
|---|---|

| 被接手 | 原本那位 |

**部門主管在任務出現時，收不到任何東西。** 他得自己想到要進系統看。

## 2. ⭐ 這跟 2026-07-29「AI 分派不主動推播」衝突嗎 —— 不衝突

`ticket-materializer.service.ts:127` 的註解寫得很清楚：

> ⚠️ 對到之後**刻意不發 LINE 通知**（2026-07-29 用戶裁定）。不是漏接，不要「修好」它。
> 理由：AI 判斷歸屬的準確度**從來沒有量測過**，而主動私訊是打擾人，
> **打擾錯的人比不打擾貴得多**。

**那條裁定管的是「通知 AI 猜出來的當事人」。** 本案不同：

| | 07-29 擋掉的 | 本案 |
|---|---|---|
| 通知對象怎麼決定 | **AI 推論**的當責人（`person` 欄位對主檔）| 群組 → 部門 → 主管，**每一層都是人設定的** |
| 會不會打擾錯的人 | 會（準確度未量測）| 不會（部門是確定的）|
| 內容 | 「這件事是你的」| 「你部門今天有 N 件事」|

⭐ **判準沒有變**：不打擾「可能不相干的人」。部門主管本來就該看自己部門的任務，
通知他不是打擾，是把他本來要做的事送到他面前。

## 3. 設計

### 3.1 ⚠️ 必須是每日彙總，不可以一張一則

台灣福祉 **572 張票 / 約 2 個月 ≈ 每天 10 張**。

一張一則的話：
- 主管一天收 10 則私訊 —— 那不是通知，是洗版
- LINE **push 訊息是計費的**（`line-api.client.ts:74`：「有 quota 計費」）
- 直接打破 `pageGuides` 對客戶承諾的「每天約 3 分鐘」節奏

所以：**一天一則**，內容是「您部門今天有 N 件事待確認」＋ 進系統的連結。

### 3.2 時機：排在批次分析之後

任務要先材料化出來才數得到。跟著 `scheduler-config` 的批次時間（客戶設 18:00），
**批次跑完再發**。

⚠️ 不可以用固定時間各跑各的 —— 批次還沒跑完就發彙總，數字是昨天的，
而使用者不會知道（同 `pitfall_setting_says_on_but_never_fired` 那一類：看起來有跑）。

### 3.3 「需要才給總經理」不用做

④「知會其他人」（`d8482da` `4bca96b`）已經上線：主管在任務詳情勾要一起通知的人，
各自收到 LINE 私訊。**主管勾總經理就是「往上報」。**

⭐ 不做自動審批鏈。理由：
- 審批鏈要定義「什麼情況該往上」—— 那是客戶的管理規則，不是我們該猜的
- 手動勾的版本已經能用，先看他們用不用得上

## 4. ⚠️ 這個功能很可能上線即無效

兩個前置條件，**任一不成立就完全不會發出任何東西**：

| 前置 | 現況 | 風險 |
|---|---|---|
| 部門要有 `role = 'group_owner'` 的人 | 沒有專屬欄位，是靠 `users.role` + `department_id` 查 | **0 個主管的部門 → 靜默沒人收到** |
| 那位主管要綁定 LINE | 任務 #29：群裡 56 人只有 12 個有系統帳號 | **沒綁 → push 無對象，靜默失敗** |

⭐ 這正是 memory `project_shipped_but_inert_features` 的形狀：
**跑了、沒報錯、什麼都沒發生。**

所以 M1 的驗收**不可以只看「沒有錯誤」**，必須：
1. 先查出「有幾個部門有主管、其中幾位綁了 LINE」的實際數字
2. 發送結果要寫 log／`notification_log`，**發不出去要留下痕跡**而不是靜默略過

## 5. 開放問題（OQ-MDG-N）

| # | 問題 | 建議 |
|---|---|---|
| **OQ-MDG-1** | 彙總要數什麼？「待確認 ＋ 待核對」還是只有其中一個？ | 建議**兩個分開列**：「N 件待判定、M 件待核對」· ⭐ 台灣福祉的痛點正好是待確認欄沒人看（見 twh-feedback §9.2）|
| **OQ-MDG-2** | 沒有任何待辦的那天要不要發？ | 建議**不發** · 天天收到「今天 0 件」會讓人開始忽略這個通知，真的有事的那天也一起被忽略 |
| **OQ-MDG-3** | 總經理室（`tenant_admin`）要不要也收一份全公司彙總？ | ⚠️ **需裁定** · 客戶原話是「需要才給總經理」—— 照字面是**不要**自動給。但他可能也想要一份自己的 |
| **OQ-MDG-4** | 一個部門有多位 `group_owner` 時，每個都發嗎？ | 建議**都發** · 他們都看得到那些任務 |
| **OQ-MDG-5** | 要不要給租戶開關（可以關掉這個通知）？ | 建議**要** · 放 `task_config`；但**預設開** —— 預設關等於沒做 |

## 7. 失效場景反思（FMEA · R17 · 草稿）

| # | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|
| **F-1** | 部門沒有主管 / 主管沒綁 LINE → 靜默什麼都沒發 | 客戶以為功能沒做 | **P0** | M0.5 先量數字 · 發送結果一律留痕，**發不出去要看得見** |
| **F-2** | 排在批次前面跑 → 數字是昨天的 | 主管照著錯的數字判斷 | P1 | 掛在批次完成之後，不用固定時間 |
| **F-3** | 一張一則 → 洗版 ＋ push 計費暴增 | 主管關掉通知 | P1 | ✅ 設計就是每日彙總（§3.1）|
| **F-4** | 天天發「今天 0 件」 | 通知被訓練成雜訊，真的有事那天也被忽略 | P1 | OQ-MDG-2 建議不發 |
| **F-5** | 批次重跑 → 同一天發兩次 | 打擾 | P1 | 每個 (部門, 日期) 只發一次，寫進 `notification_log` 去重 |
| **F-6** | 多部門同時發 → 短時間大量 push | 撞 LINE rate limit，後面的靜默失敗 | P1 | 依序發 ＋ 失敗留痕（不是 fire-and-forget，見 `pitfall_fire_and_forget_status_desync`）|
