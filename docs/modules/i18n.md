## 2. 五條軸，不是一個問題

「加英文」聽起來是一件事，實際上是**五件性質完全不同的事**：

| # | 軸 | 例子 | 語言由誰決定 | 難度 |
|---|---|---|---|---|
| **A** | **介面字串** | 側欄「任務看板」、按鈕「核對」 | 登入者的偏好 | 標準 i18n · 量大但直白 |
| **B** | **API 錯誤訊息** | 「尚未登入或工作階段已過期」 | 發請求的人 | 中 · 已集中在 `api.ts` |
| **C** | **LINE 推播文案** | 「@某某 有一件事指派給您」 | ⚠️ **收件人**（不是發起者）| 中 · 要 per-user locale |
| **D** | **AI 產出內容** | ticket 摘要「A1工位車輛更換：…」 | ⚠️ **來源對話的語言** | ⭐ **難 · 見 §3** |
| **E** | **DB 存的中文值** | `confirm_status = '待確認'` | — | ⚠️ **不可翻譯**（見下）|

### 2.1 ⚠️ E 是陷阱：DB 值長得像文案但它是資料契約

`tickets.confirm_status` 存的是中文字串（`待確認` / `待簽核` / `已簽核`…）。

`web/src/shared/confirmStatusLabel.ts` 的檔頭已經寫死了紀律：

> **比對一律用 DB 值，顯示一律走這支。**

⭐ 這對 i18n **反而是好消息** —— 顯示層早就抽出來了，
加英文只要在那張表加一欄，不用動 DB、不用 migration。

⚠️ 但也是**最容易做錯的地方**：把 `CONFIRM_STATUS_LABEL` 的 **key** 翻成英文，
全站狀態比對會靜默失效（同一支檔案已經記過這個警告）。

## 3. ⭐⭐ 結構性問題：UI 全翻完，主畫面仍有大半是中文

**這是這份 M0 最重要的一段。**

任務看板是使用者每天真正在用的畫面。一張卡片上有什麼：

```
┌────────────────────────────────────────────┐
│ A1工位車輛更換：DE中華傳愛#4492→DE長安長照#4403 │ ← AI 產出（中文對話抽的）
│ 技術工程 · 會議記錄 · 郁芬Sandra              │ ← 部門名/分類/人名（客戶資料）
│ [待核對]  [卡住 24 天]                       │ ← UI（可翻譯）
└────────────────────────────────────────────┘
```

**可翻譯的只有最後一行。** 前兩行是：
- **D 軸**：AI 從中文 LINE 對話抽出來的摘要
- **客戶主檔**：部門名、人名、群組名 —— 那是台灣福祉自己打的中文

> ⚠️ **一個英文使用者把 UI 切成英文之後，打開任務看板看到的
> 仍然是一整片中文。** 他看得懂的只有欄位標題和按鈕。

### 3.1 那 D 軸能翻嗎？

能，但代價完全不同：

| 做法 | 代價 |
|---|---|
| 讓 AI 直接輸出英文 | 改 prompt → **卡在 [`tenant-prompt-decoupling`](tenant-prompt-decoupling.md)**：目前**全租戶共用同一份 prompt**（`resolveTenant` 的 `batch` → `TWH_TENANT`），改了台灣福祉與鮮湧一起變 |
| 抽取時中英雙寫 | 每筆多一份輸出 → token 成本 ×N，且撞 [`≤16 union 上限`](meeting-decisions.md) 的風險 |
| 顯示時即時翻譯 | 每張卡一次 API 呼叫 · 成本與延遲都不可行 |
| **不翻** | 英文使用者看得懂框架、看不懂內容 |

⭐ **所以真正的問題是：這個英文使用者是誰、他要用這個系統做什麼？**
如果他只是要「看得懂這是什麼系統」（demo / 簡報 / 投資人 / 委員），
**A＋B 就夠了，D 完全不用碰**。
如果他是**要每天用它工作的人**，那 D 不解決等於沒做。

## 3-bis. ⭐ OQ-1 已裁定：使用者是**外籍主管**（2026-08-26）

這個答案把問題**收窄了，但也帶出一個必須先講的矛盾**。

### 3-bis.1 ⚠️ 他的核心工作，本質上需要讀中文

部門主管在這個系統裡每天做的事是**核對 AI 抽得對不對** ——
點開卡片、對照原始 LINE 對話、確認內容沒抽錯。

> **那件事需要同時讀懂 AI 摘要（中文）和原始對話（中文）。**
> UI 翻成英文不會讓他做得到。

所以要先對齊期待：**介面英文化給他的是「管理視角」，不是「內容視角」**。

| 他能做的（UI 英文化後）| 他仍做不到的 |
|---|---|
| 看儀表：這個月多少事、哪個部門卡住 | 讀懂任務卡在講什麼 |
| 看量：待核對幾件、逾時幾件 | 核對 AI 抽得對不對 |
| 部門／成員／權限／群組／排程 **設定** | 判定「請您判定」區那些事要不要追 |
| 指派任務給人（看得到人名與部門）| 讀原始對話 |

⭐ **如果他是「看管理面、核對交給在地主管」→ 這樣就夠了。**
**如果他自己就是要做核對的人 → 只做 UI 等於沒解決他的問題**（見 §3-bis.3）。

### 3-bis.2 範圍按**畫面**排，不是「外殼字串一律翻」

既然使用者是特定角色，就照他實際會開的畫面算（實測，非估算）：

| 畫面 | 條數 | 他用嗎 |
|---|---|---|
| 外殼（側欄／麵包屑／Toast）| 74 | ✅ 一定 |
| 總覽儀表 | 44 | ✅ 主要 |
| 任務看板（含存查／判定區／工作追蹤）| 155 | ✅ 主要 |
| 設定 · 部門/成員 | 149 | ✅ |
| 設定 · 權限管理 | 102 | ✅ |
| 設定 · LINE 群組 | 48 | ✅ |
| 設定 · 分析排程 | 57 | ✅ |
| 共用對照表（狀態／角色／分類）| 84 | ✅ 全站都吃 |
| API 錯誤訊息 | 34 | ✅ |
| **小計** | **747** | |
| ─────────── | | |
| 通知設定精靈 | 293 | ❌ 一次性建置，資訊窗口做 |
| 我的日報／行程 | 163 | ❌ 員工功能 |
| 素材 | 205 | ❌ 內容導向，翻了也看不懂內容 |

⭐ **747 條**，比「全前端 2,590 條」少 71%，而且是**一個完整可用的管理者視角**。

### 3-bis.3 若他自己要做核對：一個有界的 D 軸解法

§3 說 D 軸（AI 產出）的三種做法都很貴。但**使用者是人**這件事開了第四條路：

> **開卡時才翻譯**（on-demand）：他點開某張卡的詳情時，
> 才呼叫一次翻譯，把該卡的摘要與原始對話譯成英文。

| | 成本 |
|---|---|
| 抽取時雙寫 | 每天每筆都付 · 且卡 prompt 解耦、有 ≤16 union 風險 |
| 顯示時整頁翻 | 每張卡一次呼叫 · 不可行 |
| **開卡時才翻** | **他點幾次就付幾次** —— 主管一天開 10–30 張，成本可忽略 |

⭐ 關鍵優勢：**這條路不動抽取 prompt，所以不會波及鮮湧**
（[`tenant-prompt-decoupling`](tenant-prompt-decoupling.md) 那個 P0 繞開了）。

⚠️ 但它是**新的 LLM 呼叫路徑**，要自己的 M0（快取、失敗時顯示原文、
不可讓翻譯結果覆寫原始資料 —— R11 可溯源）。**建議列為 M7，不併進本批。**

## 5. 技術方案（做甲的話）

### 5.1 要不要引入套件

⚠️ CLAUDE.md §5.3：**新增第三方依賴要先問**。

| | 引入 `react-i18next` | 自己寫一個 `t()` |
|---|---|---|
| 複數／格式化 | ✅ 內建 | ⚠️ 要自己處理（本專案文案幾乎不需要複數，中文沒有複數變化）|
| 抽取工具 | ✅ 有 | ❌ 要自己寫 |
| 體積 | +40KB 左右 | ~50 行 |
| 與現況一致性 | — | ⭐ 本專案慣例是**手寫**（`StyledSelect`／`useDebounced`／`confirmStatusLabel` 都是）|

**建議：先手寫。** 理由不是省 40KB，是**這個專案的字串形狀很簡單**
（幾乎沒有複數、少量插值），而 `confirmStatusLabel.ts` / `roleLabel.ts` /
`categoryLabel.ts` **已經是三張現成的對照表** —— 那個 pattern 本來就在用了，
i18n 只是把它系統化。

⚠️ 若之後要做乙／丙（3,000+ 條、多語言），再評估換套件。

### 5.2 形狀（沿用既有 pattern）

```
web/src/i18n/
  ├─ zh-TW.ts      ← 現有中文（從各檔抽出來）
  ├─ en.ts
  ├─ index.ts      ← t(key) + useLocale()
  └─ (既有的 confirmStatusLabel / roleLabel / categoryLabel 併進來)
```

⭐ **併進來很重要**：現在有三張各自為政的對照表，
i18n 一旦另起爐灶就變四張，下次改狀態名要改四個地方。

### 5.3 語言從哪來

| 來源 | 用在 |
|---|---|
| `users.locale`（新欄位 · 預設 `zh-TW`）| 登入後的介面、LINE 推播（C 軸的收件人語言）|
| `navigator.language` | 登入頁（還沒有 user）|
| `Accept-Language` header | 後端 API 錯誤訊息（B 軸）|

⚠️ **加 `users.locale` 要 migration**（R1 破壞性修改需遷移計畫）。
給 `DEFAULT 'zh-TW'`，讓 migration → 部署的空窗期行為完全不變。

### M3.5b 補記：**同一條守門測試擋了三次，三種不同語法**

`ui-naming` 的「退休名字不可留在畫面上」打在 i18n 上三次，
每一次都是**規則的真陽性、對 i18n 的偽陽性**：

| # | 語法 | 什麼東西 |
|---|---|---|
| 1 | `待簽核: "待核對"` | 舊對照表的 key |
| 2 | `"confirmStatus.待簽核": "待核對"` | 字典的 key **定義** |
| 3 | `tr("confirmStatus.待簽核")` | 字典 key 的**引用** |

⭐ 分界永遠是同一條：**key 是識別字、value 才是文案。**
豁免每次都寫窄（第 3 條限 `t()`/`tr()` 呼叫內），不用萬用比對。

### ⚠️ M3.5b 修掉一個 tsc 抓不到的 hooks 違規

批次補 `useT()` 時把 `signedNote()` 也加了 —— 那是**純輔助函式不是元件**
（小寫命名、回傳 `string | undefined`、在 JSX 裡被呼叫）。

在裡面用 hook 違反 Rules of Hooks，而且**它一旦被條件呼叫就會壞掉 hook 順序** ——
tsc 全綠、build 全綠，要 runtime 才炸。

> **判準：`t()` 給非元件用、`useT()` 給元件用。**
> 補 hook 時要看函式名是不是大寫開頭，不能只看「它用到 tr 了嗎」。

---

⚠️ 途中被既有測試擋了三次，**每一次都是測試在正常運作**：
① 角色/分類一致性測試比對的是搬走前的位置 → 比對對象跟著搬
② 退休名字守門打在 i18n 的 **key** 上（`confirmStatus.待簽核`）——
   規則的真陽性、對這個檔的偽陽性（key 是識別字不是文案）→ `isDbLiteral` 補新寫法
③ 我順手加的四個零使用常數觸發同一條 → **刪掉，不為死碼開豁免**

### 5-ter. ⚠️ M4 的範圍比「API 錯誤訊息」窄

`api.ts` 的 `friendlyStatusMessage` 只是**通用 fallback**。
真正的流程是：**server 特意寫的訊息優先**，只有 Nest 預設英文才走 fallback。

所以像「這個角色的範圍是『只看自己部門』，請先幫這位成員指定所屬部門」
這種**後端寫的中文**，英文使用者仍然看得到中文。

要補齊得讓後端吃 `Accept-Language`（後端 ~1,080 條裡有 105 條屬這類）。
**列為 M4b，本批不做** —— 那些訊息多半出現在設定流程，
而外籍主管的主要動作是看儀表與任務。

| **OQ-I18N-4** ⭐ | AI 產出（D 軸）要不要碰？ | ⚠️ **取決於他自己做不做核對**（§3-bis.1）· 不做核對 → 不碰；要做 → **M7 開卡即時翻譯**（他點幾次付幾次、不動抽取 prompt、繞開鮮湧那個 P0），不要走抽取時雙寫 |
| **OQ-I18N-5** | LINE 推播（C 軸）要不要跟著做？ | 建議**先不做** · 收件人幾乎都是台灣員工 · 但 `users.locale` 先建好，之後接得上 |
| **OQ-I18N-6** | `handbook.html` / 驗收清單那些客戶文件要不要英文版？ | 建議**不做** · 那是台灣福祉專屬文件，讀者是中文使用者 |
| **OQ-I18N-7** | 要不要順便支援第三語言（日文？）？ | 建議**架構支援、內容不做** · 加一個 locale 檔的成本，跟一開始就寫死兩種差很多 |
| **OQ-I18N-8** | 中文字串是**留在原地標記**還是**全部搬進 locale 檔**？ | 建議**全搬** · 留在原地會讓「哪些翻了哪些沒翻」永遠算不清（同 [[pitfall_rename_only_half_done]] 的形狀）|

## 8. 失效場景反思（FMEA · R17 · 草稿）

| # | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|
| **F-1** | 把 `CONFIRM_STATUS_LABEL` 的 **key**（DB 值）也翻成英文 | 全站狀態比對靜默失效，**任務永遠卡在某個狀態** | **P0** | 該檔已有警告；i18n 只碰 value 不碰 key · 加測試釘住 |
| **F-2** | 翻譯只做了一半 → 中英混雜 | 正是 08-24 才修掉的問題（`production_meeting`）· 客戶對品質的觀感 | P1 | OQ-8 選「全搬」· M6 守門測試擋新增硬編 |
| **F-3** | ⚠️ **英文字比中文長 30–50%** | 側欄、按鈕、表格欄位**被擠爆或截斷** —— 這在中文版看不出來 | **P0** | M5 必須**實際切到英文逐頁看過**，不是翻完就算 · 已有前例（M3.5 排版迴歸） |
| **F-4** | LINE 推播用了登入者的 locale 而非**收件人**的 | 台灣員工收到英文通知 | P1 | C 軸的 locale 來源是 `users.locale` of **recipient** |
| **F-5** | 稽核紀錄（`audit`）歷史列用新語言重繪 | 歷史紀錄的意思被改寫 | P1 | 稽核描述**存下當時的文字**，不走 i18n |
| **F-6** | AI 完成意圖判讀（`completion-intent.ts`）被當成文案翻譯 | 「好了」「修好了」是**語意規則**，翻了會讓完成偵測失效 | **P0** | 明確標記 `task-completion/` 的 82 條**不是 UI 字串** |
| **F-7** | 外籍主管切過去，發現任務卡內容仍是中文 | 期待落差 · 「你們說支援英文」 | **P0** | ⚠️ §3-bis.1 那張「他能做／仍做不到」的表要**在動工前送出去對齊**，不是交付時才解釋 · 這是本模組唯一會讓交付被判定失敗的風險 |
| F-8 | 只翻了他會用的 9 塊，他點到精靈／素材時看到中文 | 中英混雜的觀感 | P1 | 未翻的頁面**明確標示**（或該角色本來就看不到那些頁）· 先確認外籍主管的角色權限範圍 |
