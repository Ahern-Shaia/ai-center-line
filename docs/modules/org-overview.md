## 1. 目標與範圍

用戶其實有**兩個不同需求**，用不同東西解：

| 需求 | 給誰 | 解法 | 本 doc |
|---|---|---|---|
| **A. 一眼確認設定對不對** | 總經理（自用）| **輕量「組織總覽」**唯讀分組樹 | ⭐ 主線（mockup 已做）|
| **B. 客戶/委員簡報用的漂亮圖** | 對外簡報 | 節點連線圖（react-flow/D3）| 評估，多半不必做互動版 |

---

## 2. 既有現況

「公司→部門→成員→LINE 群」這些關係**現在已經有三個地方在顯示且可編輯**：
- 設定 → 部門/成員 → **部門配置**（建部門）
- 設定 → 部門/成員 → **成員**（角色 + 所屬部門下拉）
- 設定 → **通訊管道** → LINE 群組（群組 → 部門）

→ 所以視覺化是**唯讀的彙整層**，不 load-bearing。價值在「攤在同一頁、露出設定漏洞」，不是新功能。

---

## 3. ⭐ 站在巨人的肩膀上

組織圖（Workday / BambooHR / Lattice）的價值**隨組織規模 × 層級深度放大**：

| 條件 | 節點連線圖 | 分組表格/樹 |
|---|---|---|
| 深層級（部門→科→組→匯報鏈）| ✅ 連線圖才看得懂 | ❌ 表格難表達 |
| **扁平兩層（部門→成員）** | ❌ 一個部門 20 人＝20 葉節點，畫面爆炸 | ✅ **分組樹一眼看懂** |
| 大組織（數百人+）| ✅ | 需分頁 |
| **小租戶（10–30 人）** | 殺雞用牛刀 | ✅ 一頁裝得下 |

本系統結構＝**扁平兩層 + 小租戶** → **節點圖是反模式，分組樹才對**。這也是為什麼主線走輕量版。

---

## 4. 提案

### 4.1 主線：輕量「組織總覽」（唯讀分組樹）
- 一棵樹：部門卡（含該部門的 LINE 群 tag + 人數）→ 成員列（頭像 + 姓名 + 角色 + 綁定狀態）。
- ⭐ 刻意露三個「設定容易漏又看不出來」的信號：① 群沒分派部門 → 部門卡警示；② 成員推不出部門 → 收進「未分派」卡；③ 沒綁 LINE 的成員標「未綁」。
- mockup：`docs/mockup/org-overview.html`（待 review）。
- 成本：一個唯讀彙整端點 + 一頁 React，**不用圖形庫、不用新依賴**。

### 4.2 簡報版：節點連線圖（B 需求）
- 若真要對委員展示「漂亮的關係圖」，**先別做互動版**（react-flow 依賴 + 佈局維護 + 扁平結構其實不美）。
- 更省的替代（依序）：① 輕量總覽**截圖**放簡報；② 需要「圖感」就畫一張**靜態示意圖**（Mermaid/繪圖工具，一次性）；③ 真有反覆、互動需求再上 react-flow。
- 判準：**互動節點圖只在「層級變深」或「變成對外賣點」時才划算**，目前都不成立。

---

## 5. 輕量版落地設計（4.1）

- **後端**：`GET /tenant-admin/org-overview`（`departments:view` 或 `users:view`）· 回 `[{department, lineGroups[], members[{name, role, hasLineBinding, departmentSource}]}]` + 未分派桶。aiproot 看全/租戶看自家（resolveTenantId）。彙整自 departments / users / line_group，無新表。
- **前端**：部門/成員頁加一個「**總覽**」tab（第三個分頁），或獨立頁（OQ-ORG-3）。純渲染，重用現有 API 也可（前端彙整），端點只是省往返。
- **不做**：拖拉改結構（改結構走現有可編輯的兩個分頁）、即時 websocket（進頁拉一次即可，OQ-ORG-4）。

## 8. 失效場景反思（FMEA · R17）

| 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|
| 跨租戶彙整未 scope → 甲租戶看到乙的組織 | 跨租戶洩漏 | **P0** | 🔒 端點走 resolveTenantId + RLS，比照 MDA；aiproot 才跨租戶 |
| 大部門（數十人）一頁塞爆 | 難用 | P2 | ⚠️ 部門卡可收合；小租戶暫不成問題 |
| 總覽與可編輯頁資料不一致（快取）| 誤判設定 | P2 | ✅ 進頁即拉，不快取 |
| 「未綁 LINE」誤標成設定錯誤 | 誤導 | P2 | ✅ 文案講清「未綁＝發言歸不到他」，非錯誤 |
