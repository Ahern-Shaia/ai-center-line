## 1. 現況盤點

| 視角 | 項目 | 分組 |
|---|---|---|
| 租戶（tenant_admin）| 9 | 3 群 |
| aiproot | 26 | 6 群（「AIPROOT 管理」佔 12）|

### 1.1 ⚠️ 「定時任務」與「任務」撞名

租戶側欄的「**定時任務**」是 cron 排程設定（`scheduler-config`），
跟本產品的核心產出「**任務**」（tickets）完全無關。

客戶點進去想找任務，看到的是排程時間設定。**這是硬傷，改名就能解。**

### 1.2 ⚠️ 「任務」在租戶側欄是隱形的

任務看板是「總覽儀表」底下的一個 tab，**要點兩次才到得了**，
而次要的「素材看板」反而有一級入口。

我們整天在做的核心產出，導覽上找不到。

### 1.3 同一件事有兩個入口

| aiproot 側 | 租戶側 | 實際上是 |
|---|---|---|
| LINE 綁定稽核 | 員工 LINE 綁定 | 綁定管理 |
| 對話分析歷程 | （分析列表在另一群）| 分析紀錄 |
| 稽核記錄 ＋ LINE 綁定稽核 | | 都是稽核 |

### 1.4 ⭐ 「內容誰控制」與「權限誰給」是兩層，不是一件事

用戶 2026-07-29 的澄清：

> 「客戶方自己控制」我是指客戶方自己控制**內容**（比如幾點執行定時任務、
> 任務卡什麼時間要簽核），但是**權限是我司開放給他們**。

所以正確的模型是**兩層**，先前的 doc 把它壓成一層了：

| 層 | 誰決定 | 例子 |
|---|---|---|
| **權限層** | **aiproot** | 這家客戶的 tenant_admin 看不看得到「自動化」這一頁 |
| **內容層** | **客戶自己** | 看得到之後，幾點跑批次、幾天沒簽核算逾時 |

→ 不是「把頁面交出去」，而是「**內容本來就是客戶的，但門由我司開**」。

#### 現成的正確範例就在旁邊：`定時任務`

| 頁 | 權限碼 | 被 `AIPROOT_ONLY_PAGES` 硬擋 |
|---|---|---|
| **定時任務** `scheduler-config` | ✅ 有 | **否** ← **這就是對的樣子** |
| 通知設定 `notify-config` | ✅ 有 | **是** ⚠️ |
| 資料來源 `master-data` | ✅ 有 | **是** ⚠️ |
| 分類管理 `category-mgmt` | ❌ 無 | 是 |
| 地圖里程設定 `map-config` | ❌ 無 | 是 |

`定時任務` 已經是兩層模型：權限碼決定看不看得到，看得到之後
`scheduler_config` 有 per-tenant override（prod 實例：台灣福祉自己改成 18:00，
平台預設是凌晨）。**其餘四項照這個做就對了。**

⚠️ **通知設定與資料來源更糟：權限碼寫了但被硬擋蓋掉，等於死碼。**
以為調權限就能開放，實際上完全沒作用 —— 這是 N-1「兩套閘門並存」的實證。

⚠️ memory `feedback_tenant_self_governance.md` 記著已要求過兩次租戶自治，
但那條 memory 把它記成「把頁面交還 tenant_admin」的二元選擇，
與本次澄清的兩層模型不同。已於 2026-07-29 更正該條。

### 1.5 「戰情室」混了兩種視角

「我的日報／我的行程」是**個人**，「總覽儀表」是**主管**。
同一個分組裡兩種身分，員工看到主管的東西會困惑（雖然點不進去）。

## 2. ⭐ 通用化的本體不在導覽，在寫死的流程假設

用戶說「每家公司對 task 的性質要求不一樣」。收攏側欄只是表面，
真正決定「任務長什麼樣」的是這些：

| 假設 | 現況 | 每家都一樣嗎 | 本期處理 |
|---|---|---|---|
| **抽取欄位**（任務有哪些欄位）| L2 模板 3 種，`service_order` **未開放前端選** | ❌ **這才是「task 性質不同」的本體** | ⭐ 開放選、加「任務設定」頁 |
| **一定要主管簽核** | 三欄看板的前提 | ❌ 長照的服務紀錄可能不需要 | 🔒 **預留**（裁定 2）|
| **7 天寬限期** | 硬編 `GRACE_DAYS = 7` | ❌ 維修 7 天合理，詢價太長 | ⭐ **租戶可調**（裁定 1 的「調整時間」）|
| **每日提醒的升級階梯**（1-3／4-7／8+ 天）| 硬編 | ❌ 同上 | ⭐ 租戶可調 |
| **批次分析時間** | 已可設（scheduler_config）| — | ✅ 已通用 |
| 信心度門檻（high→待簽核）| 硬編 | ✅ 技術參數，不該給客戶調 | 不開放 |
| 四個結束原因 | 硬編 CHECK | ✅ 維持 | **不開放**（Jira 的 resolution chaos 教訓）|

> **裁定 1 的「租戶只需按自己公司性質調整時間」對應的就是第 3、4 列。**
> 其餘能力一律做出來，由 aiproot 用權限決定誰看得到。

### 2.1 為什麼結束原因不開放自訂

Atlassian 官方明文警告：不要建語意為「未完成」的 resolution 值 ——
Jira 有人建了叫 `Unresolved` 的，結果那些票**全被當成已解決**。
開放自訂 outcome 等於把這個坑交給客戶去踩，而踩了之後
「完成率」這個要給總經理看的數字就永遠算不出來。

## 3. 收攏後的導覽

### 3.1 分組原則

現在的分組是**按功能模組**（AI 對話分析／通訊接頭層／AIPROOT 管理），
那是**我們的內部架構**，不是使用者的心智模型。

改成按**「這是誰的東西」**分：

```
我的     → 只跟我有關（每個人都有）
營運     → 團隊在跑的事（主管看）
設定     → 這家公司怎麼運作
平台     → 跨租戶（aiproot）
```

### 3.2 租戶視角（9 → 10 項）

| 群 | 項目 | 變更 |
|---|---|---|
| **我的** | 我的日報 | — |
| | 我的行程 | — |
| **營運** | **任務看板** | ⭐ **從 tab 升為一級入口** |
| | 總覽儀表 | 從「戰情室」移來 |
| | 對話紀錄 | 原「今日日誌」tab 升級 |
| | 素材 | 原「素材看板」·「資料·知識」群解散 |
| **設定** | 部門/成員 | — |
| | 通訊管道 | ⭐ 「LINE 群組」＋「員工 LINE 綁定」合併（兩個 tab）|
| | **任務設定** | ⭐ **新增** —— 這家公司的任務長什麼樣（§4）|
| | 自動化 | ⭐ 「定時任務」改名（含排程＋通知），解掉撞名 |
| | 稽核記錄 | — |

### 3.3 aiproot 視角（26 → 16 項）

租戶那 10 項照舊（看的是選定的租戶），另加：

| 群 | 項目 | 變更 |
|---|---|---|
| **平台** | 租戶管理 | 合併「開通新租戶」（一頁一個「新增」鈕）|
| | **系統健康** | ⭐ **4 頁合一**：抽取健康度／任務完成追蹤／對話分析歷程／AI 成本（四個 tab）|
| | LINE 機器人 | — |
| | 語言模型設定 | — |
| | 權限管理 | — |
| | 資料來源 | 留在平台（含金鑰，預設不給租戶）|

⚠️ **「系統健康」四合一的理由**：這四頁回答的是同一個問題 ——
「**這套系統跑得好不好**」。分成四個入口的結果是每一個都要點進去看一眼，
而它們的資料是互相解釋的（成本高不高要看分析量、接住率低要看抽取健康度）。

## 4. ⭐ 「任務設定」頁 —— 通用化的落點

這是回答「每家公司對 task 的性質要求不一樣」的地方。四個區塊：

| 區塊 | 內容 | 誰能改 |
|---|---|---|
| **任務長什麼樣** | 抽取模板（一般／工廠報工／服務工單）· 目前只有 aiproot 能改 `tenants.extraction_template` | 權限碼 `task-config:template` |
| **分類** | category_registry（已 tenant-scoped）· 改顯示名、封存 | `task-config:category` |
| **時間** ⭐ | 逾時寬限期（＝**任務卡幾天沒簽核算逾時**，預設 7 天）· 提醒升級階梯（3／7 天）· 分析批次時間（**幾點執行**，已可設）| `task-config:timing` ← **裁定 1 的「客戶按公司性質調整時間」就是這格** |
| **流程**（🔒 預留）| 要不要簽核 · 誰能簽 | 本期只留 UI 位置與資料欄位，**不實作** |

### 4.1 時間類設定要落在哪

```sql
-- 概念（M0 不定案，M2 再細）
ALTER TABLE tenants
  ADD COLUMN overdue_grace_days int NOT NULL DEFAULT 7,
  ADD COLUMN reminder_tier_days int[] NOT NULL DEFAULT '{3,7}';
```

⚠️ **不要各自硬編**。目前 `GRACE_DAYS = 7` 在 `warroom-tasks.service.ts`、
`tierFor()` 在 `daily-report-pattern.ts` 各寫一次 ——
這次已經因為「兩個獨立的 7 各自漂移」踩過一次坑（進欄與 pill 門檻不一致）。

## 5. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|
| **N-1** | 權限 | 15 項沒有權限碼，aiproot 以為能用權限管理調整，實際改不動 | **裁定 1 與 3 直接落空** | **P0** | M1 先補完權限碼 · 補完後把 `AIPROOT_ONLY_PAGES` 刪掉，避免兩套閘門並存 |
| **N-2** | 權限 | 補權限碼時漏掉後端 `@Roles`，只擋了側欄 | **前端隱藏、API 仍可打** —— 資安不是 UI 問題 | **P0** | ⭐ **守衛改 fail-closed ＋ 跨租戶形狀測試**（§5.1）· 排在 M0.9，**必須在 M1 之前** |
| **N-3** | 遷移 | 導覽改版後既有使用者找不到原本的頁 | 客訴、支援成本 | **P1** | 改名的項目在側欄加一次性提示（「原『定時任務』」）· 或首次登入顯示變更說明 |
| **N-4** | 合併 | 「系統健康」四合一之後，單頁載入 4 份資料變慢 | 進頁面卡住 | **P1** | tab 各自 lazy load，只載當前 tab |
| **N-5** | 時間設定 | 租戶把寬限期設成 0 或 999 | 0 → 全部立刻逾時；999 → 永遠不逾時 | **P1** | 範圍限制（1–90）· UI 顯示「目前設定下有 N 件會變成逾時」讓他先看到後果 |
| **N-6** | 時間設定 | 改了寬限期，歷史任務的「逾時 N 天」全部跳動 | 主管以為資料被改過 | **P2** | 改動當下顯示影響筆數 · 稽核記錄留一筆 |
| **N-7** | 預留 | 「要不要簽核」留了 UI 位置但不能點，客戶問「這什麼時候有」 | 期待落空 | P2 | 預留的區塊**不要顯示**，只在資料層留欄位（不做灰掉的假按鈕）|
| **N-8** | 分組 | 「我的／營運／設定」對 employee 來說「營運」是空的 | 空群組 | **P1** | 群組內全部無權限時整群不顯示（現有 `roles` 機制已有雛形）|

### 5.1 ⭐ N-2 的具體緩解（2026-07-29 盤點後）

#### 現況：135 個端點，9 個完全沒有守衛裝飾

盤下來那 9 個都是**刻意的**（打卡、改自己密碼、查自己權限 —— 任何登入者都該能用），
而且都用 `@CurrentUser()` 取 `tenant_id`、不接受 client 傳。**目前沒有已知漏洞。**

```
attendance: punch / punch/:id/label / places / my-month / trips / map-tile-config
auth: change-password
master-data: customers        （打卡選單要用，只回名稱與編號）
permission: me/permissions
```

#### 但機制是 fail-open

```ts
// auth/roles.guard.ts
if (!roles || roles.length === 0) return true;   // ⚠️ 沒寫裝飾器 = 放行
```

**忘記加裝飾器的懲罰是「安靜地放行」。**
而 M1 要一次補 15 項權限碼，正是最容易漏的時候。

#### 真正的危險形狀

不是「員工看到不該看的頁」，是這種：

```ts
@Get("stats")
async stats(@Query("tenantId") tenantId: string) {      // ← tenantId 來自 client
  return withTenant({ tenantId, role: "aiproot_admin" }, ...)   // ← 內部開 admin 上下文
}
```

漏了 `@Roles`，任何登入的員工都能傳別家 `tenantId` **跨租戶讀資料**。
⚠️ 本次新增的 `/completion-signals/*` 正是這個形狀（有加 `@Roles`，但只差一行）。

#### ✅ 採用的兩層（裁定 2026-07-29）

**① 守衛改 fail-closed** —— 沒有宣告存取層級就拒絕

```ts
if (!roles) {
  if (!this.reflector.get(ALLOW_ANY_USER_KEY, handler)) {
    throw new ForbiddenException("此端點未宣告存取層級");
  }
}
```

那 9 個現存端點加 `@AllowAnyUser()` **明示意圖**。
之後忘記寫會**炸在開發階段**，而不是安靜放行到 prod。

**② 跨租戶形狀測試** —— 比泛用 metadata 測試更有針對性

> 任何吃 `@Query("tenantId")` 的端點，**必須**有 `@Roles` 且限 aiproot／consultant。

因為那是**唯一會跨租戶**的形狀。其他端點漏了頂多是越權看自家資料，
這個漏了是**看別家的**。

#### ❌ 不做：metadata 快照測試

原本 doc 寫的「列出所有端點與守衛做快照比對」**不做**。

理由：快照測試容易變成「壞了就更新快照」的橡皮圖章 ——
**那比沒有更糟，因為它給人安全感**。
①已經讓漏寫在開發階段就炸，②守住唯一的跨租戶形狀，兩者都不依賴人的紀律。
