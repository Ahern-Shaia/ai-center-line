## 1. 目標與範圍

### 1.1 目標

1. 主管打開鮮湧戰情室，**在同一張平面圖上**同時看到「機台在做什麼」與「看著它的相機還活著嗎」。
2. 巡檢的燈號要**指向可行動的事**：相機掉線 → 找人去看；讀數不可信 → 找人重新框 ROI。
3. 這張頁面上出現的每一個巡檢數字，都是**從真實 CSV 算出來的**，不是示意值。

### 1.2 這份 doc 的核心主張

> **現行 CSV 的「狀態」欄不能直接畫上畫面。**
> 24,441 筆裡 24,259 筆（**99.3%**）標成「[異常]」。
> 照它畫，16 台相機會全部紅燈 —— 那張圖就沒有資訊量了。

### 1.3 不做的事

| 不做 | 為什麼 |
|---|---|
| 把巡檢事件變成任務卡進任務看板 | 一天 12,319 件。看板會死，而且主管會**連帶不信任本來準的 AI 任務卡**（信任是共用的）|
| 開新分頁放巡檢 | 相機就是在看那些機台的儀表，拆兩張圖等於要人自己對位置 |

| 現在就做 ingest 端點 | 先確認這是 demo 還是長期接（OQ-SI-1）|

| 相機 | 現象 |

### 2.4 ⚠️ 我自己的判準也有同一個陷阱

上表 `.106` / `.144` 我的啟發式判成 🟢，因為我用「**該台自己的中位間隔**」當基準——
一小時才回報一次的相機，它的中位數就是 3600s，於是「準時」。

> **拿自己的歷史當基準，會讓長期壞掉的東西看起來正常。**
> （同類：memory `pitfall_green_because_empty`）

**正解是拿「該型號的設計取樣率」當基準，而那個值只有客戶知道** → OQ-SI-3。

⚠️ 而 `.144` 還疊了第二層問題（解析失敗），見 §2.5 —— **兩個原因疊在一起，畫面上只會看到一個結果**。

### 2.5 ⭐⭐ 我第一版把 `.144` 誤判成「停止回報」—— 其實是解析失敗

初稿寫「`.144` 08-25、08-26 完全沒有資料」。**錯的。**

那兩天的資料一直都在，只是這台的時間格式跟別台不一樣：

| | 格式 | 例 |
|---|---|---|
| 其餘 15 台 | `%Y-%m-%d %H:%M:%S` | `2026-08-25 14:42:10` |
| **`.144`** | `%Y/%m/%d %H:%M` | `2026/8/25 16:42`（斜線、月日不補零、**沒有秒**）|

我的第一版解析器只認前者，`strptime` 失敗就 `continue` —— **31 列被靜默丟掉**，
於是這台看起來像 08-27 才突然開始回報。

> **「沒有資料」和「我讀不到資料」在畫面上長得一模一樣，但處置完全相反。**
> 一個是叫人去現場修相機，一個是叫人來修我們的 parser。
>
> 修法：`scripts/inspection-probe.py` 現在**解析失敗一律計數並印出來**，不可以 `continue` 就算了。
> 同類：memory `pitfall_green_because_empty`。

⚠️ 這也代表現場**至少有兩種寫檔器**。做 ingest（OQ-SI-1 選 B）時，
格式白名單要涵蓋全部，而且**不在白名單內要報錯不要跳過**。

## 4. 提議的呈現方式

### 4.1 巡檢是平面圖的**第二個圖層**，不開新分頁

`DATA[樓層]` 加一個 `cam` 陣列，與 `dev` **共用同一個座標空間**：

```js
cam:[{
  id:"CAM-2F-01",           // 相機代號
  ip:"192.168.134.101",     // ← CSV 檔名來的
  of:"ST-2F-01",            // ⚠️ 這台相機在看哪台機台 —— CSV 沒有，要客戶給（OQ-SI-2）
  x:60, y:160,              // 跟著 of 的機台座標（或另給偏移）
  s:"g",                    // 燈號（語意見 §4.2）
  last:"13:56", iv:15, n:238,   // 最後回報 / 中位間隔(s) / 今日筆數
  v:6.6, trust:"ok"         // 讀數中位 / 可信度
}]
```

### 4.2 ⭐⭐ 三色語意必須換掉（本 doc 最重要的一條）

`dev` 的 g/y/r 是「溫度偏離目標」。相機**不能照抄**：

| 燈 | 判準 | 主管該做什麼 | 現況台數 |
|:-:|---|---|--:|
| 🟢 | 正常回報、讀數在量程內 | 不用做事 | **3** |
| 🟡 | **讀數不可信**（判讀跳動 / 超出量程）| 找人重新框 ROI / 調焦 | **8** |
| 🔴 | **停止回報** | 找人去看相機或網路 | **5** |
| ⚪ | 未納入本期 | — | 0 |

> **紅燈給「沒回報」，不給「數值變動」。**

### 4.3 點擊互動：複用同一個面板

點相機 → 沿用機台那個 `#dt`，把「近 60 分鐘溫度曲線」換成
「**近 60 分鐘讀數曲線 ＋ 判讀穩定度**」。版位、視覺語言、互動全部沿用，不另發明一套。

`ks` 那組 KPI 格換成：最後回報 / 取樣間隔 / 今日筆數 / 讀數中位 / **10× 跳動率** / 可信度。

### 4.4 頂部 KPI 與圖例

- KPI 加一格：**「巡檢在線 N / 16」**
- 圖例加一條「相機」，跟「網路拉線」並列

### 4.5 ⚠️ 這張圖上**不要**放的東西

| 不要放 | 為什麼 |
|---|---|
| 「今日異常 12,319 件」 | 隔壁「批次品質」寫的是「**40 批全部吻合，零例外**」。一個 99.3% 的指標擺旁邊，會把那塊的說服力一起拉下來 |
| 去噪後的「修正讀數」 | 沒有量程就沒有工程依據（R11）|
| 相機縮圖 / 即時影像 | 另一個模組的事（`media-and-vision`），而且有個資疑慮 |

## 5. ⛔ 硬 blocker：CSV 沒有「相機 ↔ 機台」對應

CSV 只有 IP + `camera_NN`，**沒有位置、沒有機台代號、沒有樓層**。
沒有這張表，相機點不到平面圖上任何一個位置。

需要客戶給的最小資訊（16 列）：

| IP | 相機 | 樓層 | 對應機台 | 讀什麼儀表 | 合理量程 | 設計取樣率 |
|---|---|---|---|---|---|---|
| 192.168.134.101 | camera_01 | 2F? | ST-2F-01? | ? | ? | ? |

- **對應機台** → 決定畫在哪
- **合理量程** → 決定什麼叫「離譜」（§2 用 P95×3 是統計猜測，**不是工程判準**）
- **設計取樣率** → 決定什麼叫「停止回報」（避免 §2.4 那個陷阱）

## 7. ⛔ 進任務看板的 gate

我試算過三種替代判準（停止回報 / 讀數離譜 / 去抖動），**合計仍有 576 件/天**：

| 判準 | 件數 | 換算/天 |
|---|--:|--:|
| ① 停止回報（> 中位間隔 20 倍且 > 10 分）| 680 | 345 |
| ② 讀數離譜（> 該台 P95 的 3 倍）| 304 | 154 |
| ③ 去抖動（連續 3 筆偏離中位數 6×MAD）| 151 | 77 |
| **合計** | **1,135** | **576** |

比現行判準好 21 倍，但**離「一天 20 件」還差 29 倍**。

> **Gate：單日事件數壓到 20 件以下，才可以接進任務看板。**
> 依據：主管一天核對得完的量。現行 12,319 件是它的 **616 倍**。
>
> ⚠️ 這三條判準是**統計猜測不是工程判準** —— 沒有量程（OQ-SI-2）之前，
> 「離譜」的定義只能靠該台自己的分佈推，而那正是 §2.4 的陷阱。

## 10. 測試策略

| 層 | 測什麼 |
|---|---|
| 資料 | CSV 解析：混進來的表頭列要被跳過；`辨識數值` 非數字要落 `null` 不可當 0 |
| 判準 | 給一台「3 天沒回報」的假資料 → 必須 🔴（**反向驗證：故意餵好資料確認不會誤報**）|
