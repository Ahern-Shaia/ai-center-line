## 3. 設計

### 3.1 兩個選項（客戶原話同時支持兩種讀法）

| | A · 當成分類存起來 | B · 抽出決議各自成待辦 |
|---|---|---|
| 做什麼 | 在「任務設定 → 分類詞庫」新增「會議記錄」分類 | 二次 LLM 呼叫，從會議對話抽出每一項決議 |
| 一場會 → 幾張卡 | 1 張（存查）| 1 張會議紀錄 ＋ N 張決議待辦 |
| 工作量 | **XS**（不用寫程式，客戶自己就能加）| **L** |
| 回答了客戶哪句話 | 「會議記錄進到會議記錄區」 | 「**這個項目還沒完成**」|
| 風險 | 沒解決客戶真正的痛 | 待核對佇列量級跳升（§3.4）|

⭐ **A 不需要我們做任何事** —— 分類是開放的，客戶在分類詞庫加一個「會議記錄」，
AI 下次就會用它。**如果客戶要的只是 A，這一項現在就結案了。**

### 3.2 ⭐ B 的架構已被限制決定 —— 只能走二次呼叫

**不是設計選擇，是硬限制。**

`templates.ts:70` 已經記著同款事故：

> ⚠️ v2：這是**獨立的第二次 LLM 呼叫**，不併進 service_order 主 output schema ——
> 併進去會讓整包 union 參數超過 Anthropic **≤16 上限**、API 回 400（doc §3.6 / FMEA F-10）。
> 本 schema 單獨算約 11 個 union（9 nullable + array + enum），在上限內。

`service_intake` 2026-08-01 就是併進去踩到 400 後 revert 的（memory
`pitfall_anthropic_structured_output_union_limit`）。

⚠️ **這個限制在 zod 綠、tsc 綠、unit test 綠的情況下完全驗不到** ——
限制在 Anthropic API 端。**改抽取 schema 必須跑一次真實 LLM 呼叫才算驗收。**

所以 B 的形狀是固定的：

```
第一次呼叫（現況不動）
  → classifications + records + service_reports
       ↓ 若 classifications 裡有會議類
第二次呼叫（新增 · 只在需要時跑）
  → meeting_decisions[]
```

### 3.3 ⭐ 只在偵測到會議時才跑第二次

`service_intake` 目前是**每批都跑**。會議不該照抄這一點：

- 會議不是天天有 —— 每批都跑第二次呼叫等於**天天付一次沒有產出的錢**
- 第一次呼叫的 `classifications` 已經給出分類，用它當閘門是零成本的

```
if (classifications.some(c => 是會議類)) → 跑第二次
else → 完全不呼叫
```

### 3.4 ⚠️ B 真正的代價不是錢，是主管的節奏

一場會抽 5–10 項決議 → **待核對佇列的量跳一個級距**。

pageGuides 現在對客戶承諾的是「每天約 3 分鐘」。
如果會議決議讓每天要核對的卡從 5 張變 25 張，**那句承諾就不成立了**，
而客戶會體驗成「這系統變吵了」。

這是要跟客戶講清楚的**取捨**，不是實作細節 —— 也是 OQ-MD-3。

### 3.5 決議要抽哪些欄位（草案 · 待 §6 資料驗證）

```
meeting_decisions[]
  · title        決定要做的事（必填）
  · owner        誰負責（對不到主檔就留原文並降 confidence）
  · due          什麼時候前（沒明講填 null · 禁止推算日期）
  · source_ids   回溯到原始訊息（R11）
  · confidence
```

⚠️ **`due` 一律不猜**。「下週處理」不可以變成某個具體日期 ——
猜錯的期限會讓逾時 pill 亂長，而使用者沒辦法分辨那是 AI 猜的還是人講的。

⚠️ 單獨算 union：`owner` `due` 各 1 nullable ＋ `source_ids` array ＋ `confidence` enum
≈ 4–5，遠在上限內。

## 6. 前置：prod 探查（R10 · 由人執行）

腳本：[`scripts/meeting-probe.sql`](../../scripts/meeting-probe.sql)（唯讀）

```bash
psql "<PROD_DATABASE_URL>" -f scripts/meeting-probe.sql
# 租戶名稱對不上時：-v tenant='部分名稱'
```

六段：`診斷` → `列租戶` → **RLS 護欄** → 會議任務分布 → 摘要樣貌 → **原始對話全文**。
決定性的是最後一段。

### 6.1 ⚠️ v1 的教訓：這支腳本自己踩了它在警告的坑

v1 把查 `tenants` 寫在 `SET` **之前**。實際 policy（`pg_policies` 查證）：

| 表 | policy | 平台角色逃生門 |
|---|---|---|
| `tenants` | `tenant_id = current_tenant OR actor_role = 'aiproot_admin'` | ✅ 有 |
| `line_message` | `… OR actor_role IN (aiproot_admin, consultant, system)` | ✅ 有 |
| `tickets` | `tenant_id = current_tenant AND (…department…)` | ❌ **AND-only，沒有** |

於是 v1 的第 0 段兩個條件都不成立 → **靜默回 0 列** → tenant_id 抓不到 →
後面每一段都在查全零 UUID → 全空。

**而最糟的不是抓不到，是抓不到之後繼續跑** —— 印出一整排 0 列，
讀起來就是「客戶根本沒開會」。差一點就據此做出錯誤結論。

v2 的三個修正：
1. `SET` 移到所有 `SELECT` 之前
2. `\set ON_ERROR_STOP on` —— 抓不到 tenant 就**當場中斷**，不產出會被誤讀的空表
3. 加一段 **RLS 護欄**（這個租戶總共幾張票）—— 這裡是 0 的話，下面所有的 0 都沒有意義

⚠️ **本機驗不到 RLS 那條路**：本機用 `postgres` 連線會繞過 RLS。
兩條路徑（抓得到／抓不到）都在本機實測過，但「RLS 擋住」的情境只有 prod 才驗得到 ——
所以護欄段才是必要的。

### 7.1 M1 為什麼不走 category_registry

原本想「在分類詞庫新增會議記錄」—— 但 registry 在 prod 是空的（任務 #35，
upsert 被 `catch {}` 吞掉）。而且**這不是台灣福祉特有的缺口**：
內建清單沒有會議，任何客戶的會議內容都會讓模型自己造 slug。
補進內建清單才是治本，也不依賴那條壞掉的路。

### 7.2 ⚠️ 判別軸比清單本身重要

`schemas.ts` 自己的註解早就寫了：「**只加清單不給判別軸，模型會在邊界上亂猜**」。

而且測試也擋了 —— 我第一版只加 enum 沒寫 prompt 定義，
`conversation-analysis.templates.test.ts` 的
「每個建議分類都要在 tenant prompt 裡有定義」當場紅。

分類規則 7 定的軸是**主題優先**：

> 會議上談的維保仍是 maintenance、談的報價仍是 sales ——
> 不可以因為它在會議上被提到就改歸 meeting，否則要找維保時就找不到它了。

⭐ 這也是為什麼 §2.2 那 4 張散在 `rnd`/`sales`/`chitchat`/`attendance` 的
**刻意不搬**：它們有明確主題，分類本來就是對的。
現有 8 個分類的軸是**主題**，「會議」的軸是**來源** —— 兩條軸混在一起，
會議上談的維保就得二選一，選了會議記錄之後就再也找不回維保視角。

### 7.2-bis ⭐⭐ AI 自己造分類是**訊號**，不是缺陷

prod 實查列出三個英文 slug，**每一個都指向內建清單真的缺的東西**：

#### 為什麼 `document_control` 先不動
