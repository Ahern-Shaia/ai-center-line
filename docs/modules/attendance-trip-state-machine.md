## 0. 觸發 · 一位業務的原話

> 「如果第一段行程到第二段行程，是不是除了第一段抵達要打一次之外，**如果從第一段離開也要再打一次開始的概念**，這樣才能有第二段的開始？
>
> 或是前面直接防呆，因為**打卡回去補打就容易變成作假**，例如**一段開始強制要結束、結束強制要開始下一段**，除非你按今天行程已結束⋯之類。
>
> 我們要協助站在他們思維，就能是個貼心的好產品。」

### 0.1 產品原則（本模組的判準）

> **「站在使用者思維的小白舒適體驗」不是加分項，是我方的商業護城河。**
>
> 競品業務王 Salesking 功能比我們深得多（表單引擎、電子簽名、防偽、離線），但員工端評分 **1.35★ / 2.2★**，一星評論是「為了省錢叫員工下載」。這條賽道上，**功能不是勝負手，員工願不願意用才是**。
> 本模組所有取捨一律以此為準：**寧可少一個功能，不可多一次員工要自己判斷「我現在該按哪個」的瞬間。**

## 1. 問題診斷 —— 一個問句裡藏了三個問題

| # | 表面問句 | 真正的問題 | 性質 |
|---|---|---|---|
| **P1** | 「離開是不是也要打一次？」 | **語意不清**：使用者看不出「記錄這一站」到底代表什麼——是「這段結束」還是「下段開始」？ | UX |
| **P2** | （同上） | **資料真的缺**：現況拿不到「停留多久／路上多久」。抵達 A → 抵達 B 的時間差 = 停留 + 移動，**無法拆分** | 資料模型 |
| **P3** | 「補打就容易變成作假」「強制要結束、強制要開始」 | **沒有狀態約束**：目前任何時刻都可以打任何一種卡，系統不知道「你現在應該做什麼」，也沒有「今天結束」的概念 | 流程 |

**P1 是徵狀，P2/P3 是病灶。** 只改文案（解 P1）會讓業務覺得「被打發」；只加打卡（解 P2）會讓員工多一倍動作。要一起解。

## 2. 現行模型與它的極限

### 2.1 現況（migration 0023 + `attendance.service.ts`）

```
打卡序列：  clock_in ──── arrive_site ──── arrive_site ──── arrive_site
                  └─ trip 1 ─┘     └─ trip 2 ─┘     └─ trip 3 ─┘
```

- `punch_type` CHECK 已含 `clock_in | arrive_site | clock_out`，但 **`clock_out` 從未被前端使用**（死代碼）。
- `trip` **只在 `arrive_site` 時建立**，`from` = 當日前一筆打卡（不分型別）。
- 沒有任何狀態驗證：`attendance.controller.ts` 只驗 `punchType` 是三者之一，不驗「現在能不能打這種卡」。

### 2.2 為什麼「抵達即出發」在數學上夠、在心智上不夠

算 A→B 的距離**不需要**知道在 A 停了多久——所以現行模型算里程完全正確。
但使用者的心智模型是**「一段有頭有尾」**。當畫面只讓他標「尾」不讓他標「頭」，他會懷疑系統漏記（這正是 `attendance-mileage-transparency.md` §1 的爭議 (b)「記少了」的同一個根）。

### 2.3 現行模型算不出來的東西

| 缺 | 誰要用 | 場景 |
|---|---|---|
| **停留時長**（arrive → depart） | 長照核銷、巡檢驗收、客戶拜訪品質 | 「照服員在案家服務了多久」 |
| **純移動時長**（depart → arrive） | 交通補助核銷、路線效率 | 政府長照交通補助要求分開列 |
| **今日是否已結束** | 日報生成、主管視圖 | 17:30 生日報時不知道人是否還在外面 |
| **最後一段回程** | 里程合計 | 最後一站 → 回公司/回家的路完全沒被記 |

> 競品業務王在長照垂直明確主打「到達 A → 離開 A → 抵達 B」+「行程區段時間統計，符合政府交通補助核銷」。**這不是他們發明的需求，是這個產業本來就有的。**

## 3. 方案選型

| 方案 | 做法 | 員工每站點擊 | 解 P1 | 解 P2 | 解 P3 | 判定 |
|---|---|---|---|---|---|---|
| **A · 只改文案** | 保持一次打卡，文案講清「抵達＝上一段結束」 | 1 | ✅ | ❌ | ❌ | 治標 |
| **B · 雙段強制** | 每站強制打「到」+「離」，兩顆按鈕並列 | 2 | ✅ | ✅ | ✅ | **踩競品的雷**（多一倍動作、要自己選按鈕） |
| **C · 單鍵狀態機** ⭐ | 引入 `depart_site`，但**任何時刻畫面只有一個主按鈕**，按鈕語意隨狀態切換 | 2（但零判斷） | ✅ | ✅ | ✅ | **建議** |

### 3.1 C 案的核心洞見

**「離開 A」和「抵達 B」在時間上是兩件事，但在使用者心智上是同一個念頭——「我要走了 / 我到了」。**

所以不要問他「你要打哪種卡」，而是**由系統決定現在該打哪種，他只要按那顆唯一的按鈕**。
點擊數確實從 1 變 2，但**認知負荷從「選擇」降到「零」**——這跟我方 2026-07-26 已上線的單按鈕防呆是同一條路線的延伸，不是新方向。

## 4. 核心設計 · 狀態機

### 4.1 狀態與轉移

狀態以**台北日**為界，每日自動重置（沿用現行 `getLatestPunchToday` 的當日範圍）。

```
              ┌──────────────┐
              │ not_started  │  今天還沒打過卡
              └──────┬───────┘
                     │ 開始外勤 (clock_in)
                     ▼
              ┌──────────────┐  ◀─────────────────┐
              │   moving     │  在路上            │
              └──────┬───────┘                    │
                     │ 我到了 (arrive_site)       │ 出發前往下一站
                     │   └─ 產生 trip（里程）     │ (depart_site)
                     ▼                            │
              ┌──────────────┐                    │
              │   at_site    │  在站上 ───────────┘
              └──────┬───────┘
                     │ 今日行程結束 (clock_out)
                     ▼
              ┌──────────────┐
              │    ended     │ ──── 繼續外勤 (clock_in) ──▶ moving
              └──────────────┘
```

`moving` 狀態也可直接 `clock_out`（下班前最後一段回程 → 產生最後一段 trip，見 OQ-TSM-5）。

### 4.2 每個狀態畫面上有什麼（**主按鈕永遠只有一顆**）

| 狀態 | 主按鈕（大、primary） | 次要動作（小、文字連結） | 說明文案 |
|---|---|---|---|
| `not_started` | **開始外勤** | — | 出門時按一下，之後每到一個地方再按一次 |
| `moving` | **我到了** | 今日行程結束 | 到達下一個地點時按 |
| `at_site` | **出發，前往下一站** | 今日行程結束 | 目前在〈客戶 A〉· 已停留 32 分鐘 |
| `ended` | （不顯示主按鈕，顯示今日總結） | 繼續外勤 | 今日 4 站 · 38.2 km · 已結束 |

**「今日行程結束」永遠是次要位階**——它是逃生門不是常用鍵，但**任何狀態都摸得到**（正是業務說的「除非你按今天行程已結束」）。

### 4.3 里程口徑（⚠️ 破壞性變更）

| 段的來源 | 語意 | 可算移動時長？ | UI 標示 |
|---|---|---|---|
| `depart_site` → `arrive_site` | **純移動**（新口徑 · 最精確） | ✅ | 正常顯示 |
| `clock_in` → `arrive_site` | 第一段（從出發地到第一站） | ✅ | 正常顯示 |
| `arrive_site` → `arrive_site` | **漏打離開**（舊口徑 · 含停留時間） | ❌ | 標「未記錄離開」 |
| `arrive_site`/`depart_site` → `clock_out` | 最後一段回程 | ✅ | 標「回程」（OQ-TSM-5） |

> **不加 `from_kind` 欄位**——`trip.from_punch_id` join 回 `attendance_punch.punch_type` 就知道，不做冗餘欄位。

### 4.4 停留時長 · 不落庫

停留時長 = 相鄰 `arrive_site` → `depart_site` 的時間差，**衍生計算、不存欄位**（避免與 punch 原始資料不一致）。若該站沒有 `depart_site` → 顯示「離開時間未記錄」，**不推估、不填數字**（承 R11 精神：缺漏填 null，禁止臆測）。

## 5. 🩹 貼心設計 · 「忘記按離開」怎麼辦

**這是 C 案唯一的真實風險，也是這份設計最重要的一段。**

員工在 A 站按了「我到了」，離開時忘記按，直接開車到 B。這時他打開 APP 看到的主按鈕是「出發，前往下一站」——但他人已經在 B 了。如果他照按，系統會用 **B 的座標記成「離開 A」**，資料就爛了。

### 5.1 位置感知的自動切換

`at_site` 狀態下，前端取得目前位置並與 A 站座標比對：

| 目前位置 | 主按鈕 | 提示 |
|---|---|---|
| 距 A 站 **< 200 m**（還在站上） | **出發，前往下一站** | 目前在〈客戶 A〉· 已停留 32 分鐘 |
| 距 A 站 **≥ 200 m**（已經走了） | **我到了（新的一站）** | 偵測到你已離開〈客戶 A〉· 這段會標記為「未記錄離開時間」 |

**按下去就是對的**——使用者永遠不需要意識到自己漏了一步。

### 5.2 漏打的資料處理原則：誠實降級，不偽造

- **不**補寫一筆假的 `depart_site`（時間是猜的、座標是猜的 → 這正是業務擔心的「補打卡＝作假」）。
- 該段 trip 就用 `arrive_site → arrive_site` 的舊口徑，**在「我的行程」明示「這段未記錄離開時間，含停留時間」**。
- 里程數字仍然正確（距離不受影響），只有「移動時長／停留時長」不可得。

### 5.3 教育而不責備

在該段詳情附一句：

> 下次離開時按一下「出發」，就能分開算「停留」和「路上」的時間。

不彈窗、不紅字、不擋流程。

## 6. 資料模型變更（R1 遷移計畫 · Migration 0029）

### 6.1 變更清單（極小）

```sql
-- 1. punch_type 加 depart_site
ALTER TABLE attendance_punch DROP CONSTRAINT attendance_punch_punch_type_check;
ALTER TABLE attendance_punch ADD CONSTRAINT attendance_punch_punch_type_check
  CHECK (punch_type IN ('clock_in', 'arrive_site', 'depart_site', 'clock_out'));

-- 2. source 加 auto（自動收班用 · 見 OQ-TSM-4）
ALTER TABLE attendance_punch DROP CONSTRAINT attendance_punch_source_check;
ALTER TABLE attendance_punch ADD CONSTRAINT attendance_punch_source_check
  CHECK (source IN ('liff_geo', 'location_msg', 'manual', 'auto'));
```

**沒有新表、沒有新欄位、沒有資料搬遷。**

### 6.2 影響範圍與相容策略

| 面向 | 影響 | 策略 |
|---|---|---|
| 歷史打卡資料 | 無 `depart_site` | **不回溯、不改寫**（R11 原始不可變）；舊段自動落入「未記錄離開」顯示 |
| 歷史 trip | 口徑為 arrive→arrive | 同上，UI 標示區分 |
| `PUNCH_TYPE_LABEL` | 需加 `depart_site: "離站打卡"` | 影響 `attendance.suspicious` 通知文案 |
| `computeSuspicious` | 速度判定目前用「相鄰任兩筆」 | **應改用 depart→arrive**（純移動）才準；`arrive→depart`（停留期間）不該判速度 |
| 補算 `backfillMileage` | 不受影響（只看座標） | 無 |
| `personal-daily-report` | 可新增「今日行程已結束」訊號 | 非必要，列 OQ-TSM-10 |

### 6.3 回滾

CHECK constraint 放寬是**向下相容**的（舊值仍合法）。回滾只需把前端切回三型別；已寫入的 `depart_site` 資料不會讓舊程式碼崩潰（`listPunchesByDate` 原樣回傳字串）。**低風險。**

## 7. API 變更

### 7.1 新增 `GET /attendance/state`

前端不再自己用 `punches.length` 推狀態（現行 `PunchView.tsx` 的做法，加了 `depart_site` 後會推錯）。

```jsonc
{
  "state": "at_site",                       // not_started | moving | at_site | ended
  "allowedActions": ["depart_site", "clock_out"],   // 後端權威 · 前端只負責畫
  "lastPunch": {
    "punchId": "…", "punchType": "arrive_site",
    "punchedAt": "2026-07-27T06:12:00Z",
    "customerName": "福特斗六廠",
    "lat": 23.7, "lng": 120.5
  },
  "today": { "punchCount": 5, "tripCount": 2, "totalDistanceM": 38200 }
}
```

`lastPunch.lat/lng` 是給前端算「我離上一站多遠」用的（§5.1）。

### 7.2 `POST /attendance/punch` 加狀態驗證

| 目前狀態 | 允許的 punchType |
|---|---|
| `not_started` | `clock_in` |
| `moving` | `arrive_site`, `clock_out` |
| `at_site` | `depart_site`, `clock_out`, **`arrive_site`（僅當距上一站 ≥ 200 m）** |
| `ended` | `clock_in` |

違反 → `400`「目前狀態不允許此動作 · 請重新整理頁面」。

> **防呆必須在後端。** 前端只給一顆按鈕是體驗，後端擋狀態才是資料完整性——否則舊版 webview 快取、重送、或有人直接打 API 都會破壞序列。

**例外放行**：若當次打卡**取不到座標**（`lat/lng` 為 null），`at_site → arrive_site` 無法判距離 → **放行並標 `suspicious.missing_geo`**。寧可資料標記，不可讓員工在收訊差的地方打不了卡（見 FMEA F-3）。

### 7.3 冪等

同一 user、同一 `punchType`、**60 秒內**重複請求 → 不新增，回上一筆的 `punchId`（防連點與網路重送，見 FMEA F-2）。

## 9. 補打卡政策（回應「補打就容易變成作假」）

### 9.0 先劃清界線：「證據」不可補，「標籤」可以補

| | 是什麼 | 可否事後修改 |
|---|---|---|
| **證據**：座標、打卡時間、里程、路線折線 | 系統當下自動採集，用來證明「人在那裡」 | ❌ **一律不可改**（R11 原始不可變） |
| **標籤**：地點名稱（`customer_name`） | 給人看的名字，讓報表看得懂 | ✅ **可事後補填/修正** |

補填地點**不構成造假空間**——它不會讓一個沒去過的地方變成去過。反之，強迫「打卡當下必須先打完字」才是問題：打卡有時效（GPS、時間），打字沒有，把沒時效的輸入設成有時效動作的前置條件，順序就錯了。

> **已落地**（2026-07-27）：`PATCH /attendance/punch/:punchId/label`，員工在「我的行程」點該列即可補填；只更新 `customer_name`，`WHERE user_id` 擋跨員工 IDOR，audit 由全域 interceptor 記錄。

### 9.1 補打卡本身

**v1 明確不做補打卡。** 所有打卡一律取當下 GPS + server 時間。

理由：一旦開了補登入口，就要配套主管核准流程、補登理由、稽核報表，而**這個入口本身就會被當成常態使用**（業務的直覺是對的）。
若日後確有需求（忘打整站），走**主管代為補登 + 強制留理由 + `source='manual'` + audit log**，而非員工自助。→ OQ-TSM-9

## 11. 失效場景反思（FMEA · R17）

| # | 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|---|

### 11.1 三題 pre-mortem（`rule_pre_mortem_user_triggered_paths`）

- **5x 併發**：見 F-1/F-2 → 冪等 + busy lock。
- **濫用**：員工用假 GPS 定位軟體 → 狀態機**不改變**現有反作弊面（`computeSuspicious` 仍在）；但新口徑讓速度判定更準（只在 depart→arrive 判）。
- **競態**：見 F-4 → 單 tx 讀寫 + advisory lock。
