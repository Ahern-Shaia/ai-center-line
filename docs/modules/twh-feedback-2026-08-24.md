## 3. 🟠 誤解與文案（③⑤⑦）

### 3.1 ⭐ ③「已簽核」又「卡住 24 天」—— 兩個不同的軸，不是矛盾

看程式碼（`warroom-tasks.service.ts:213`）：

```ts
const isStuck = (r) =>
  r.work_status === "open"          // 事情還沒做完
  && r.confirm_status === "已簽核"   // 但主管已經確認過「AI 讀對了」
  && daysSince(r.created_at) > GRACE_DAYS;
```

| 欄位 | 真正的意思 | 總經理以為的意思 |
|---|---|---|
| `confirm_status = 已簽核` | **確認 AI 整理得對**（這件事真的存在、內容沒抽錯）| ❌「這件事處理完了」|
| `work_status = open` | 事情**還沒做完** | — |

**所以「已簽核 + 卡住 24 天」＝「你確認過這件事是真的，但 24 天沒人去做」——
邏輯完全一致，是「簽核」這個詞被誤讀。**

⭐ 這跟 `recordStatusLabel.ts` 早就記過的問題同源：
> `resolved` 刻意**不叫「已完成」**：那是 AI 讀到的（推論），而「完成」是本人回報的（承諾）。
> 兩者用同一個詞的話，看板上會出現「已完成但尚未確認完成」這種自相矛盾的句子。

**當時把這條紀律套在 `records` 上，卻沒套在 `tickets` 的「簽核」上。**

**建議改法（純文案，不動資料）**：

| 現在 | 改成 |
|---|---|
| 已簽核 | **已確認**（＋ tooltip：「主管確認過 AI 整理得對；事情做完沒有另外看『進度』」）|
| 卡住 24 天 | **確認後 24 天沒進度** |
| 待簽核 | **待確認** |

### 3.2 ⑤ 任務先給部門主管、需要才給總經理

**資料層本來就是這樣**：`tickets` 的 RLS 讓 `group_owner` 只看得到自己部門的任務，
`tenant_admin` 才看全公司。所以「總經理看到全部」是**他的角色本來的設計**，不是漏擋。

⚠️ 但客戶說的可能是**通知**不是**畫面** —— 現在還不確定他指哪一個：
- **(a) 畫面**：已經是分層的，不用改（要說明給他聽）
- **(b) LINE 通知**：目前指派通知只發給**被指派的那個人**（`assign-notify.service.ts`），
  沒有「先通知主管、主管決定要不要往上報」這條鏈
- **(c) 總經理不想看到全部**：那是他自己的角色範圍太寬 —— 可以用自訂角色做一個
  「只看摘要不看細節」的視角，但這是產品方向不是 bug

**這一項不寫需求，先問清楚**（OQ-TWH-4）。

### 3.3 ⑦「併發限制」是什麼 —— 客戶不該看到這個欄位

`concurrency` 是**分析批次同時跑幾個群組**的技術參數，屬成本控管。
`scheduler-config.service.ts:11` 的註解自己就寫了：

> 欄位級 whitelist · **tenant_admin 不能改**成本控管欄位（concurrency / lookback_days）

**改不了卻看得到 —— 那就是純粹的困惑來源。** 客戶會問「這是什麼」正是這個原因。

**建議**：租戶端**不顯示** `concurrency` 與 `lookback_days`（aiproot 端保留）。
這跟 08-21 那個「助理角色看得到、改不動、也用不了」是同一類。

## 4. 🟡 差最後一哩（①⑥）

### 4.1 ① 素材下載 —— 後端已經有了

`GET /media/:mediaId/content`（`media:view`）已存在，客戶的記憶是對的。
它現在回 `content-disposition: inline`（給縮圖與預覽用）。

**要做的**：
- 前端加「下載」按鈕
- 下載時要 `attachment` 而不是 `inline` → 加一個 `?download=1` 參數切換 disposition
- 中文檔名已經走 RFC 5987，不用另外處理

⚠️ **不要**用前端 `<a download>` 硬幹：跨來源時瀏覽器會忽略 `download` 屬性，
變成直接開新分頁。要在後端下對 header。

### 4.2 ⑥ 已簽核的資料存哪 + 搜尋

**存在「存查」頁**（任務看板右上「存查」按鈕）—— 客戶可能沒發現。
但目前有兩個實際限制：

```ts
const archived = notTracked.slice(0, 50);   // warroom-tasks.service.ts:296
```

- **只回 50 筆**，沒有分頁 → 累積久了看不到舊的
- **沒有搜尋**

**建議**：存查頁加分頁 ＋ 關鍵字搜尋（跟 ② 的素材搜尋一起做，兩者形狀一樣）。

## 5. 🔵 要開發（②④⑧）

### 5.1 ② 素材搜尋（日期／關鍵字）

現況只有「類型」篩選（`MediaLibrary.tsx:79`）。要加：
- 日期範圍
- 關鍵字（比對什麼？**檔名？群組名？訊息內容？** → OQ-TWH-2）

### 5.2 ④ 指派時同時通知其他人

現況 `assign-notify.service.ts` 只通知**被指派的那一位**。

要決定的是**通知誰**：
- (a) 固定加上該部門主管
- (b) 指派時可以自己勾要一起通知的人
- (c) 通知到 LINE 群組並 @ 那些人 ← 這條**已經有 M0**：[`notify-group-mention.md`](notify-group-mention.md)

⚠️ **注意 memory `project_line_group_never_speaks`**：2026-08-12 已裁定
**LINE 群組一律不出聲**（reply 是全群可見）。所以 (c) 要走**主動 push 到群**，
不是 reply，而且要重新確認那條裁定涵不涵蓋這種情境（OQ-TWH-5）。

### 5.3 ⑧ ⭐ 會議記錄 —— 最大的一項，且**不能直接開工**

客戶的原話：
> 他們有一整坨的會議記錄，可能有回覆所以直接進到已簽核，但這個項目還沒完成。
> 不知道會議記錄這個部分能否讓 AI 判讀並且進到會議記錄區之類的

拆開來其實是**三個不同的問題**：

| | 問題 | 性質 |
|---|---|---|
| a | 「有回覆就直接進已簽核」 | ⚠️ **可能是 bug** —— 要查完成訊號的判定是不是太寬鬆 |
| b | 「這個項目還沒完成」 | 同 ③ —— 已簽核 ≠ 已完成，可能又是命名誤解 |
| c | 「進到會議記錄區」 | 🔵 新功能：會議記錄要獨立成一個區域／分類 |

⚠️ **c 有一個現成的機制被忽略了**：AI 已經可以自己造分類，而 08-24 剛修好
「新分類必須用繁體中文」（`a477a61`）。所以「會議記錄」**可能不需要寫程式** ——
它可以是一個分類，在「任務設定 → 分類詞庫」裡管理。

但要先確認 a：**如果會議記錄是因為 bug 才跑進已簽核，那先修 bug，不是加新區域。**
