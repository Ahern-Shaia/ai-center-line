## 1. 觸發事件（2026-08-21 · 對廠商展示）

用戶展示組織圖時，廠商當場指出「**一位員工跨多個部門**」。

初步判斷有三種可能（A 一人身兼兩職／B 一人在多個 LINE 群／C 主管要看多部門），
用戶確認是 **B**。B 的好消息是資料層本來就記得住（`line_member` 唯一鍵是
`(bot_id, group_id, user_id)`，一人多列很正常），壞消息是查下去發現**根因不是 B**。

### 2.4 一個資料衛生問題

> 若該群不是 active 就根本不會被算進去。
> **實際有沒有汙染，取決於它的 `status`，M0.5 要查**（OQ-GTC-2 同批）。
> 但無論如何「測試群不該掛在真部門下」這件事本身仍要修。

### 2.5 更大的落差：56 人 vs 12 個帳號

| | 人數 |
|---|--:|

### 2.6 ⭐ 那 21 個「跨部門」的人，現在被算在哪一個部門？

寫完 v0.1 之後才去查的，而這其實是**廠商問題的直接答案**。

`employee-binding.service.ts:199` —— LIFF 綁定完成時，系統會推導主要部門：

```sql
SELECT lg.department_id, count(*) AS message_count
FROM line_message lm
JOIN line_group lg ON lg.bot_id = lm.bot_id AND lg.group_id = lm.group_id
WHERE lm.sender_line_id = <他> AND lm.sent_at > now() - interval '30 days'
  AND lg.department_id IS NOT NULL
GROUP BY lg.department_id
ORDER BY count(*) DESC
LIMIT 1          -- ← 發言最多的那個群，決定他的部門
```

**「一個員工跨多群組」在資料層早就解了**：`users.department_id` 是單值，
值＝「近 30 天發言最多的那個群所屬的部門」。組織圖上那 21 個人**每個都只有一個部門**，
跨的是「他在幾個群發言」—— 那是另一個維度，本來就不該畫進部門樹。

而且已有兩層防護（`member-department-assignment.md` 的設計）：
- 推不出來（30 天沒發言／那些群都沒接部門）→ `department_id = null`，落「未分派」等主管指派
- 主管手動改過的標 `department_source = 'manual'`，**自動推導日後不得覆寫**（Okta / Azure 的手動優先）

> ⭐ 所以本模組**不需要**讓 `users` 支援多部門。單值 ＋「主要部門」語意是對的。

### 2.7 但那個推導有三個洞

| # | 問題 | 狀態 |
|---|---|---|
| **① 全員群會汙染推導** | 「有你真好」40 人都在，而社交群通常話最多 —— 在那裡發言最多的人會被歸到「有你真好」這個假部門 | ❌ **本模組要修**（§4.5）|
| **② 只在綁定當下跑一次** | 半年前綁定時主要在業務群，現在調到技術部天天在技術群發言 —— `department_id` 還停在業務部，**沒有任何機制會發現** | ❌ 未解 · 見 OQ-GTC-11 |
| **③ 44 人根本沒觸發過** | 推導只在 LIFF 綁定完成時跑。群裡 56 人只有 12 個有帳號（§2.5），其餘從來沒走過這條路 | ❌ 未解 · 屬帳號覆蓋率那一案（OQ-9）|

⭐ **①和本模組是同一件事** —— 修好 `group_type` 就順帶修好它，而且是這次分類工作**最大的實益**。
v0.1 只想到組織圖與統計分母，漏了推導這一層。

## 3. 根因

**LINE 群至少有三種語意，而我們只有一種模型。**

| 種類 | 例子 | 語意 | 該定義組織嗎 |
|---|---|---|:--:|
| **部門群** | 福祉集團-業務部、台灣福祉法規組、福祉—品保部 | 一個組織單位 | ✅ |
| **流程／主題群** | 有你真好（全員公告）、報工及車輛調度（跨部門作業） | 一件事，參與者橫跨部門 | ❌ |
| **測試／私訊** | 福祉 分析表測試群、`AI-TWBRAUN, 柏淵` | 不是組織的一部分 | ❌ |

`line_group` 目前只有 `department_id` 一個欄位表達歸屬，於是三種都被塞進同一個結構。
結果就是「每個人都跨部門」—— **那不是組織的形狀，是我們的分類把它變成那樣。**

## 4. 設計

### 4.1 ⚠️ 一個原本想做、但被 schema 否決的方向

原本的直覺是「流程群不掛部門」（`department_id = NULL`）。**不行**：

```sql
-- 0001_init.sql:57
tickets.department_id uuid NOT NULL REFERENCES departments(...)
```

`tickets.department_id` 是 **NOT NULL**，而**流程群正是產出最多任務的地方**
（報工群 19 人、天天在報工）。拿掉部門關聯 → 材料化建卡直接失敗 → 那些任務**整批消失**。

> 這是為什麼要先讀 schema 再寫設計。少看這一行，M1 會在 prod 上炸。

### 4.2 正解：類型是「顯示與統計」的分類，不是「移除關聯」

`line_group` **加一個 `group_type`，`department_id` 一律保留**。

| 用途 | 讀什麼 | 流程群算不算 |
|---|---|:--:|
| 任務要掛在哪個部門（材料化） | `department_id`（照舊）| ✅ 算 |
| 組織圖的成員歸屬 | `group_type = 'department'` 才算 | ❌ 不算 |
| 部門健康度／簽核率的**分母** | 同上 | ❌ 不算 |
| 訊息分析、任務產出 | 照舊全部都跑 | ✅ 算 |

⭐ **關鍵取捨：流程群的任務仍然有部門、仍然要簽核、仍然進看板** ——
只是它**不再宣稱「這些人屬於那個部門」**。
把「資料歸屬」與「組織歸屬」拆開，是這份設計的全部內容。

### 4.3 資料模型（migration 0066）

```sql
ALTER TABLE line_group
  ADD COLUMN IF NOT EXISTS group_type text NOT NULL DEFAULT 'department'
    CHECK (group_type IN ('department','process','announcement','test'));
```

- **預設 `'department'`** —— 既有 13 個群行為完全不變（R1：破壞性變更要可回退）
- 回填由人判斷，不自動猜（OQ-GTC-3）

### 4.4 UI

- **通訊管道 → LINE 群組**：每個群多一個「群組類型」下拉，附一句說明
  （「流程群：跨部門協作用，成員不會被視為該部門的人」）
- **組織圖**：只吃 `department` 型的群；流程群另開一區「跨部門群組」，
  列出群名 + 人數，**不畫進部門樹**
- **部門健康度**：分母說明加一句「不含跨部門群組」

---

### 4.5 ⭐ 部門推導也要吃 `group_type`（v0.3 補）

除了組織圖與統計分母，**`employee-binding.service.ts` 的主要部門推導**也必須排除非部門群：

```sql
-- employee-binding.service.ts:199 的 WHERE 加一行
  AND lg.department_id IS NOT NULL
  AND lg.group_type = 'department'      -- ← 本模組新增
```

沒有這一行，一個在「有你真好」（全員群，40 人）發言最多的人會被歸到那個假部門。
**一行 SQL，解掉 §2.7 的問題①。**

⚠️ 這條改動**只影響之後新綁定的人**。既有的 12 個帳號不會自動重算 ——
要不要回頭重算是另一個決定（OQ-GTC-11），因為重算會動到已經手動指派過的人。

### 4.6 ⭐ 讓「他在哪些群」看得見（v0.4 補）

**現況：`line_member` 一列都沒有進到任何使用者看得到的畫面。**
它被後端用在訊息顯示名、完成訊號比對、指派人解析，但成員頁只有
「顯示名稱／Email／角色／所屬部門／密碼」—— 沒有「他在哪些群」。

於是廠商當場問「這個人是不是跨多個部門」時，**畫面上答不出來**，只能下 SQL。

| 想知道 | 現在 |
|---|---|
| 這個員工在哪些 LINE 群 | ❌ 只能下 SQL |
| 他的部門是怎麼推出來的 | ❌ 只能下 SQL |
| 某個群裡有誰 | ❌ 只能下 SQL（機器人管理頁只顯示人數）|

#### 做法：在「所屬部門」下面補出依據

`department_source`（自動判定／手動指派）**畫面上已經在顯示**，
但它只說「是自動判的」，**不說依據是什麼**。補上依據就同時回答兩個問題 ——
他在哪些群、以及為什麼被歸到這一個：

```
所屬部門
┌──────────────┐
│ 業務助理  ▾   │
└──────────────┘
· 系統自動判定 · 依 3 個部門群中發言最多的
  ⌄ 福祉業務助理小組 42 則 · 福祉集團-業務部 11 則 · 人資總務群 3 則
```

⭐ **為什麼併進本模組而不是另開一案**：「依 N 個**部門群**中發言最多的」這句話，
**只有在 `group_type` 修好之後才是真的** —— 現在會把全員群算進去（§2.7 ①）。
兩件事分開做，中間那段時間畫面會顯示一個**誤導的依據**，比不顯示更糟。

#### ⚠️ 這會把 PII 曝露到畫面上

`line_member.display_name` 是 LINE 暱稱，migration 0015 的註解自己就寫了
「**常是真名 · PII · 客戶需明確授權**」。

現在總經理看得到的是「有系統帳號的 12 個人」；開了之後會變成
「**在群裡講過話的 56 個人，含他們的 LINE 暱稱**」。
那是合理的（都是他公司的人），但**性質變了** —— 要跟客戶說一聲，不是默默打開（OQ-GTC-13）。

#### ✅ 落地形狀（2026-08-21 · M3.5 完成）

用戶裁定：**只做已綁定的 12 個人，不列沒帳號的** —— 也就是上面那段 PII 疑慮
（OQ-GTC-13）**直接不觸發**，畫面上出現的名字全都是本來就有系統帳號的人。
`line_member` 這次一列都沒用到。

| 檔 | 做了什麼 |
|---|---|
| `server/src/tenant-admin/member-group-activity.service.ts` | `user_line_binding` → `line_message` → `line_group` · 回 `userId → 群清單`（發言數多到少）|
| `GET /tenant-admin/users/group-activity` | `@RequirePermission("users:view")` · 與成員清單同權限 |
| `web/src/settings/depts-members/Members.tsx` | 「所屬部門」下方的依據區塊 · 三種狀態：自動判定／手動指派／沒發言 |
| `server/test/member-group-activity.test.ts` | 4 條 · 釘住「沒帳號的不出現」與「非部門群要回但標不計入」|

⭐ **兩個實作時才確定的形狀**：

1. **查詢必須跟 `employee-binding.service.ts` 走同一條 join**（`user_line_binding` 而非
   `line_message.sender_user_id`、同樣 `chat_context='group'`、同樣近 30 天）。
   差一個條件，畫面顯示的數字就不是當初做決定用的那組，使用者會拿它來質疑歸錯部門。
2. **非部門群要回傳但標「不計入」，不是不回傳。** 不回傳的話「他明明在那個群，
   為什麼沒算」在畫面上沒有答案 —— 而那正是廠商當場問的那一題。

#### 另外兩個位置（本次不做，記著）

- **組織圖的成員 chip 標「＋2 群」** · 輕，但資訊密度低，只適合當輔助
- **通訊管道 → LINE 群組加「成員」欄** · 反方向（從群看人）·
  順帶解掉 [`notify-group-mention.md`](notify-group-mention.md) 要的「選要 @ 的人」，兩者共用同一份資料

## 5. 企業級 cross-cutting

### 5.1 數字會跳動 —— 這是最大的溝通風險
改完之後部門人數、健康度、簽核率**都會變**（分母縮小）。
客戶看到數字一夜之間不一樣，第一反應是「系統壞了」。
→ 必須有**變更當下的對照說明**（改前／改後、為什麼），不能靜靜地換掉（OQ-GTC-7）。

### 5.2 觀測
`group_type` 的每次變更要進 `audit_log`（R5）—— 它會改變統計口徑，
事後追「那天數字為什麼變」需要這條線索。

### 5.3 容量與成本
一個欄位、一次回填，無新增查詢成本。組織圖少畫幾個節點反而更快。

### 5.4 向後兼容
`DEFAULT 'department'` ＝ 不回填就行為不變。
材料化、RLS、簽核流程**一行都不用改** —— 這是 §4.2 那個取捨換來的。

## 9. 失效場景反思（FMEA · R17 · M0 版）

| 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|:--:|---|
| 材料化 | 誤以為「流程群不該有部門」而把 `department_id` 設 NULL | `tickets.department_id` NOT NULL → **建卡失敗，報工群的任務整批消失** | **P0** | ✅ §4.2 結構上避開：`department_id` 一律保留，只加 `group_type` |
| 回填 | 把真部門誤標成流程群 | 該部門**從組織圖消失**，成員變未分派 | **P0** | ⚠️ OQ-3 人工判斷 ＋ 可還原（改回 `department` 即可，無資料損失）|
| 統計 | 分母改了但沒告知 | 客戶看到健康度一夜變動，判定「系統壞了」 | **P1** | ⚠️ OQ-7 改前／改後對照 |
| 資料 | 測試群仍分派在部門（§2.4 已存在）| 該部門人數與健康度長期偏差 | **P1** | ⚠️ M0.5 修掉 · 這是**現在就在發生**的錯 |
| 上線 | 組織圖改了、健康度沒改 | 兩處對同一件事講不同的數字 | **P1** | ✅ OQ-8 同批上線 |
| 推導 | 只改組織圖沒改 §4.5 的推導 | 全員群繼續汙染新綁定者的部門 · 而且**分類看起來已經修好了**，沒人會回頭查 | **P1** | ⚠️ M1 與 §4.5 同批做 · 不可只改顯示層 |
| 認知 | 客戶以為這解決了「員工跨部門」 | 若真有身兼兩職的人，期待落空 | P2 | ⚠️ 說明時講清楚：本次解的是**分類**，不是多對多（OQ-10）|

**M0 結論：兩個 P0 都圍繞同一件事 —— 分類改動不可以動到「任務掛在哪個部門」那條線。**
§4.2 把它結構性地隔開了，M1 實作時不得為了「乾淨」而把 `department_id` 清掉。
