## 1. 目標與範圍

### 1.1 目標

判斷鮮湧的「業務工作日誌」該用什麼形式搬進 LINE，並決定我方要不要為此建一個**可重複賣**的能力
（不是只為鮮湧做一次客製）。

### 1.2 為什麼現在談

- 鮮湧已是我方第三個租戶，但**實質未上線**（見 §2）
- 業務日誌是**每天、每人、強制**的動作 —— 導入成功與否直接決定續約
- 這個決策會**定義我方產品邊界**：做成表單就是往競品靠，做成抽取才是我方主張（§4）

### 1.3 不做的事

- 不在本文決定 Ragic 欄位對應（那屬 [`data-sync-layer`](data-sync-layer.md)）
- 不做通用「表單建構器」—— 那是另一個量級的產品

## 3. ⚠️ 缺的關鍵輸入：表單題型分佈

決策完全取決於題目的**性質比例**，不是題數。請把題目給我（截圖或貼文字），我方要判斷的是：

| 分類 | 例子 | 對 AI 抽取的難度 |
|---|---|---|
| **A. 敘述型** | 今天拜訪了誰、談了什麼、客戶反應、下一步 | ✅ 容易 —— 對話裡本來就會講 |
| **B. 可推導的結構** | 日期、拜訪對象、地點 | ✅ 中等 —— 通常講得出來，但可能省略 |
| **C. 強制結構** | 訂單金額、品項數量、成交與否、單選狀態 | ❌ **困難** —— 講話時常省略，抽不到就是空 |
| **D. 非文字** | 照片、簽名、GPS | ❌ 對話抽取拿不到，需另設計 |

**判準**：C + D 佔比。
- C+D **少** → 走純抽取（方案 B），我方主場
- C+D **多** → 純抽取的漏填率會讓資料不能用，須走混合（方案 C）

## 4. 三個方案

### 方案 A · LIFF 表單（把 Google 表單搬進 LINE）

業務員從圖文選單開表單、逐欄填寫、送出。

| 優點 | 缺點 |
|---|---|
| 欄位齊全、資料可直接進 Ragic | **這正是打卡之星／NUEIP 在做的事**（見競品分析）—— 往競品靠 |
| 行為與現況（Google 表單）一致，導入阻力低 | 員工端摩擦沒有降低，只是換個地方填 |
| 我方已有 LIFF 基礎建設（binding / punch / trips / mine） | 賣點退化成「不用開瀏覽器」，客戶會問「那跟 Google 表單差在哪」 |

### 方案 B · 純 AI 抽取（我方主張）

業務員照常在群組／私訊講話，AI 抽成結構化日誌。**已有的 `personal-daily-report` 就是這個形狀。**

| 優點 | 缺點 |
|---|---|
| **零輸入** —— 我方唯一站得住的差異化 | C 類欄位漏填率高，資料完整度不可控 |
| 基礎建設**已經 SHIPPED**（個人日報 + 確認迴圈） | 業務員不講的東西就是抽不到 |
| 抽取結果附 `source_ids` 可回溯（R11） | 若客戶要拿它做績效考核，漏填會有爭議 |

### 方案 C · 混合（AI 先抽 → LIFF 補齊）

AI 從對話抽出草稿 → LIFF 顯示 → 業務員**只補 AI 抽不到的欄位** → 送出。

| 優點 | 缺點 |
|---|---|
| 摩擦低於 A、完整度高於 B | 實作最複雜（要處理「哪些欄位算已填」） |
| 與既有 `personal-daily-report` 的「AI 產草稿、人確認」流程**同構** | 需要欄位級的信心度呈現 |
| 對外話術仍成立：「不用從頭填，只補 AI 不知道的」 | |

> 【推】カイクラ（日本，見 [`../market/模式驗證-カイクラ AI業務日報.md`](../market/模式驗證-カイクラ%20AI業務日報.md)）
> 走的正是 C 的變體：AI 生成 → 人在「下書き／完了」二態間把關。
> 它的教訓是**人為 gate 要放在「發布」而非「生成」**，否則零輸入的主張就破了。

## 5. 第四種可能：表單其實是搬運工

【推】鮮湧是食品業，aiproot 群組裡討論過他們的**生產製令單、客製列印格式、Ragic 主檔**。

如果那份 Google 表單的**真正目的是餵下游系統**（Ragic / ERP），那它本身就是中間的搬運工 ——
正解可能是**直接寫進 Ragic**（走 [`data-sync-layer`](data-sync-layer.md) + 既有 notify 模組的反向），
表單則整個消失。

**這要看題目才能判斷**，但若成立，它比 A/B/C 都好：少一個要維護的東西。

## 7. 落地順序（暫定 · 待 OQ 裁定）

| 里程碑 | 內容 |
|---|---|
| **M0** | 本文 · **等表單題目** + OQ 裁定 |
| **M0.5** | 資料整備：改 `extraction_template`、開群組分析、4 位未分派使用者歸部門、建真實業務群 |
| **M1** | 收集兩週真實對話語料，**先不做功能** —— 用真語料評估 AI 抽得到哪些欄位（回答 §3 的判準） |
| **M2** | 依 M1 結果實作（B 或 C）|
| **M3** | 2-3 人試點兩週，比對「AI 抽的」vs「他自己會填的」 |
| **M4** | 全面導入 + Ragic 匯流（若 OQ-2 是 (c)）|

> **M1 是刻意的**：現在沒有任何真實業務對話（19 則測試訊息、0 任務）。
> 不先看語料就決定抽取 schema，等於用猜的定資料契約 —— 那是 R1 明令要避免的。

## 8. 失效場景反思（FMEA · R17 · M1 前補全）

| 路徑 | 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|---|
| 抽取 | C 類欄位（金額、數量）長期抽不到 | 日誌不完整 → 客戶退回用 Google 表單 | **P0** | ⚠️ 待 M1 語料驗證；不足就走方案 C |
| 抽取 | AI 抽錯金額而業務員沒發現 | 績效/報表錯誤且無人察覺 | **P0** | ✅ R11 `source_ids` 回溯 + 確認迴圈；**數字類一律不推估（R11）** |
| 導入 | 業務員仍照舊填 Google 表單，兩套並行 | 雙軌 → 兩邊都不準 | P1 | ⚠️ 需與鮮湧約定切換日，不可長期並行 |
| 導入 | 試點期抽取品質差 → 業務員失去信任 | 之後再改也推不動 | **P0** | ✅ OQ-7 小規模試點；先確認品質再擴大 |
| 隱私 | 業務員發現「講的話都被 AI 讀」 | 抗拒、改用私下管道 | P1 | ⚠️ 需明確告知 + 可查閱（見日本市場研究的合規敘事） |
