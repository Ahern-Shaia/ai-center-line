## 1. 問題

**LINE 群組 ID（`Cxxxx…`）在 LINE App 裡看不到** —— 它不是給使用者看的東西，
只能透過 Messaging API 的 webhook 事件（`source.groupId`）取得。

客戶在什麼時候需要它？

| 情境 | 是否真的需要「原始 ID」|
|---|---|
| 連結群組給系統分析 / 分派部門 | ❌ 不需要 —— 系統已**自動註冊 + 自動抓群名**，後台按**名字**選 |
| 設定通知規則（notify 手動填群組 ID）| ✅ 需要原始 ID（目前決定「人工填 ID 最有彈性」）|
| 客戶自己想驗證「這個群是哪一個」| ✅ 想看到 ID |

⭐ **關鍵洞見**：這其實是**兩個不同的需求**，不要用同一個方案硬解：
- **A. 連結群組** → 目標是「**永遠不碰原始 ID**」，按名字選（現況已做到，要強化）
- **B. 真的要拿到原始 ID** → 給一個**最快的自助取得管道**（命令回覆）

## 2. 既有現況（查證 2026-07-31）

`line-webhook.service.ts`：

- **群組自動註冊**：bot 收到群裡任何事件 → `upsert line_group`（§146）
- **自動抓群名**：偵測到新群 → `autoProbeGroupName` 抓 display_name（§165）
  → 所以後台「通訊管道 → LINE 群組」列出的是**群名**，客戶不必看 ID
- **關鍵字→回覆機制成熟**：1-on-1 已有「設密碼」「日報」等關鍵字 → `replyMessage`（§405+）
  → 加一個「群組 ID」關鍵字是**零新機制**，建在既有 pattern 上
- **後台已有複製 ID**：通訊管道頁點群名下方灰字即複製完整 ID（notify 手冊 §7 寫過）

**所以缺的不多** —— 主要是「客戶在群裡就能自助拿到 ID」這條最快路徑還沒有。

---

## 3. ⭐ 巨人的肩膀

「LINE bot 怎麼讓人拿到群組 ID」是 LINE 生態的老問題，成熟做法有四種：

### 3.1 命令回覆（最普遍 · 幾乎每個 LINE bot 工具都有）
群裡打一個關鍵字（`群組ID` / `@bot id` / `/id`）→ bot 立刻回覆該群 ID。
- ✅ 最快、自助、不需後台權限、客戶自己就能做
- ⚠️ ID 會顯示在群裡（所有成員看得到）· 但群組 ID **不是機密**，只是雜訊

### 3.2 加入群時歡迎訊息（zero-effort）
bot 被加進群（`join` 事件）→ 自動回一則「已加入 · 本群已登錄 · 若需 ID：Cxxxx」。
- ✅ 零操作，加進去就有
- ⚠️ 同樣在群裡露出 ID

### 3.3 自動註冊 + 後台按名字選（現況 · 最適合「連結群組」）
bot 在群 → 系統登錄 + 抓群名 → 後台按名字選，**客戶完全不碰 ID**。
- ✅ 對「連結群組給部門/分析」是最佳解 —— 原始 ID 根本不該讓客戶處理
- ❌ 對「我就是要那串 ID」（notify 手動填）沒幫助

### 3.4 配對碼（pairing code · 隱藏原始 ID）
bot 在群裡貼一個短碼（如 `AB12`）→ 客戶到後台輸入短碼 → 系統對應到真實群。
- ✅ 客戶不碰醜長的 ID、比較好念
- ❌ 多一個步驟、多一張對應表

### 3.5 一句話
| 借來的 | 用在哪 |
|---|---|
| 命令回覆（3.1）| 需求 B「真的要 ID」的最快自助管道 |
| 加入歡迎（3.2）| 加群當下順手給，降低「不知道去哪拿」|
| 自動註冊+按名字選（3.3）| 需求 A「連結群組」，客戶永遠不碰 ID（現況強化）|
| 配對碼（3.4）| 若要完全隱藏 ID 的進階版（本期不做，複雜度不值）|

## 4. 提案設計（分兩個需求解）

### 4.1 需求 A「連結群組」→ 強化現況，客戶不碰 ID

現況已自動註冊 + 抓群名。要補的只有**讓客戶知道「群已經在系統裡、按名字選就好」**：
- 通訊管道頁對「剛偵測到、還沒分派部門」的群加一個「**新群 · 待分派**」標記
- （bot 加群歡迎訊息裡帶一句「此群已自動登錄，請到後台分派部門」）

### 4.2 需求 B「真的要原始 ID」→ 命令回覆（主方案）

在**群組訊息**處理加一個關鍵字（建議 `群組ID` 或 `#id`）：

```
使用者在群裡打：群組ID
bot 回覆：
  本群組 ID：
  Cxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
  （複製後可貼到通知設定的「LINE 目標群」）
```

- 建在既有 `replyMessage` + 關鍵字 pattern 上（§405 的群組版）
- ⚠️ 該關鍵字訊息**不落庫**（是指令、非工作記錄）—— 比照現有 1-on-1 關鍵字的處理
- 回覆用 `reply token`（免費），不是 push（計費）

### 4.3 加分：加群歡迎訊息（4.1 + 4.2 順手一起給）

bot `join` 群時回一則：
```
已加入！本群對話會由 AI 每日整理成日誌。
· 需要本群 ID（設定通知用）：在群裡打「群組ID」我就回你
· 分派部門請到後台「通訊管道」
```
一次講清楚兩條路，客戶不用問窗口。

## 5. ⚠️ 這裡藏著一個更大的問題（單一固定 bot 的租戶歸屬）

用戶說「**我司有一個固定的 Line Bot**」。若這是**一支共用 bot 服務所有客戶**（非每租戶一支），
那「群組 ID」不是最難的 —— **「這個群屬於哪個租戶」才是**：

- 現況 `line_group` 靠 `bot_id → tenant_id` 推租戶。**一支共用 bot 的話這條就斷了**，
  所有客戶的群都掛同一個 bot，系統無法自動判斷群屬於誰。
- 這時 **4.4 配對碼**反而變成剛需：群裡貼碼 → 特定租戶的 admin 在後台輸入碼 → 完成
  「這個群 = 這個租戶」的認領（同時解決 ID 與租戶歸屬）。

> **先確認：這支 bot 是「一租戶一支」還是「全體共用一支」？**（OQ-GID-1）
> 若共用，本模組的重點要從「拿 ID」轉成「群組認領（claim）」，設計不同。

## 6. FMEA（P0 先列）

| 失效模式 | 影響 | 嚴重度 | 緩解 |
|---|---|---|---|
| 共用 bot 下，群組被錯誤歸到別的租戶 | 跨租戶資料混入 | **P0** | 🔒 若共用 bot → 必走「認領」機制（配對碼 + admin 確認），不可自動歸屬 |
| 關鍵字太常見（「id」）誤觸、洗版 | 群裡噪音 | P1 | 🔒 用不易誤觸的關鍵字（`群組ID` / `#群組id`）· 30 秒內重複只回一次 |
| ID 回在群裡被截圖外流 | 低 —— 群 ID 非機密，只能配合 bot token 才有意義 | P2 | ✅ 可接受 · 但文案不要顯示 tenant 相關資訊 |
| 關鍵字訊息被當工作記錄落庫 | 污染日誌 | P1 | ✅ 指令訊息不落庫（比照現有 1-on-1 pattern）|

| # | 問題 | 為什麼要先問 |
|---|---|---|
| **OQ-GID-1** ⭐ | 這支固定 bot 是**一租戶一支**還是**全體共用一支**？ | 決定性 —— 共用的話重點從「拿 ID」變「群組認領+租戶歸屬」，設計完全不同 |

| **OQ-GID-3** | 要不要做 4.3 加群歡迎訊息？（會在客戶群裡自動發言）| 有些客戶不喜歡 bot 主動發言，要確認 |
| **OQ-GID-4** | 長期要不要讓客戶**完全不碰原始 ID**（notify 也改成按名字選）？ | 若是，需求 B 只是過渡，最終走純「按名字選」|
