## 1. 系統上下文與部署拓撲

```
                LINE Platform ──webhook──▶ [1] Bot/Ingest ──▶ raw_messages(DB)
                                                                    │
  ┌──────────────── 地端 On-prem（Docker Compose / K8s）────────────┼───────────────┐
  │ [1] Bot/Ingest 服務   [2] 去識別前處理   [3] 批次 Worker(cron)                     │
  │ [4] 地端多模態(Whisper/OCR/NER/BGE-M3)   [5] Grounding   [6] 簽核/同步 Worker      │
  │ [7] Web API + 前端(戰情室)   [8] PostgreSQL(RLS)   [9] Redis(鎖/outbox佇列)        │
  │ [10] RAG 索引(BGE-M3 向量庫)                                                       │
  └───────────────────────────┬──────────────────────────────────────────────────┘
                              │ 僅去識別文本 + 已遮罩圖（HTTPS）
                              ▼
                  雲端 Claude API（分類/抽取/vision/摘要）

```

| 項目 | 選型 | 備註 |

## 1-B. 合夥人原型對齊（功能盤點・缺口・設計缺陷）

> 依據：`合夥人/戰情室原型_taiwan_homecare_war_room (3).html`（tenant_admin／總經理室單視角，合夥人確認的需求呈現）。本節盤點原型全部功能、對齊本文件、補上缺口，並反思設計缺陷。

### B1. 原型功能盤點
1. **Header**：系統名＋副標（Powered by aiproot · LINE×Ragic×工研院RAG）、登入身份（總經理室・全群組總覽）、AI 引擎狀態、即時時鐘、**主題切換（暗/亮）**、**語言切換（中/EN）**。
2. **三環形儀表**：簽核完成率（即時計算，簽核後重算）、健康度（4/6 綠燈）、高信心比例（**標「本案場實測」**，8/13）。
3. **三 KPI 卡（含趨勢）**：本月維修工單 47 **↑12% 較上月**；知識庫 312 **↑18 件/週**；待人工確認 6（即時攔截層）。
4. **六大群組即時狀態**：群組名＋燈號＋**Ragic 表友善名（員工日報表/維修服務單/車輛改裝進度表/訂單與採購總表/行政公告與總務表/法規與技術KM）**＋相對更新時間＋**處理狀態細節（影像辨識 2 筆處理中／OCR 手寫單 1 筆待核／2 筆設備報修未派工）**＋技術表名。
5. **每日簽核面板**：每群組一列——名稱、count（X 筆待簽核／✓ 已由〈簽核者〉確認·時間）、**展開明細（逐筆列出＋高/中/低信心 tag、低信心・已即時攔截）**、確認鈕（確認後轉「已確認」disabled）。
6. **智慧檢索/對話（多模態 RAG）**：多輪對話、AI 回答**附來源引用（來源: 維修工單 WO-2506-041、圖紙 v2、已同步工研院RAG）**、**AI 主動追問（followup）**、輸入框。
7. **多模態素材看板**：媒體卡（圖示依類型、檔名、來源群組、類型 tag IMAGE/VIDEO/DOCUMENT/TABLE）。
8. **全台客戶地理資訊**：台灣地圖標記＋各縣市案場數清單（台北/新北 5、台中 3、彰化 2、高雄 4、南投 1、其他 6）。

### B3. 缺口補強（schema / API deltas）
```sql
-- B3-1 群組友善名 + 處理狀態細節
ALTER TABLE departments ADD COLUMN display_name text;   -- 「員工日報表」等友善名（技術名仍為 ragic_table）
-- 群組即時狀態細節（處理中/待核/未派工…）由 tickets 依 status 聚合即可，前端顯示；必要時 status 補 enum（處理中/待核/未派工/已結）。

-- B3-2 KPI 趨勢（每日快照，供「較上月/每週」環比）
CREATE TABLE metric_snapshots (               -- 每日一列/租戶，避免趨勢造假
  tenant_id uuid NOT NULL REFERENCES tenants, snapshot_date date NOT NULL,
  monthly_service_tickets int, km_documents int, pending_review int,
  PRIMARY KEY (tenant_id, snapshot_date));    -- 趨勢＝今日 vs 上月同期/上週；無足夠快照則不顯示趨勢

-- B3-3 RAG 多輪對話 + 引用
CREATE TABLE rag_conversations ( id uuid PK, tenant_id uuid, user_id uuid, created_at timestamptz );
CREATE TABLE rag_messages (
  id uuid PK, conversation_id uuid REFERENCES rag_conversations, role text CHECK (role IN ('user','ai')),
  content text, citations jsonb,              -- [{type:'維修工單',ref:'WO-2506-041'},{type:'工研院RAG',ref:'#0142'}]
  followup text,                              -- AI 主動追問建議
  created_at timestamptz );

-- B3-4 全台客戶地理（台灣福祉自有 CRM；與 tenants 不同層級）
CREATE TABLE customers (                      -- 台灣福祉的終端客戶（車輛買主/維修對象）
  customer_id uuid PK, tenant_id uuid NOT NULL REFERENCES tenants,
  name text, city text, district text, address text, lat numeric, lng numeric );
ALTER TABLE vehicles ADD COLUMN customer_id uuid REFERENCES customers;  -- 車↔客戶
```
- **API 補**：`GET /km/query` 改為 session 制（`POST /rag/conversations`＋`POST /rag/conversations/:id/messages`，回傳含 `citations`＋`followup`）；`GET /warroom` 回傳加入各群 `display_name`、處理狀態細節、KPI `trend`（有快照才給）、`GET /customers/geo`（縣市聚合，供地圖）。
- **簽核即時重算**：確認 API 回傳後，前端 refetch `/warroom` 或 optimistic 更新，儀表隨簽核數即時重算（對應原型 `updateSignoffGauge()`）。

### B4. 設計缺陷反思（⚠ 動工前處理）
1. **趨勢造假風險**：原型的「↑12% 較上月」是示意數字。**無 `metric_snapshots` 歷史就不得顯示趨勢**——否則違反「誠實鐵律」（§9），委員會質疑。要嘛建快照、要嘛先不放趨勢。
2. **「客戶」命名混淆**：地圖的「客戶」＝台灣福祉的**終端車主/維修對象**（`customers` 表），**非 aiproot 的租戶（tenants）**。兩層概念，schema 與 UI 文案都要明確分開，別讓委員誤解成「aiproot 客戶分布」。且此資料源（台灣福祉自有 CRM）仍待確認是否存在。
3. **暗色主題 vs blueprint**：原型有暗/亮切換，但本專案前端已定案 **blueprint「只淺色」**（§B0-BP，用戶多次確認）。**暗色不做**——原型的暗色是舊設計，以 blueprint 淺色為準。i18n（中/EN）若委員或未來海外需要再做，非首期必需（一線員工全中文）。
4. **「本案場實測」標籤要當真**：高信心比例與效能數字須為**台灣福祉真實資料實測**，不可沿用他案（呼應原型標籤與 §11 SFT 警告）。首期以真實訊息量校正後才放上簡報。

## 5. 訊息接入與每日批次（流程時序）

### 5.1 Ingest（即時）
```
LINE webhook → 驗簽章(X-Line-Signature) → 依 group_id 找 department → 寫 raw_messages(processed=false)
  → 若 media：立即下載 content → 存物件儲存 → 記 media_object_key（LINE URL 有時效）
  → opt_out 成員訊息標 opt_out=true（不分析）
```

### 5.2 批次（cron，冪等）
```
03:00 Asia/Taipei，每租戶一次：
1. 取 Redis 鎖 lock:batch:{tenant_id}（防重入）；產 batch_run_id
2. SELECT raw_messages WHERE tenant_id=? AND processed=false AND opt_out=false ORDER BY created_at
3. 去識別前處理（§6）→ 依 department 分組
4. 每 department：會話切分＋事件聚類 → 呼叫該 department 的抽取 schema（§7）
5. LLM 回傳 → grounding 還原 token（§7.5）→ upsert tickets（source_message_ids 冪等去重）
6. 抽 KM → knowledge_cards → 佇列 RAG 索引
7. UPDATE raw_messages SET processed=true, batch_run_id=? WHERE id IN (...)
8. 逾時掃描：confirm_status='待簽核' AND now()-created_at > overdue_window → '逾時警示'
9. 釋放鎖；失敗自動重試 3 次後告警（不標 processed，下次重跑）
```
**冪等鍵**：`(tenant_id, source_message_ids)` 去重，重跑不重複產 ticket。

## 6. 去識別前處理（地端）

- **偵測**：規則（車號正則、電話）＋ 輕量繁中 NER（人名/客戶/地址）。
- **替換**：實體 → `EMP_/VEH_/CUST_` token；查/寫 `employee_pseudonym_map`（同實體同 token）。
- **輸出**：去識別文本；圖像先過人臉/車牌遮罩。**對照表不出地端**。
- 還原（§7.5）：LLM 結果中的 token 依對照表回填為 `*_id`。

## 7. AI 分析管線

### 7.1 路由
`raw_messages.group_id → departments.line_group_id → departments.extraction_schema`。schema key 對應一組 prompt＋輸出 JSON schema（zod 驗證）。

### 7.2 抽取（雲端 Claude，分階）
每 department 綁定模型與 schema（見 §3.2 選型表）。呼叫用 structured output（`output_config.format`）＋ prompt caching（system+主檔詞庫為穩定前綴）。每筆輸出含 `confidence`；`low` 標 `needs_review`。

### 7.3 事件聚類/合併
同 department 內，以時間鄰近＋實體重疊（同車號/工單）＋語意相似聚類；一事件多訊息 → 單 ticket，狀態 open→in_progress→resolved 隨後續訊息更新；`source_message_ids` 累積。

### 7.4 KM 抽取
偵測「經驗/根因/預防建議」語意 → 生成 `knowledge_cards`（title/body/entity_tags/source）→ BGE-M3 索引。

### 7.5 Grounding
token → 主檔比對（employees/vehicles/work_orders）＋ `tenant_vocabulary` 詞庫消歧；對不到 → 保留原文並降 confidence、進 `pending_review`。

### 7.6 信心度
誠實輸出，不系統性高估（system prompt 強制）；戰情室高信心比例即由此統計。

## 8. 簽核與同步

### 8.1 簽核狀態機
```
待簽核 ──group_owner 確認──▶ 已簽核 ──enqueue outbox──▶ (sync worker)
   └──now-created_at>overdue_window──▶ 逾時警示 ──補簽──▶ 已簽核
低信心(needs_review) 須先補資訊才可確認（API 擋）
代簽：consultant 且 can_proxy_signoff=true → 已簽核, proxy_by=consultant, audit_log(proxy_sign)
```

### 8.2 同步（Outbox）
```
確認交易內：UPDATE tickets SET confirm_status='已簽核',confirmed_by,confirmed_at
            + INSERT ragic_sync_outbox(target='ragic',payload)  （同交易，保證入列）
sync worker：SELECT ... WHERE done_at IS NULL FOR UPDATE SKIP LOCKED
            → Ragic API 寫入 → 成功:sync_status_ragic='已同步',done_at=now()
            → 失敗:attempts++,last_error, 指數退避重試；ticket 顯示「同步失敗」徽章（不回退簽核）
技術研發群組另 enqueue target='itri'（工研院 RAG）
```

## 9. 指標計算與健康度（戰情室資料源）

參考實作：`src/warroom/aggregate.ts`（已實跑）。

| 指標 | 公式 | 來源 |
|---|---|---|
| 簽核完成率 | 已簽核 department ÷ 部門數 N | tickets.confirm_status |
| 健康度 | 綠燈 department ÷ 部門數 N | 狀態機↓ |
| 高信心比例 | high ÷ 當日已標 | tickets.confidence |
| 待人工確認 | count(pending_review WHERE reviewed_at IS NULL) | pending_review |

> **N = 該租戶實際 department 數（後台配置，非固定；台灣福祉示範為 6）**。分母一律動態取該租戶部門數，**勿寫死 6**。`aggregate.ts` 已用 `data.departments.length`；M4 `/warroom` API 與前端卡片數同樣依 N 動態。

**健康度狀態機（參數可租戶設定）**：`active_window=24h, overdue_window=24h, inactive_red=72h`
```
綠：活動≤active_window 且 無逾時 且 無低信心待簽核
黃：活動≤active_window 且（低信心待補 或 待簽核未逾時）
紅：待簽核逾 overdue_window  或  無活動>inactive_red
```

### 10.1 內部（戰情室）
| Method Path | 角色 | 回傳 |

## 12. 可觀測性與失效

- **audit_log**：所有 view/sign/proxy/export/km_query。
- **告警**：批次失敗、Outbox 積壓、LLM 連續失敗、逾時警示數異常。
- **LLM 失效**：佇列等待或切地端小模型，戰情室標「分析延遲」，不靜默跳過。
- **日誌**：結構化，含 tenant_id/batch_run_id 便於追蹤。

## 13. 測試規格（開發驗收）

| 類型 | 案例 |
|---|---|
| 單元 | 去識別遮罩正確率；事件聚類合併；grounding 消歧；健康度狀態機邊界 |
| 整合 | 批次冪等（重跑不重複產 ticket）；Outbox 重試；Ragic 寫入失敗不回退簽核 |
| 權限（E2E） | tenant(A) 查 tenant(B)→403/空（API＋RLS 雙驗）；aiproot 查 tickets→僅 COUNT，取不到 summary |
| 反幻覺 | 模糊訊息（無車號「門壞了」）→ low+needs_review+攔截；未簽核不入 Ragic |
| 簽核 gate | 未簽核不進 Ragic；簽核後 audit_log 有記錄；逾時自動轉警示 |
| 代簽 | 授權後代簽→proxy_by＋徽章＋audit(proxy_sign) |
| 不外流 | 抽查上雲 payload → 皆 token、無原始媒體/語音 |
