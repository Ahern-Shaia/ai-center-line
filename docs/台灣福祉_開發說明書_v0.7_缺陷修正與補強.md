# 台灣福祉 AI 智慧戰情室 — 開發說明書 v0.7（缺陷反思與設計補強）

> 定位：**補強 v0.6（CTO 版），不取代**。v0.6 的四層角色單一應用、tickets 通用事件表、human-in-the-loop 簽核方向正確且保留。本文只做兩件事——(A) 逐項指出 v0.6 的缺陷與矛盾，(B) 把每個缺口補成可實作、可驗收、可對委員交代的規格。
>
> 讀者：CTO／工程團隊（Boyuan、Zonghan）＋簡報負責人。P0 = 動工前必須決策；P1 = 開發中必須補；P2 = 上線前補。

# Part A — 缺陷反思

## A1. 架構級矛盾（P0，未解會被委員或客戶當場問倒）

### A1-1 「全地端、資料不外流」與「Claude API 雲端分析」直接矛盾 ★最嚴重
v0.6 §十 寫「全地端部署，避免雲端 API 費用與資料外流風險」，但 §三架構圖、§九 System Prompt、成本原則同時把 **Claude API** 當分析引擎。**送 LINE 對話（含員工姓名、車號、客戶名）到 Anthropic 雲端，就已經外流。** 委員問答準備文件宣稱「模型運算、資料儲存、檢索都在客戶環境內完成，不透過雲端 API」——這句話與現行 prototype（本專案就是用 Claude API）**互相打臉**。這是可信度的頭號風險，必須先決策（見 B1）。

### A1-2 多模態（OCR／影像／語音）技術現實未面對
售後（照片/影片關聯）、報工（影像/語音辨識）、業務（OCR）都重度依賴多模態，但：
- 沒說 vision/ASR 跑在哪個模型。Claude vision（雲端，強）與地端開源模型（弱、中文與工業場景落差大）差距巨大。
- §八 說長期用地端 SFT Llama 3 8B/11B——**這類小模型的多模態與繁中工業術語抽取能力，撐不起 demo 展示的效果**。用 Claude 做 demo、上線改地端小模型，會有「展示效果 vs 實際效果」的落差（§八自己也警告過不可混用數字）。

### A1-3 consultant「代簽」是治理漏洞，不是待確認小事
v0.6 §十二 把「consultant 是否可代簽」列為 TODO。但這動搖**整套系統的核心賣點**：「AI 不自己說了算，由客戶負責人把關」。若系統商的顧問（Sandy）能代替客戶 group_owner 簽核，那把關的就不是客戶、責任歸屬斷裂，稽核性崩解。這是 P0 決策，不是選配（見 B10-代簽）。

## A2. 合規與資安缺口（P0/P1）

- **知情同意流程只有一張 `consent_log` 空表，沒有流程**：誰在何時、對哪個群組、用什麼文案取得同意？成員中途加入/退出 LINE 群怎麼辦？政府補助 + 員工對話 = 個資法（PDPA）高敏感，這塊空白會是審查與法遵風險。
- **假名化只寫「user_id 假名化處理」五個字，沒有方法**：可逆映射表？單向雜湊？對照表存哪？grounding（把「阿明」對回 employee）需要可還原，但可還原就有還原被濫用的風險。方法未定義（見 B2）。
- **完全沒有 `audit_log`**：一套主打「治理、可溯源、租戶隔離」的系統，卻沒有存取稽核表。誰查了哪個租戶、看了哪筆 summary、何時——無法回答，也就無法向委員「證明」隔離有效（見 B3）。
- **原始訊息保存期限未定義**：`raw_messages.content` 存員工對話原文，存多久？永久？這對個資最小化原則不利（見 B2）。
- **租戶隔離只靠「API 層不回傳 summary」單一防線**：一行 API 邏輯寫錯就洩漏跨租戶資料。缺 DB 層 Row-Level Security 作縱深防禦（見 B3）。

## A3. 資料模型不一致（P1）

- **`tickets.module_type` enum（KM/訂單/客服/維保）與六大群組對不齊**：六群組是技術工程/售後服務/報工生產/業務一部/人資總務/技術研發，硬塞進四個 module_type 會失真。應以 `department_id` 為主鍵路由，module_type 若保留須重新定義或降為標籤。
- **「五大 Agent」vs「六大群組」數量不符**：§九 System Prompt 只定義了 生產報工/售後維保/研發法規 等（且自稱五大），但群組有六個，**人資總務沒有對應 Agent 與抽取 schema**（見 B5）。
- **`raw_messages.reply_token` 存進 DB 意義不大**：reply_token 約 1 分鐘失效，批次（每日一次）跑到時早已過期，存了也不能用。應移除或明確標註只在即時路徑短暫使用。
- **`licenses` 同時有 `tenant_id` 與 `department_id`**，但商業模式寫「一企業、一部門、一 License」——到底是租戶級還是部門級授權？「席位（seat）」如何定義與計數（是 group_owner？還是所有能登入的 employee？）未定義，直接影響給委員看的營收模型。
- **缺 `updated_at` 一致性與 tickets 版本**：AI 重跑或人工修正後，舊值如何保留？correction_log 有記錄，但沒有回饋到 `tenant_vocabulary` 或 SFT 的學習迴圈設計。

## A4. 可靠性與可運營缺口（P1）

- **批次沒有失效設計**：跑幾點？時區？跑到一半掛了怎麼辦？重跑會不會重複產生 tickets（冪等性）？`processed` boolean 有幫助但沒有重試/死信/backfill 機制。
- **簽核→Ragic 同步的失效未處理**：`confirm_status=已簽核` 觸發 `sync_to_ragic=true`，但**若 Ragic 寫入失敗**呢？狀態已是「已簽核」，資料卻沒進 Ragic，且沒有重試——會產生「以為同步了其實沒有」的靜默資料遺失（見 B6）。
- **健康度燈號門檻未定義**：委員文件說「超過設定時間無活動→紅燈」，但「設定時間」是多少？可否每租戶設定？綠/黃/紅的精確狀態機沒寫（我在 prototype 先假設 24h，但 spec 的人資範例用 3 天，前後不一）（見 B7）。

## A5. 商業與範圍缺口（P1/P2）

- **成本控制只有定性、沒有數字**：42 萬補助案，委員會期待成本拆解。每租戶每日 token 量、20 租戶月成本、地端 GPU capex（SFT Llama 要 GPU）全缺（見 B8）。
- **工研院多模態 RAG 整合是黑箱**：被當技術差異化核心，但整合契約（API/認證/資料格式/IP 歸屬/SLA）只有一個電話號碼在 TODO。技轉 vs 委外都沒定（見 B11）。
- **全台地理地圖與核心系統正交**：它是台灣福祉自有 CRM 的資料，跟 LINE-AI 主線無關，對 demo 是加分但對開發是 scope creep；資料來源還是 TODO。

## A6. 文件自身問題（P2）

- **範例資料用了疑似真實人名**：§九 System Prompt 範例 `"employee_name": "黃柏源"`——與交付對象「Boyuan」疑似同一人。對外文件與 demo 應一律假名化（見本專案 mock 已全面假名化的做法）。
- **五/六 Agent 數量、版本引用**前後不一致，宜統一。

# Part B — 設計補強（把缺口補成可實作規格）

## B1. 部署與模型架構決策（解 A1-1 / A1-2）✅ 已決策（2026-07-03）

**決策：「只有服務部署在地端」——戰情室 Web 服務、資料庫、原始媒體、語音、知識庫索引皆在地端；LLM 分析可用雲端 API，但一律吃「去識別後」的內容。** 這把「地端」的範圍精確界定在**服務與資料層**，解開了 v0.6「全地端」與「Claude API」的矛盾。

**精確資料流：**
```
【地端 On-prem】
  戰情室 Web 服務 + DB（raw_messages / tickets / audit_log / 假名對照表）
  raw_messages → 去識別前處理（NER＋規則遮罩：人名/車號/客戶名/電話 → 佔位 token）
  語音 → 地端 ASR（音檔不出場）
  影像 → 地端人臉/車牌遮罩
  知識庫 Embedding/RAG 索引（BGE-M3，繁中）→ 索引不出場
        │  僅「已去識別文本＋已遮罩圖」出場
        ▼
【雲端 Cloud LLM】Claude 分類/抽取/摘要/vision（看不到可識別個資）
        │  回傳結構化結果
        ▼
【地端】以對照表還原 token → employee_id / vehicle_id（grounding）→ 寫 tickets
```

**「資料不外流」的誠實定義（委員話術照此改）**：**服務、資料庫、原始媒體、語音、知識庫索引皆在地端；送雲端的僅為去識別後的文本與已遮罩圖像。** 不宣稱「完全不透過雲端 API」——而是「機敏原始資料與可識別個資不出場，雲端只看得到去識別內容」。這句可信、可驗（見 B10 測試）、且不牴觸事實。

## B1-M. 多模態模型選型（解 A1-2）✅ 由技術判斷逐場景指定

原則：**品質優先用雲端 Claude（吃去識別內容），但含生物特徵/高敏感的模態（語音、知識庫索引）留地端**；純異音等專門聲學任務先以務實替代方案，不假裝 LLM 做得到。

| # | 群組・場景 | 模態 | 選用模型 | 部署 | 理由 |
|---|---|---|---|---|---|
| 0 | 共用・去識別前處理 | 文字 | 地端 NER（規則＋輕量繁中模型） | 地端 | 遮人名/車號/客戶/電話 → token，是上雲的前提 |
| 1 | 技術工程・報工日報 | 文字 | **Claude Haiku 4.5** | 雲端 | 日報格式固定、抽取簡單，用最省的一階 |
| 2 | 售後服務・維修工單 | 文字＋照片 | **Claude Sonnet 4.6（vision）** | 雲端（車牌遮罩後） | 需把異常照片與文字做因果關聯，vision＋推理要中階 |
| 2b | 售後・影片「異音檢測」 | 音訊 | 地端 ASR 轉技師口述；**真·聲學異常偵測列為專門 ML、本期不做** | 地端 | 自動異音辨識是專門聲學任務，非通用 LLM 能力；先靠技師口述＋人工，誠實標示 |
| 3 | 報工生產・進度照片 | 影像 | **Claude Sonnet 4.6（vision）** | 雲端（遮罩後） | 改裝進度視覺理解 |
| 3b | 報工生產・語音回報 | 音訊 | **Whisper large-v3（地端）** | **地端** | 語音含生物特徵，音檔不出場；輸出去識別逐字稿再上雲 |
| 4 | 業務一部・報價/訂單 | 文件/表格 | **Claude（vision 文件理解）**；地端備援 **PaddleOCR** | 雲端（遮客戶名後）／地端 | 繁中表格版面理解 Claude 強；要求純地端的客戶用 PaddleOCR＋LLM |
| 5 | 人資總務・行政/報修 | 文字 | **Claude Haiku 4.5** | 雲端（去識別後）；敏感人事可切地端小模型 | 分類指派為主，簡單；人事敏感度高時可整群留地端 |
| 6 | 技術研發・KM/法規 | 長文字 | **Claude（長上下文摘要）＋ BGE-M3 embedding（地端索引）＋ 工研院 RAG** | 混合 | 知識庫索引地端不外流；生成用 Claude 或工研院 RAG（依 B11 契約） |

> 說明：Claude 分階（Haiku→Sonnet→Opus）依場景複雜度選，控成本又不犧牲關鍵場景品質。語音與知識庫索引刻意留地端，正好強化 B1 的「不外流」定義。日後若客戶要求更純地端，可逐群組把 Claude 換成地端 SFT 模型（模組化，不動架構）。

## B2. 個資治理與假名化設計（解 A2）

**假名化**：
```
employee_pseudonym_map          -- 僅存地端，不進雲端、不進 aiproot
  tenant_id      uuid FK
  employee_id    uuid FK
  pseudo_token   string          -- 送分析用的佔位符，如 "EMP_a3f9"
  -- 對照為受控資料，存取寫入 audit_log
```
去識別採**佔位 token（可還原）**而非單向雜湊，因為 grounding 需還原；但對照表存取受 RBAC + 稽核控制，且**絕不隨結果進雲端或 aiproot 視圖**。

**知情同意流程（state machine）**：
```
群組導入 → [公告同意文案 via LINE] → consent_log 記錄(notice_date/notice_text/版本)
        → 成員可退出（退出者訊息不納入分析，raw_messages 標 opt_out）
        → 文案版本變更需重新公告
```
`consent_log` 補欄位：`notice_version`、`acknowledged_by`（若採主動同意）、`opt_out_user_ids`。

**保存期限（資料最小化）**：`raw_messages.content` 原文保存 **N 天（建議 30–90，租戶可設）後刪除原文、僅保留結構化 tickets 與去識別摘要**；媒體檔即收即存但設 TTL。新增 `retention_policy(tenant_id, raw_message_days, media_days)`。

## B3. 稽核與租戶隔離縱深防禦（解 A2 / A3）

**新增 `audit_log`（治理系統的必要件）**：
```
audit_log
  id          uuid PK
  actor_user_id uuid FK
  actor_role  enum
  action      enum        -- view_tenant / view_ticket / sign_off / export / assign_consultant ...
  tenant_id   uuid        -- 被存取的租戶
  target_id   uuid, nullable
  result      enum        -- allowed / denied
  ip          string
  created_at  timestamp
```
- **DB 層 Row-Level Security（RLS）作第二道防線**：不只 API 過濾，DB policy 依連線帶的 `tenant_id`/`role` 強制過濾。API 邏輯寫錯時仍擋得住跨租戶查詢——這才敢對委員說「隔離經得起測試」。
- `aiproot_admin` 的查詢在 DB 層即被限制為聚合檢視（view 只暴露 COUNT/GROUP BY，物理上取不到 `tickets.summary`）。

## B5. 訊息路由與 Agent 對應（補齊 v0.6 §5 / §9）

**完整路由表（含第六個 Agent）**：

| # | 群組 | 路由鍵 line_group_id → | 抽取 schema | Ragic 表 | Agent 職能 |
|---|---|---|---|---|---|
| 1 | 技術工程 | department D1 | 報工日報（姓名/工時/工項） | HR_daily_reports | 生產報工 Agent |
| 2 | 售後服務 | D2 | 維修工單（車號/異常件/處置） | CRM_service_tickets | 售後維保 Agent |
| 3 | 報工生產 | D3 | 改裝進度（影像/語音→備註） | MES_production_progress | 生產進度 Agent |
| 4 | 業務一部 | D4 | 採購/訂單（OCR→子表格） | ERP_order_management | 業務訂單 Agent |
| 5 | **人資總務** | D5 | **行政異動/設備報修（指派/追蹤）** | HR_admin_tickets | **人資行政 Agent（v0.6 缺，補上）** |

## B6. 失效處理與冪等（解 A4）

- **批次冪等**：以 `raw_messages.id` 為冪等鍵，`processed` 標記 + 批次 run_id；重跑不重複產 tickets。批次固定時間（建議 03:00 Asia/Taipei）、取單一鎖避免重入、失敗自動重試 3 次後告警。
- **Ragic 同步用 Outbox pattern**：簽核只做兩件事——`confirm_status=已簽核`＋寫入 `ragic_sync_outbox`。獨立 worker 排空 outbox、重試、更新 `sync_status`。**Ragic 寫入失敗不回退簽核**（人已把關），但 ticket 顯示 `同步失敗` 徽章、列入待處理，避免「以為進 Ragic 其實沒進」的靜默遺失。
- **LLM 失效**：雲端不可用時，降級為佇列等待或切地端小模型（依 B1 方案），並在戰情室標「今日分析延遲」，不可靜默跳過。

## B7. 健康度燈號狀態機（補 §7，可租戶設定）

```
參數（tenant 可設）：active_window = 24h，overdue_window = 24h，inactive_red = 72h
綠燈：最近活動 ≤ active_window 且 無逾時 ticket 且 無低信心待簽核
黃燈：最近活動 ≤ active_window 且（有低信心待補 或 有待簽核但未逾時）
紅燈：有 ticket 待簽核逾 overdue_window（→逾時警示）  或  最近活動 > inactive_red（無活動）
```
（本專案 `src/warroom/aggregate.ts` 已按此邏輯實作並實跑驗證 33%/67%/62%，可作為參考實作。）

## B8. 成本模型（量化，解 A5；數字為估算，須以實測校正）

**假設**：每租戶 6 群組、每日約 150–300 則訊息、每日批次一次、prompt caching 命中主檔。

| 項目 | 方案①純雲端估算 | 方案③混合估算 |
|---|---|---|
| LLM/租戶/日 | ~NT$30–80（視訊息量與模型） | ~NT$15–40（去識別後較短、敏感群組地端） |
| 20 租戶/月 | ~NT$1.8–4.8 萬 | ~NT$0.9–2.4 萬 |
| 地端 GPU capex | 0 | 1 張推論級 GPU（vision/ASR/敏感群組），一次性 |
| 資料外流風險成本 | 高（合規） | 低 |

> 本專案 PoC 實測：單群組單日 AI 推論約 NT$1–2（Opus 4.7 + caching）。上表為放大估算，**送委員前須以台灣福祉真實訊息量重跑校正**，且效能數字標明「本案場實測」或「參考基準」（呼應 §八 警告）。

## B9. 非功能需求（NFR，v0.6 完全缺）

- **批次 SLA**：每日分析須在客戶上班前（建議 08:00）完成，否則戰情室當日無資料。
- **可用性**：戰情室 Web 應用目標 99.5%；批次失敗有告警與人工介入 runbook。
- **備份/DR**：DB 每日備份、異地保存；地端部署需定義硬體故障的復原程序（RTO/RPO）。
- **規模目標**：20 租戶 × 6 群組 × ~300 則/日 ≈ 36,000 則/日的處理與儲存規劃；tickets 表按 tenant_id 分區。
- **安全 hardening**：地端部署的作業系統/網路隔離、金鑰管理、最小權限、依 B3 稽核。

## B10. 驗收與測試計畫（解 A4「宣稱 vs 證明」落差）

系統的三大對外宣稱都要有**可當場驗**的測試，這是委員簡報的底氣：

| 宣稱 | 驗收測試 |
|---|---|
| 租戶隔離 | 以 tenant_admin(A) 帳號嘗試查 tenant(B) 資料 → API 與 DB RLS 皆回 403/空；aiproot_admin 查任一租戶 tickets → 只得 COUNT，取不到 summary（DB view 物理隔離） |
| AI 不幻覺/不硬寫 | 餵入語意模糊訊息（如「門壞了」無車號）→ 系統標 low + needs_review + 攔截，**未簽核前 sync_to_ragic=false**、不計入正式統計 |
| 簽核 gate | 未簽核的 ticket 不出現在 Ragic；簽核後才寫入且 audit_log 有記錄 |
| 逾時警示 | 造一筆超過 overdue_window 未簽核 → 自動轉逾時警示 + 紅燈 |

**consultant 代簽決策（收斂 A1-3）✅ 已採用**：**預設不可代簽**；若導入初期需協助，採「代理簽核」但**強制標記 `confirmed_by=consultant(代 group_owner X)` 並寫 audit_log**，且需客戶端一次性書面授權（`consultant_assignments` 增 `can_proxy_signoff` + `authorized_by` + `authorized_at`）。維持責任可追溯，不讓把關失真——代簽在戰情室與 Ragic 皆顯示「代簽」徽章，客戶隨時可稽核。
