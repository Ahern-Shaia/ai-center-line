# 市場研究 · 日本為何沒人做「群組對話 → 工作記錄」

> 版本：v1.0（2026-08-05）｜分析人：ahern + Claude Code
>
> **為什麼查日本**：LINE 是日本公司、在日本滲透率與台灣同級，LINE WORKS 在日本企業市場比台灣普及得多。
> 若連日本都沒有人做「群組對話 → AI 工作記錄」，那**不是沒人想到，而是有結構性的難處**——
> 而那個「難在哪」比任何競品的功能清單都有價值。
>
> **一句話結論**：**日本確實沒有人做，而且原因不是技術。**
> 是 (A) LINE WORKS **根本沒開「讀群組訊息」的一般 API**，唯一路徑是監查／モニタリング下載 API，
> 需付費方案＋管理者權限＋事前同意設定——**你只能把產品定位成「監控工具」而非「效率工具」**；
> 加上 (B) 厚労省指針要求監控員工須訂社內規程並明示、(C) 日本主流論述正在勸企業**停止用消費級 LINE 談公事**、
> (D) 這個品類已被佔位成「不正偵測」而非「工作記錄」。
> **這四點在台灣全都不成立。我方的機會窗來自台灣的制度縫隙，不是技術領先。**

## 4. ⭐ 為什麼沒人做？四個具體障礙

### (A)【官】平台面 —— LINE WORKS 根本沒開「讀群組訊息」的一般 API

**這是最硬的結構性障礙。**

- Bot **無法**進入含 LINE 使用者或外部 LINE WORKS 使用者的聊天室
- **沒有「指定 talk room ID 取訊息列表」的 API**
- 唯一取得訊息內文的路徑是**監査／モニタリング下載 API**
  （2025-11 底舊 `/audits/logs/download` 廢止，改 `/monitoring/message-contents/download`）

該路徑要求：

| 條件 |
|---|
| **付費 Standard 以上方案**（Standard 只能監控 talk，Advanced 才含 mail／Drive）|
| 管理者被授予「監控」權限 |
| `monitoring.read` scope |
| **管理畫面事前同意設定為必須** |
| 保存僅 **180 天** |

> **也就是說，在日本要做這件事，必須把產品定位成「監控／稽核工具」，而不是「效率工具」。**
> 這直接決定了它在客戶心中的位置——而「監控」在勞資關係上是完全不同的一場仗。

### (B)【官】法規面 —— 不是不能做，但**必須明示、不可偷偷做**

厚生労働省《雇用管理個人情報指針》明定監控員工須：

1. 事先特定目的與利用目的、**訂入社內規程並向員工明示**
2. 定監控責任者與權限
3. 規程草案事前周知全社
4. 妥善管理實施狀況

判例基準是**「必要性＋相當性」**，核心是「**不是躲起來監視，而是把規則講清楚再執行**」。
實務見解：檢查公司伺服器上的郵件**不需要本人同意**，但不得僅憑模糊懷疑就調查。

> 【推】**法規不是禁止，是提高導入成本**：需社內規程、勞資說明。
> 對 SaaS 而言，「每個客戶導入前都要先改社內規程」是致命的摩擦。

### (C)【三】文化／敘事面 —— 日本主流論述正在勸企業**停止**用 LINE 談公事

社労士事務所、SaaS 廠商大量產出「LINE 業務使用絕對該停」的內容，理由是：
資料綁個人手機與帳號、離職帶走、外洩無 log 可追。

日本的既定解方是**遷移到 LINE WORKS／專用 App**。

> **我方「員工照常用 LINE」的賣點，在日本正面對撞主流合規敘事。**
> 在台灣則沒有這股逆風——中小企業普遍用消費級 LINE 群組談公事是既成事實。

### (D)【三】既有品類已被佔位成「風險偵測」而非「工作記錄」

**エルテス《AI テキスト分析服務》**（2023-03 起）已在做 mail／Slack 內文 AI 分析，
但抓的是**不正交易、回扣、侵占、內線交易、職權騷擾**。

> 日本企業對「AI 讀員工聊天」的既有心智模型＝**內控監控**。
> 新進者要先花力氣扭轉這個定位。

---

## 5. ⭐ 日本已接受「被動訊號」，但只用在時間，不用在內容

【官】日本有成熟的零操作出勤產品：

| 產品 | 做法 |
|---|---|
| **ラクロー** | 主打「**打刻レス**（免打卡）」：先取客觀 log 為準，反推勞動時間 |
| **MITERAS**（PERSOL）| PC log 對比申報工時、抓「隱形加班」 |

驅動力是日本法定的**労働時間客観把握義務**——使「被動訊號取代自我申報」有**法源正當性**。

> **關鍵洞察**：日本已接受「被動訊號做出勤」（PC log／門禁／人臉），
> **但被動訊號只用在「時間」，不用在「內容」。**
> **跨越「時間 → 內容」那條線的，日本沒有人。**

## 6. 對我方的結論

### 6.1 機會窗的來源

| 日本的阻礙 | 台灣是否成立 |
|---|---|
| (A) 平台不開群組訊息 API | ❌ **不成立** —— LINE Messaging API webhook 可直接收群組訊息 |
| (B) 監控須訂社內規程並明示 | ❌ 無等價的行政指導壓力 |
| (C) 主流論述勸企業別用消費級 LINE | ❌ **相反** —— 台灣中小企業用 LINE 群組談公事是常態 |
| (D) 品類被佔位成內控監控 | ❌ 台灣尚無此既有心智模型 |

> **我方的機會窗來自台灣的制度縫隙，不是技術領先。**
>
> 這句話有兩個推論：
> 1. **不要以為有技術護城河。** 護城河是領域抽取準確率與客戶資料累積，不是「想到用 LINE」。
> 2. **台灣既有的 7 家 LINE 打卡廠商隨時可以進來** —— 他們已經有客戶基數與 LINE 整合，只差一層抽取。
>    （見 [市場地景](市場地景-台灣出勤與工作記錄.md)）

### 6.2 若未來要打日本

【推】**卡點在 LINE WORKS 的 API 政策，不是 AI 能力。** 三條可能路徑：

1. 走監査 API，**接受「監控工具」定位**，賣給已有合規需求的企業
2. 等 LINE WORKS 開放（不可控）
3. 換語料 —— 學カイクラ 走通話錄音，但那就不是我方的命題了

### 6.3 對產品的直接啟示

- 日本的 (B)(C)(D) 雖然在台灣不成立，但**它們指出的疑慮是真的**：
  「AI 在讀員工的對話」這件事，客戶遲早會問。
- **提早準備好敘事與機制**：明確告知、可查閱、可關閉、來源可溯源（R11）、audit log（R5）。
  這些在台灣目前不是法規要求，但**是把「監控」翻譯成「留證」的關鍵**——
  而後者正是我方對員工端的既有主張（「不是監控，是替員工留證」）。
