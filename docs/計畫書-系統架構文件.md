# LINE 群組 AI 對話分析系統 — 系統架構與技術方案

（產發署數位轉型補助計畫・技術章節素材，v1，2026-07-02）

---

## 一、方案概述

### 1.1 痛點

台灣中小製造業的現場溝通高度依賴 LINE 群組（研發、技術、報工、維保），造成資訊極度碎片化：

- 員工每晚以自由格式文字傳日報，無法統計、無法追蹤漏交
- 研發與採購決策散落在聊天室，事後找一筆記錄動輒 30 分鐘起跳
- 老師傅的維修經驗（故障原因、處理手法、預防建議）隨訊息洗版流失，**工廠隱形知識（KM）完全無法留存**
- 主管無法掌握多群組的即時狀態，管理靠人肉爬訊息

### 1.2 解題思路

**不改變工廠員工的使用習慣**——員工照常在 LINE 打字、拍照，由後端 AI 通盤處理：

> LINE 多群組對話 → AI 語意分析 → 結構化匯流（Ragic ERP／知識庫）→ AI 戰情室

對員工而言，AI 不是「多一套要學的系統」，而是「幫我把表填好的助理」。

### 1.3 本案開發範圍（三大模組）

| 模組 | 內容 |
|---|---|
| 模組一：AI 群組導入與語意分析 | AI 助理加入工作群組，對文字日報、出勤變動、工程照片進行自動語意分析 |
| 模組二：自動分類與匯流 | 分析結果自動格式化、分類，經 API 匯流至 Ragic ERP 與知識庫後台 |
| 模組三：AI 戰情室後台 | 獨立管理後台，整合客服、訂單、維保進度，主管一目了然所有群組運作狀態 |

## 二、系統架構

```
┌────────────── 工廠端（不改變使用習慣）──────────────┐
│   LINE 群組：研發 ｜ 技術 ｜ 報工 ｜ 維保               │
│   文字日報・出勤變動・工程照片・維修討論                  │
└─────────────────┬──────────────────────────────┘
                  │ LINE Messaging API（Webhook 即時事件）
                  ▼
┌────────────── AI 分析引擎（本案核心開發）─────────────┐
│  1. 事件接收與落庫    原始訊息保全；照片/影片即收即存        │
│  2. 會話切分         以日為週期＋事件脈絡，保留前後文        │
│  3. 語意分類         日報/出勤/維保/研發/採購/閒聊 六類     │
│  4. 結構化抽取       以主檔 grounding：人員/機台/工單對應   │
│  5. 事件合併與知識卡片 跨訊息事件（報修→查修→修復）合併單筆   │
│  6. 工廠詞庫         台語/黑話/機台代號，每廠累積專屬資產    │
└───────┬──────────────────────────┬──────────────┘
        │  確認迴圈：AI 草稿以 Flex Message 卡片回群組，
        │  員工/主管一鍵確認後才正式入庫（human-in-the-loop）
        ▼                          ▼
┌── 結構化資料 ──┐          ┌── 知識庫（KM）──┐
│  Ragic ERP     │          │  公研院知識庫後台  │
│  報工/出勤/維保  │          │  知識卡片・向量檢索 │
│  （API 寫入）   │          │  LINE 反向問答 bot │
└───────┬───────┘          └────────┬────────┘
        ▼                           ▼
┌─────────────── AI 戰情室後台 ───────────────────┐
│  群組健康度・日報繳交率・未結異常清單・跨群搜尋・警示推播  │
└─────────────────────────────────────────────┘
```

### 2.1 資料流說明

1. **接入層**：一個 LINE 官方帳號（OA）bot 可加入多個群組，以 groupId 對應「工廠 × 群組類型」；Webhook 即時接收訊息事件。媒體檔案的下載連結有時效，採**即收即存**策略保全。
2. **冷啟動**：LINE Messaging API 無法回溯 bot 加入前的歷史訊息，導入時由客戶直接匯出聊天記錄（.txt），**第一天即可用歷史資料完成分類法調校**，不需等待收集期。
3. **AI 分析層**：以 LLM（Anthropic Claude）進行分類與結構化抽取。關鍵設計是**主檔 grounding**——抽取時以該廠的 Ragic 主檔（人員、機台、工單）為對應依據，將「阿明」「1號機」「018」解析為 P-002、M-001、WO-2506-018，而非自由生成。
4. **確認迴圈**：AI 抽取結果以 Flex Message 卡片回貼群組，一鍵確認後入庫。同時解決三件事：資料品質、導入信任、員工「被監控」的心理阻力（AI 是幫忙填表，不是監看聊天）。
5. **雙軌輸出**：進度類資料（報工/出勤）走結構化 API 寫入 Ragic 表單；知識類內容（維修經驗、研發決策）摘要成知識卡片進知識庫，支援向量檢索與 **LINE 反向問答**（師傅在群組問「3號機上次過熱怎麼處理」，bot 直接回歷史處理記錄）——資料流雙向，員工自己有動機讓知識進系統。

### 2.2 與 Ragic 的整合介面

| 方向 | 介面 | 用途 |
|---|---|---|
| Ragic → AI 引擎 | Ragic HTTP API（讀） | 拉取主檔：人員、機台、工單、客戶，作為抽取 grounding |
| AI 引擎 → Ragic | Ragic HTTP API（寫） | 確認後的日報/出勤/維保記錄寫入對應表單欄位 |
| AI 引擎 → 知識庫 | REST API | 知識卡片（標題/內文/實體標籤/來源訊息）匯入公研院知識庫後台 |

範例欄位對應（報工日報 → Ragic 報工表單）：

| AI 抽取欄位 | Ragic 欄位 | 範例 |
|---|---|---|
| date | 報工日期 | 2026-06-29 |
| reporter_code | 人員編號 | P-002（陳志明） |
| machine_code | 機台編號 | M-001（1號機） |
| work_order | 工單號 | WO-2506-018 |
| output_qty / defect_qty | 產出 / 不良數 | 1250 / 12 |
| overtime_hours | 加班時數 | 1 |
| issues | 異常備註 | 3號機早上卡料停約20分 |
| confidence | 信心等級 | high（低信心者標記待人工複核） |

## 三、概念驗證（POC）成果

已完成端到端 prototype（LINE 匯出檔 → AI 分類抽取 → 結構化輸出 → 視覺化報告），以三個模擬工廠群組（報工、維保、研發採購，共 77 則訊息，含台語混寫、口語、照片、多行日報）實測：

| 驗證項目 | 結果 |
|---|---|
| 訊息分類覆蓋率 | 100%（77/77，零漏分類、零低信心） |
| 日報結構化 | 8 筆全數正確，欄位完整 |
| 實體對應 | 暱稱→人員編號、機台口語→機台編號、工單簡稱自動補全，全數正確 |
| 台語/黑話理解 | 「teh叫」「歹去」等經詞庫正確解析 |
| 跨訊息事件合併 | 橫跨一日 10 則零碎訊息的維修事件（報修→判斷→拆檢→換件→恢復）合併為單筆完整記錄，狀態自動標記「已解決」 |
| 隱形知識抽取 | 師傅口述的預防性建議（「軸承壽命偏短，下次保養用雷射對心儀校正」）獨立留存為知識卡片 |
| 資料誠實性 | 缺漏欄位輸出 null 不臆測；推斷值自動降信心等級 |
| AI 推論成本 | 約 NT$1–2／群組／日（prompt caching 命中率 100%，快取讀取成本為原價 1/10） |

**成本推估**：以每廠 4 個群組計，AI 推論成本約 NT$150–300／月／廠，具備對 20 家以上客戶規模化的成本結構。

## 六、資安與個資治理

1. **知情同意**：AI 助理加入群組前，於群組公告分析用途與範圍，並取得企業與成員同意；提供退出機制。
2. **資料最小化**：閒聊類訊息僅分類、不留存內容；只結構化與業務相關的資料。
3. **傳輸與儲存安全**：全程 TLS 加密；API 金鑰集中管理；媒體檔案存取權限控管。
4. **多租戶隔離**：各廠資料（含詞庫、主檔、知識庫）邏輯隔離，互不可見。
5. **法遵**：符合個人資料保護法；AI 推論不將客戶資料用於模型訓練（採用具此承諾之商用 API）。
6. **可稽核性**：每筆結構化記錄保留來源訊息 ID 與確認人，全程可追溯。

## 七、風險與因應

| 風險 | 因應設計 |
|---|---|
| LINE API 無歷史訊息回溯 | 導入時以聊天記錄匯出檔冷啟動，bot 只負責之後的即時流 |
| AI 抽取錯誤損害信任 | Flex Message 一鍵確認迴圈；低信心記錄標記待人工複核；錯誤案例回饋至詞庫 |
| 員工抗拒「被監控」 | 不改變使用習慣；AI 定位為「幫填表的助理」；閒聊不留存 |
| 各廠用語差異大 | 每廠獨立詞庫（台語/黑話/機台代號），隨使用累積，形成可規模化資產 |
| LINE 推播訊息費用 | 確認卡片優先使用免費 reply token；push 訊息量納入成本監控 |

## 附錄：POC 技術棧

- 解析層：TypeScript／Node.js，LINE 聊天記錄匯出檔解析器（12 小時制、多行訊息、媒體標記）
- AI 層：Anthropic Claude API（結構化輸出保證 schema 合法、prompt caching 降低成本、adaptive thinking）
- 會話切分：以日為週期切分，保留事件完整前後文
- 輸出：JSON（供 API 匯流）＋ HTML 視覺化報告（demo 用）
